# factory-rf

The second implementation of the factory (github.com/pkrahmer/factory), planned and built by the factory itself: v1.1, v1 reimplemented by v1, and since the handover built by v1.1 itself. The pipeline's rules reach every agent in its instructions (the shipped agent files under `claude/agents/`), so this file holds only what is true of this project. `docs/project-guide/README.md` is the guide for agents: read it, then the files it names for the domains your story touches, before you change anything.

## Language
- Everything in this repository is English: code, comments, docs, work items, commit messages.

## Vocabulary
- v1's history (its stage table, its forms and its features F0001 to F0017, in v1's words) was `factory/v1/`; it is kept at the tag `planning-history-2026-10-19`, with the planning history.
- Everything else, the pipeline's own files under `factory/` included (the pipeline definition, the story and feature forms, the features and their work items), uses the glossary's names: work item, journal, backlog, start, approval, pipeline definition, write paths, project commands, acceptance reviewer, smoke test, error (R3). Stall, lease, crash, `time_limit` and provider limit keep the meanings the decision log gives them.

## Architecture
- One package, `factory`, under `src/` (Python 3.12, uv). Four layers; a higher one may import a lower one and never the reverse: `factory.entry` → `factory.adapters` → `factory.application` → `factory.domain`. import-linter enforces this in `make check`.
- `factory.domain`: pure rules and data, the Pydantic DTOs and the decisions made on them. No I/O, no tool, no clock or process of its own.
- `factory.application`: the use cases (the pipeline, its stages, claim, lease and recovery) and the interfaces they need from the outside: the hosting service, the agent runtime, the project commands. It knows no concrete tool.
- `factory.adapters`: the wrappers, readers and writers behind those interfaces: git, PyGithub, `claude -p`, make, ruamel.yaml, python-frontmatter, and the fake hosting service the tests use.
- `factory.entry`: the command line and the wiring that picks the concrete adapters. Nothing else wires.
- Wrappers (R5). Git, each agent runtime and the build commands are each reached only through one wrapper class (`claude_runtime`, `opencode_runtime`), and what the runtimes share lies in `factory.adapters.agent_launch`; the hosting service only through the hosting-service interface. No other module calls a command-line tool.
- Interfaces (R6). Where other stacks will want other tools, an interface stands in front, and v1's tool is its first implementation. Nothing is built for the other stacks now, but no interface or DTO may rule them out.
- Interfaces are abstract base classes: a class in `factory.application` deriving from `abc.ABC`, every operation an `@abstractmethod` whose body is its docstring alone, no state. Every implementation the factory writes, fakes included, inherits its interface (`class GitCli(Git):`), so the class says what it implements and Python refuses an incomplete one. `typing.Protocol` is only for shapes of code the factory does not own (a stand-in for a third-party object in a test). Decided by the human on 2026-10-13.
- DTOs (R7). Inputs and outputs are Pydantic models shaped by what the factory needs, not by the tool. A wrapper translates them into call parameters and the tool's output text back into return types. No `dict[str, Any]` crosses a function boundary.
- Layers belong to the project (R8). The factory knows no layer names: a project declares its layers and checks them with a project command, and the DTOs carry a generic check result. Do not copy the todo demo's split into this code.
- Git and the hosting service (R9). The git command-line tool sits in a wrapper class with DTOs; PyGithub sits behind the hosting-service interface. Not GitPython, pygit2, dulwich, githubkit, the `gh` tool or plain httpx.
- The hosting-service client (R10) does pull requests only: create as draft or ready, read state and merge state, list comments with id and author, post with the marker, close and reopen; and labels, written as a projection of the stage and never read back. One fake implements the same interface.
- Project commands (R11). The factory calls a project-commands interface; the make-based class is its first implementation (make targets that call uv). Gradle or npm implementations come with those stacks.
- Agent runtime (R12). An agent-runtime interface with factory-shaped DTOs; the first implementation wraps `claude -p`, the second `opencode run`, each under the login its files hold (a subscription token or an API key) or, for an operator's opencode build, the login it keeps in the agent's home. Every agent run starts through `factory-confine`, which restricts the run's writes with Landlock to its write paths, its tool paths and its own temporary folder; after every call the runtime ends every process the agent's user still runs (`factory.entry.leftovers`, as that user), and after every run the factory removes the checkout's git-ignored paths, so nothing a run leaves behind reaches the checks; every project command runs as the agent's user too (`sudo`, the agent's own `timeout`, `env -i`), with the checkout's git folder sealed, and is followed by the same end of the agent's processes; every agent run and every project command starts from a fresh agent home (`factory.entry.fresh_home`, as that user), so no code an agent wrote runs as the factory's user and no run reads or inherits what an earlier one left in the home other than uv's package cache; the undo after the run reverts whatever else changed outside the write paths, and no hook judges a tool call. The runtime is chosen per instance (`FACTORY_AGENT_RUNTIME`).
- File formats (R13). ruamel.yaml (keeps comments and order when it rewrites YAML the human edits) and python-frontmatter, each format behind one reader and one writer class, validated into Pydantic DTOs.
- Type everything; `mypy --strict` is part of the checks. `Any` only at a boundary that Pydantic validates immediately.
- Before changing the architecture, read `docs/decisions.md`; lasting reasons are there.
- Before writing a helper, search `src/factory` for one that does the same, and reuse or extend it; the reviewer counts a second copy of an existing helper as a finding.

## Tests
- pytest. Tests live under `tests/` and mirror the package: `tests/domain/`, `tests/application/`, `tests/adapters/`, `tests/entry/`, each folder a package with an `__init__.py`; a module outside the layers is tested at the `tests/` root.
- Plain test functions, shared fixtures in `tests/conftest.py`, parametrize for tables of cases. Never mock the code under test.
- Fake: the hosting service, through its one fake implementation; the agent runtime, through a fake implementation of its interface.
- Do not fake git. Tests use a real local bare remote and clones in a temporary directory (`tmp_path`).
- No network, no sleeps, no files outside `tmp_path`.
- No test, no smoke test and no command a stage runs by hand runs `factory.entry.leftovers` as the user it names, and none calls `factory.adapters.process.signal_every_other`: the program ends every process of its own user, and in an agent's run that is the run itself (and under `make check`, which runs as the agent's user too, the check itself). Tests inject `kill`, `processes`, `identity` and `sleep`; a child process of the real program names a user it does not run as, so it refuses before its first signal. A runtime test passes a stand-in program as `leftovers`, never the real command.
- No test and no smoke test runs `factory.entry.fresh_home` with a `--home` outside its own temporary folder, and none calls `factory.adapters.home_files.clear_home` or `SudoAgentHome.reset` on one: the program removes every file its user made in that folder, and in an agent's run that user is `agent` and its home holds the run's own session.
- A test whose child must do something before its time limit kills it (write a record or a pid file, print a line, finish a first call) gives it `ROOMY_LIMIT` of `tests/time_limits.py` (ten seconds) and bounds the elapsed time by `ROOMY_BOUND_SECONDS`: `make test` runs on every core, and on 2026-10-19 a stand-in started through `factory-confine` needed more than three seconds to write its first record. A test whose child need not start to be killed may keep a shorter limit. What a stand-in waits that the limit must end is longer than the bound, so a missed kill fails; never a check that a limit is met to the tenth.
- A test that fails under `make check` and passes when run alone is reported, never only named: the entry names the test and quotes, from the failed run's output, the lines of its failure that pytest printed (the `E` lines and the `file:line` of the failing line, from `--tb=short`). Without that text the cause of a failure seen once cannot be traced.
- Tests pass `mypy --strict` once the code exists: never use the value of a call to a function typed `-> None` (no `assert f() is None`); call it as a statement. To test that a Pydantic model refuses an unknown or a wrong-typed field, construct it through a variable typed `type[BaseModel]` (the pydantic mypy plugin types the real constructor); no `type: ignore`. Fake commit ids and other hex test values are low-entropy (`"a" * 40`), so `make secrets` stays green without a baseline entry.
- Two more `mypy --strict` traps in tests: assign to a field of a frozen model with `setattr(instance, field, value)`, the field's name in a variable (a direct assignment is `misc`, a constant name is ruff's `B010`); and call an abstract class through a variable typed `type[object]` (`interface: type[object] = Git`), as `tests/application/test_interfaces.py` does (a direct call is `abstract`). A third: `dataclasses.replace(instance, **{name: value})` is checked against every field, so a row that replaces one field picked by name fails `arg-type`; make each row a typed `Callable[[T], T]` (`pytest.param(lambda b: replace(b, checkout=b.checkout / "elsewhere"), id="checkout")`).
- A test that sets a file on `main` through `human.push_file` (`tests/human_clone.py`) pushes only when the text differs from what `main` already holds (for example `PIPELINE_YAML`, which the `remote` fixture already has): an unchanged file makes the commit empty, and `GitCli.commit` raises `NothingToCommit`.
- A pipeline definition written in a test passes every load-time rule unless the test is about that rule: a `done` stage, every role's `time_limit` plus the `time_limit`s of its stage's checks and reports within its `lease_duration`, names that exist, values in their YAML type (see `docs/project-guide/stages.md`, *The pipeline definition*). Otherwise every test that parses it fails before it reaches the code under test.
- Every limit the Interface states is tested on both sides, also when no criterion spells out the refused side: a field typed `NonNegativeInt` gets a test with `-1` and one with `0`; "three or more" gets a test with two; "at column 0" gets an indented case. The reviewer counts an untested side as a finding.
- `tests/test_model_configuration.py` checks that every model is frozen and forbids unknown keys; a new model needs no test of its own for an assignment or an unknown key, and a model that reads a tool's own output joins its exceptions with `extra="ignore"`. The `type[BaseModel]` rule above stays for wrong-typed fields.
- A tick records a question in the journal; the ask handler posts it on the next tick (record first, post once). A test that reads a posted question, or answers it, runs one more `world.tick.run()` after the tick that blocks the work item, as the fault-path tests do: a comment written before the question was posted ends no wait.
- The sides of one rule are rows of one parametrized test, not separate test functions; setup that several tests share is a fixture.
- Test data and test helpers obey the code already built, unless the test is about that rule: a work item text the readers accept, a branch that exists before it is read (`show_file` raises `GitError` for a missing ref), a commit range that holds only the commits the helper can parse, a file selection that expects the work item's `.costs.jsonl` sidecar beside its `.md` file. Before writing a helper, read the tests that pin the behaviour it calls.
- The standing leave to move a shared test helper: a helper, constant or fixture that a new test would copy from another story's test module, or that an earlier test module still holds as a copy of a shared one, may be moved to one shared place under `tests/` (a module at its root, or `tests/conftest.py` for a fixture), and the earlier tests that held it changed to use it from there, without asking, as long as every earlier test keeps its name and checks the same thing. The tester makes the move, never the coder, and its entry names each earlier test file it changed. Any other change to a test another story wrote still needs the human's leave.

## Docs
- `README.md` is for the newcomer: what it is, how to run it, where to look next. `docs/operator-guide.md` is for the operator: install, configure, the stops and what to do about each. `docs/project-guide/` is the project guide for agents (R17): the index `README.md` and one file per domain, which a story reads when it touches that domain. `docs/decisions.md` is the decision log. The documenter stage keeps these four true from each story's docs criterion; the coder does not write them. `docs/operator-playbook.md` is the human's playbook for running the factory without the human: no stage keeps it, and a story changes it only when its docs criterion names it.
- Docstrings: one per module (its purpose, a sentence) and one per public class and function in every package under `src/factory/`; none on private names or where the signature says it all. Comments say why, never what. `ruff`'s `D` rules (Google convention) enforce the presence; the reviewer judges the content.

## Checks
- `make check` must be green before any stage reports done. It runs `make lint` (ruff check and format check, including the docstring rules), `make types` (`mypy --strict` over `src` and `tests`), `make layers` (import-linter), `make sast` (semgrep with the rules in `security/semgrep`, and bandit over `src`), `make secrets` (detect-secrets against `.secrets.baseline`, over the files changed against `origin/main`, every tracked file on `main` itself), `make licenses` (pip-licenses against an allow list for the production dependencies) and `make test` (pytest on every core with pytest-xdist, `--dist worksteal` so an idle worker takes over waiting tests, branch coverage of `src/factory` at least 90 %, a JUnit report in `.reports/junit.xml`). Each target ends with the line `<target>: green (<seconds> s)`; `make check` ends with `check: green`. A test must pass when its module runs on a worker of its own, beside the other modules.
- `make lint` and `make test` run those two alone. `make duplicates` reports similar code (pylint's duplicate-code) and dead code (vulture) in `src/factory` against the accepted findings in `security/duplicates-baseline.txt`, as `duplicates: <n> new, <k> known, <g> gone`: a record after the coder, never a check; the reviewer reads its new findings. `make documents` runs the document check: a check of the docs stage, not of `make check`. `make mutants` runs mutmut and is never part of `make check`. No stage and no agent runs it: mutation testing runs only as sweeps outside the factory, which the human starts on a fresh copy (the human, 2026-10-19). Every run removes `mutants/` first, so nothing is kept between runs. It mutates the modules named by hand, as in `make mutants MODULES='factory.domain.disk factory.application'` (dotted modules or packages, each run by its pattern `<name>.*`), or, with `FEATURE=<feature id>`, the modules under `src/factory` that the feature's story commits on `origin/main` changed; `MODULES` wins when both are given. `MUTANTS_SECONDS` stops mutmut after that many seconds (no stop when unset), and `MUTANTS_CHILDREN` caps its workers. It ends with mutmut's own listing of the mutants it did not kill, and fails with `mutants: stopped after <n> s, ...` when the stop came first. mutmut leaves out the structural tests listed in `pyproject.toml`, which read the source it rewrites. The pipeline knows these six targets (`check`, `lint`, `test`, `secrets`, `duplicates`, `documents`).
- The records contract: `src/factory/contract/*.schema.json` are generated from the models `factory.domain.contract.CONTRACT` names. A change to one of those models, its docstrings included, regenerates them with `uv run python -m factory.entry.contract` in the same story; the coder writes them through that command and never by hand, and the reviewer checks the contract's version rule (`docs/decisions.md`).
- Run `make check` and every other make target in the foreground and read its output. Never start one in the background, and never wait for a process with `pgrep -f`: it matches its own command line, so the wait never ends and the stage runs until the command times out. `make check` takes more than two minutes: give the shell tool a timeout of 600000 ms for it, so that the tool does not move it to the background.
- The documenter runs `make check` only when it changed a file outside `README.md` and `docs/`: after changing only documents it ends without it, because the factory checks right after the docs stage: it runs `make check`, or reuses its passed result when nothing that `make check` reads has changed (`not_read` in `factory/pipeline.yml`), then `make secrets` over the changed files and `make documents`. Those are the gate.
- Run Python through `uv run`. All dependencies, runtime and development, are declared and pinned in `pyproject.toml`; the lockfile is `uv.lock`.

## The human's files
- `planning/` and `docs/runs/` belong to the human. No stage edits them; they are outside every write path.

## Not without asking (end the stage with `question`)
- New dependency, new top-level package, change to `factory/`, change to a test you did not write beyond the standing leave under *Tests*, a new entry in `.secrets.baseline` or a `pragma: allowlist secret`, a `nosemgrep` or `nosec` marker, a licence outside the allow list.
- The one exception, decided with the seed: `src/factory/adapters/process.py`, the one module that starts processes (R5), may carry `# noqa: S404` and `# nosec B404` on its `subprocess` import, `# noqa: S603` and `# nosec B603` on its one `Popen` call, and `# noqa: S606` and `# nosec B606` on its one `os.execvpe` call (F0019: the write guard's wrapper replaces itself with the runtime); and `src/factory/domain/confinement.py` may carry `# noqa: S108` and `# nosec B108` on the one line of `DEVICE_FOLDERS` that names `/dev/shm` (F0019: a device folder the kernel is told to allow, not a temporary file), with a comment that says why; and nothing else.
