# Installing and running an instance

A topic of the [operator guide](README.md).

## Install

Install v1.1 only on a repository v1 has not worked in, or whose v1 work items are archived or discarded: v1.1 starts fresh, and nothing detects a v1 work item.

Install the factory with `uv sync`, then check the installation with `make check`; it ends with the line `check: green`. `operator/vm/setup.sh` is the way to run an instance (see "The machine" in [machine.md](machine.md)): it makes the VM, installs the factory and the service, and the stage image carries the agent runtime and the pinned tools. Then set the instance's environment as described under "Configuration".

## Configuration

One factory instance runs one project and is told what it needs through environment variables. `factory.shared.domain.settings.read_settings` reads them and refuses a bad one with `SettingsInvalid`, whose message is `<variable>: <fault>`; it reports the first fault in this order: the repository, the instance, `FACTORY_CHECKOUT`, `FACTORY_STATE`, the image identity file, `FACTORY_WORKSPACE`'s faults (a relative path, a checkout or state directory inside it), then the variables below those in the table. `factory-run` calls it first; `factory-watch` reads the same environment.

**The stage environment.** Every stage runs its commands in throwaway Podman containers on a folder whose base is kept and reset before every stage. By default that folder is a ZFS dataset (`FACTORY_SNAPSHOTS=zfs`); with `FACTORY_SNAPSHOTS=copy` it is a plain directory whose base is a copy of it (see *Without ZFS*). Nothing else chooses between ways: the setting that once did is under "Replaced in v1.2" in [README.md](README.md).

An instance needs `FACTORY_WORKSPACE` and `FACTORY_STAGE_IMAGE`, and with `zfs` `FACTORY_DATASET`, with `copy` `FACTORY_SNAPSHOT_BASE`. `factory-run` refuses to build its boundaries when one is missing, before it builds anything, naming the first missing one in this order: with `zfs` the dataset, the workspace, the image; with `copy` the base, the workspace, the image (`<variable>: missing`). The container is the boundary. The agent's `HOME` is `/work/home` on the dataset. `read_settings` refuses a relative workspace, and a checkout or a state directory that is the workspace or lies inside it, with `FACTORY_CHECKOUT` (checked first) or `FACTORY_STATE` as the variable and `<path> lies inside FACTORY_WORKSPACE`: every rollback of the dataset would reset the factory's own checkout, and the agent's container would reach the health file and the runs. With the default checkout, `FACTORY_WORKSPACE=/work` is refused for that reason.

The VM the instance runs on, with the dataset and the stage image, is prepared by `operator/vm/setup.sh`, and the preflight checks them: see "The preflight's items" in [health.md](health.md).

A required variable that is missing, empty or only spaces is refused. The two commit-identity variables are decided one by one: a half that is unset or only spaces falls back to its own default, so the commits are `factory <factory@noreply.invalid>` unless you set them. No preflight item checks the identity.

The image identity is read from the file, stripped, so that a rebuild of the image with the same build argument cannot keep an old preflight stamp valid. `operator/vm/setup.sh` makes the file and you renew it after every build of the stage image (see "The stage image" in [machine.md](machine.md) and "The rebuild after a merge" in [machine.md](machine.md)). A file that does not exist, cannot be read or holds only spaces is refused with `FACTORY_IMAGE_ID_FILE` as the variable. The variable `FACTORY_IMAGE` is only a label of the build and is never read as the identity.

A blank value of the three optional variables above counts as unset. The token is read once, when the boundaries are built, from the file `FACTORY_TOKEN_FILE` names, stripped of surrounding whitespace. An unset variable, a file that does not exist or cannot be read, and a file that holds only spaces are each refused with `FACTORY_TOKEN_FILE` as the variable; the message names the path and never the token. The token reaches the hosting service (PyGithub) from the factory process, and git only through its credential helper, `/usr/local/bin/git-credential-factory`, which reads the same file (see "The hosting-service token" in [health.md](health.md)).

The repository's `owner/name`, which the hosting service needs, is taken from `FACTORY_REPOSITORY_URL`: `https://host/owner/name(.git)`, `ssh://git@host/owner/name(.git)` or `git@host:owner/name(.git)`. Any other URL is refused with `FACTORY_REPOSITORY_URL` as the variable. `factory-run` builds the boundaries from them when it starts.

The checkout and the state directory are settings: `FACTORY_CHECKOUT` and `FACTORY_STATE`. Unset, they keep `/work/checkout` and `/state`; the VM sets both under `/srv/factory/<instance>` (see "The machine" in [machine.md](machine.md)). `FACTORY_STATE_DIRECTORY` and any other variable the table does not name are ignored.

### A repository URL with a password is refused

A URL whose user information holds a colon, that is a user name followed by a password before the `@`, is refused, because git would keep the password in the shared checkout's `.git/config`, which the agent can read. Put the token in the token file instead. A user name alone is accepted: `ssh://git@github.com/owner/project.git`, `https://user@github.com/owner/project.git` and the form `git@github.com:owner/project.git`.

## When the process refuses to start

`factory-run` ends with status 2, never with a traceback, when the environment is invalid (any fault in the table above, including a missing or empty image identity file), when the token file cannot be read, and when the repository URL has no owner and no name. It writes one time-stamped line to the factory log and standard output, `settings invalid: <variable>: <fault>`, and a `preflight_failed` stop with scope `machine` to `health.json`, both in the directory `FACTORY_STATE` names, else in `/state`; a relative `FACTORY_STATE` is itself the fault reported, and its stop goes to `/state`, so the container's health check fails and the fault is visible without opening the log. The stop is added to the stops already in the file; an older `preflight_failed` stop is replaced and no other stop is dropped. When the state directory cannot be written (a `state` volume mounted read-only or with the wrong owner), `factory-run` still ends with status 2: the time-stamped line reaches standard output, two lines go to standard error, `factory-run: settings invalid: <variable>: <fault>` and `factory-run: cannot write the machine stop: <error type>: <message>`, and no stop is written. Check the `state` volume's owner and mode. Correct the variable or the file and start the instance again.

## The loop and its pauses

An instance repeats one iteration: it prepares the checkout, then makes one tick. The first iteration of a run happens at once, so a restart with the same instance name does not wait out a pause. Only a tick that handled an event other than `idle` counts as activity: a standing stop, a capped event and an error are idle, so the pause keeps growing while nothing changes. The first iteration follows the same rule: there is no pause after it when its tick handled an event other than `idle`, and 30 seconds when it was idle. One tick object serves the whole run, which keeps its error counts in memory from one iteration to the next; a restart starts them again.

After an iteration whose tick found activity the instance does not pause: the next iteration starts at once, because the next tick has work. After an idle iteration it pauses 30 seconds, and each further idle tick in a row doubles the pause (30, 60, 120 seconds) up to 120 seconds; the next activity ends the pauses again. An iteration whose preparation or tick fails counts as idle. The failure is one line in the factory log, `iteration failed: <exception type>: <message>`, and the loop goes on.

With `FACTORY_IDLE_SHUTDOWN_MINUTES` set, the loop also counts its idle ticks in a row (a tick that ran, ended at no stop and handled the event `idle`) and may power the machine off after them; the pauses above are unchanged. An iteration whose preparation failed ran no tick: it neither counts nor ends the stretch. See *The idle shutdown* under "The machine" in [machine.md](machine.md).

### The checkout is cloned when it is missing

The checkout lies where `FACTORY_CHECKOUT` names (`/srv/factory/<instance>/repo` on the VM). When that directory has no `.git`, the instance clones the repository into it. A checkout that has a `.git` is kept as it is: the factory does not check it, does not clone it again and removes no repository nested in the work tree. What an agent can reach is bounded by the container it runs in (see "What the container can and cannot see" in [machine.md](machine.md)), not by checks on the checkout.

A folder with files and no `.git` is still refused: git will not clone into a non-empty directory and the iteration fails. Delete the checkout directory and let the next iteration clone it again. The checkout is disposable (see "The stops of the tick" in [stops.md](stops.md)), so nothing is lost.

## The project's make targets

The factory runs a project's build through make and calls four targets: `check` (the full gate, which must be green before a stage hands forward), `lint` (run after the tester stage), `test` and `sync`. `sync` is the fourth: it brings a checkout's tools up to date after a checkout, `uv sync --frozen` in a Python project and the project's own command in another stack. The stage environment runs it before every agent run and before every check, and no stage lists it in `checks` or `reports`. A project must define them in the Makefile at the root of its checkout. Each is judged by its exit status alone, and a target that does not exist counts as a failed command. A target that runs past its time limit is killed and counts as failed for that reason; the factory reads only the exit status, the last line and the last 30 lines of the output.

The factory does not remove ignored paths (`.venv`, the caches). The checks run on a rolled-back copy of the dataset, and only the paths the role may write reach the checkout. Each target should build what it needs (kumpel-factory's and the template's `uv run` create `.venv` from `uv.lock`; the first check after a rebuild of the image downloads the packages once), and a target that relies on an ignored file another stage left fails.

A project whose `check` scans for secrets, with the template's `make secrets` or a scanner of its own, must leave out the factory's cost records (`*.costs.jsonl`, beside each work item), or the first agent run of every work item makes `check` red.

### Mutation testing by sweep

No stage and no agent runs `make mutants`. Mutation testing runs only as sweeps outside the factory, which the human starts on a fresh copy in a throwaway container, with `mutants/` made anew for every run (the human's decision of 2026-10-19). The `mutants` target stays for those sweeps. A sweep's command is

```
make mutants MODULES=factory.pipeline.application MUTANTS_SECONDS=7200 MUTANTS_CHILDREN=2
```

`MODULES` names the modules or packages, `MUTANTS_SECONDS` stops mutmut (no stop when unset) and `MUTANTS_CHILDREN` caps its workers, which matters in a container limited to fewer cores than the host reports. A coder's entry has no `mutants` line, and the acceptance's check 3, *Mutation testing*, says `By sweep, not run here.` The template's `CLAUDE.md` and `Makefile` say the same: `make mutants` is for a sweep by hand.

**How long it takes.** Every run starts with mutmut's stats, and they are the cost to plan for: 165 s on 20 cores (28 s listing the tests, 131 s of mutmut's clean test run, 5 s generating), and 4.5 to 19 minutes on two cores in the sweeps of 2026-10-19. On top of that each mutant costs 0.13 to 0.25 s on 20 cores. The recipe sets no stop unless `MUTANTS_SECONDS` is given. Every run removes `mutants/` first, so no run keeps the stats of an earlier one.

**A run that never gets past mutmut's stats.** Every run starts with mutmut's stats over the whole suite in one process. A `MUTANTS_SECONDS` below the stats checks no mutant, and the run then fails with `mutants: stopped after <n> s, so the mutants it did not reach are not checked`. A `MUTANTS_SECONDS` must cover the stats plus the mutants' time, for example:

```
make mutants MODULES=<module> MUTANTS_SECONDS=1500
```
