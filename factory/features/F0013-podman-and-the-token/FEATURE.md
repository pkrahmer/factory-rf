# Podman and the token

## Goal

v1.1 runs under rootless Podman as well as under Docker Desktop, and on neither can the agent read the hosting token. Podman, not Docker Desktop, is the runtime at the human's work, and the first start on the real machine (plan step 2, `planning/overnight/restructure-after-f0011.md`) runs under both, so this is plan step 1b, built by v1 right after F0012. It is drafted from a probe of v1.1's image under rootless Podman on 2026-10-17 (`planning/overnight/podman-probe-2026-10-17.md`), not from guesses. The probe found the image working under Podman, and five faults: the agent can read the token on both runtimes, because Compose ignores a file secret's owner and mode outside Swarm (a security fault of v1.1, fixed first, before any real run with a token); no restart after the Podman machine restarts; `podman-compose` cannot build the compose file on Windows; the disk record sees the machine's virtual disk; the image pins are placeholders (the human's, step 2). F0012's acceptance added its two proposed stories (F0012 decision 56). It is for the human, who starts v1.1 under Docker Desktop and Podman next, and for the team setup after it. Done when every story below is merged, `make check` is green, the token's folder and mount are in the image and the compose file, the preflight checks the folder, and the operator guide names the runtimes and says how to run under Podman.

## Scope

- The token (the probe's fault 1, the human's answer 1): the token file in a folder only the factory's user can enter, made in the image, mounted there by Compose in place of the compose secret, read from there through `FACTORY_TOKEN_FILE` (S0001); the preflight item `token-file` checks that folder instead of the file's own owner and mode (S0002); the operator guide says where the file lives on the host and that its host permissions still matter (S0001's docs criterion).
- F0012's two proposed stories, renumbered (the human's answer 2): the acceptance handlers' no-state refusals (S0003, was F0012-S0031) and the demo check's backlog path through `work_item_path` (S0004, was F0012-S0032).
- Podman's restart service, the Compose provider and the runtimes in the operator guide (faults 2, 3 and 4, the human's answers 3 to 5): one documentation-only story (S0005).
- The stale header comment of `image/entrypoint.sh` that F0012's acceptance found (its section 4), fixed by the next story that touches `image/`: S0001.

## Out of scope

- The image pins (the probe's fault 5): the human's, before the first start (plan step 2).
- A test of the restart after a Podman machine restart, and of the token's folder in a running container: by hand, at the first start (plan step 2), as the morning observations S0001 and S0005 write.
- `userns_mode: keep-id`, `:U` volume options and rootful Podman: not needed, since the probe found the image's owners and modes inside the container under rootless Podman as built.
- SELinux labels on a bind mount (`:z`) for a Linux host with SELinux enforcing, and a Mac: not probed; the first run on such a host says whether a story is needed.
- The health check under Podman: it runs and reports as under Docker (probe); neither runtime acts on an unhealthy container, and the factory builds no watchdog (F0010).
- `podman-compose` as a provider, and Podman without a Compose provider: the guide names docker-compose v2 only.
- The project commands that run as the factory's user and can read the token file: left for v2 (F0010, the human's decision of 2026-10-14).
- Per-story mutation testing and the time limit of `make mutants`: plan step 7a and F0012 decision 56.

Rejected: a `chown` or `chmod` of the file in the entrypoint (the entrypoint runs as `factory`, and a bind mount's owner and mode are the host's), Swarm mode. (S0001)
