# An approval's description is written before its push

## Assignment (as of log entry 1)

At the shakedown of 2026-10-18 (the night log's result section, finding 3) the board showed F0003's acceptance (demo #12) at `approval` about 25 seconds before its pull request's description held the report; at first the description was the report's head, its title and journal. The cause is the order in the code. `StageFinisher.finish` commits the result, pushes it (from then on the remote, the board and `factory-watch` show the work item at `approval`) and writes the stage label. The description is written only by the hand-over, which is another event: the next tick sees the work item at an approval with `handed_over` unset and runs `HandOverHandler` or `AcceptanceHandOver`, which writes the description, marks the pull request ready, posts the cost table and records `handed_over`. Between the two ticks lie the scheduler's pause (15 seconds after an active tick) and the next tick's fetch and evaluation. Stories have the same gap: their pull request shows, for the same time, the story's text as it was opened, without the reports and the commits (FEATURE decision 8). This story makes the finisher write the description of a move to an approval stage after the result commit and before its push, from the document and the commits it is about to push, the same text the hand-over writes. So a human who opens the pull request the moment the board shows `approval` reads the full description. The ready flag, the cost table and `handed_over` stay the hand-over's, on the next tick as today, and the hand-over writes the description again with the same text. A failing description write before the push does not stop the push: the factory logs it, and the hand-over writes the description on the next tick (FEATURE decision 7). The tester changes one test of an earlier story and adds one test to the module of another, by the human's leave (FEATURE decision 9).

## Interface

`src/factory/application/stage.py`, `StageFinisher`. Only the path of `finish` that ends in a result commit changes; `_stall_red` is not touched.

- When the stage of the move, `move.stage`, is an approval stage (`self._definition.stages[move.stage].approval`), the finisher writes the pull request's description after `git.commit` of the result commit and before `git.push`: `self._boundaries.hosting.set_description(started.pull_request.number, text)`. For every other move (a forward move, a rework, a question) it writes no description.
- `text` for a story is `hand_over_description(moved, commits)` (`factory.domain.hand_over`), with `moved` the document the result commit holds and `commits = self._boundaries.git.log("HEAD", since="origin/main")`, which after the push are the commits the hand-over reads from `origin/<branch>`. For an acceptance (`is_acceptance(started.work_item)`, `factory.domain.identifiers`) it is `acceptance_description(moved, role)` (`factory.domain.acceptance`), with `role` the role of the stage that ran, `self._definition.stages[started.stage].role`.
- A `HostingServiceError` from that `set_description` is caught: the finisher writes the line `pull request #<number>: description not written before the push: <error>` to `self._boundaries.log` (the `FactoryLog`) and goes on with the push and the label as today.
- Nothing else changes: the push, `PushFailed`, the label after the push, the `StageReport`, and the state (`handed_over` stays unset by the finisher). `HandOverHandler` and `AcceptanceHandOver` stay as they are: on the next tick they write the description again (the same text, since they read the same document and commits), mark the pull request ready, post the cost table and record `handed_over`.

The split of the work between `finish` and `_commit_and_push` (for example a private `_describe(started, moved)` called between the commit and the push) is the coder's; the order is not.

## Acceptance criteria

1. A stage that moves a work item to an approval stage writes the pull request's description before the push of its result commit: killed at that push, the remote still shows the stage that ran, and the description already holds the smoke tester's report and ends with the hand-over's closing text. Row `approval` of `test_the_description_is_written_before_the_result_push_only_for_a_move_to_an_approval`.
2. A stage that moves a work item anywhere else, or asks, writes no description: a rework from `smoke-test` to `doing`, a forward move from `review` to `docs` and a question at `smoke-test`, each killed at the result push, leave the description as it was before the tick. Rows `rework`, `forward` and `question` of the same test.
3. Right after the tick whose stage moved a story to its approval, before its hand-over, the remote shows the story at `approval` with `handed_over` unset, the pull request is still a draft, and its description is `hand_over_description` of the pushed document and the branch's commits. After the next tick (the hand-over) `handed_over` is `approval`, the pull request is ready, and the description is unchanged: `test_a_work_item_at_its_approval_shows_the_full_description_before_its_hand_over`.
4. An acceptance whose stage ends with `approval` has `acceptance_description` of the pushed report as its description right after the run, while its pull request is still a draft and `handed_over` is unset: `test_an_acceptance_that_ends_with_approval_has_its_report_in_the_description_at_once` in `tests/application/test_stage_run_acceptance.py`.
5. A failing description write before the push does not stop the push: the work item reaches `approval`, the description stays as it was, the factory log holds `pull request #<number>: description not written before the push`, and the next tick's hand-over writes the description: `test_a_failing_description_write_before_the_push_is_logged_and_the_hand_over_writes_it`.
6. What must still hold: a hand-over whose description fails three times is reported once after the error cap (`test_hand_over_that_fails_every_time_is_reported_once_after_the_error_cap`, with its failures injected after the smoke test's tick), and every other test of `tests/application/handlers/test_hand_over.py`, `tests/application/test_acceptance_hand_over.py`, `tests/application/test_stage_finish.py`, `tests/application/test_stage_run_acceptance.py` and `tests/test_stop_table.py` passes.
7. `make check` stays green.
8. docs: the project guide's *`StageFinisher.finish(aftermath)`* gets a step between the commit and the push of step 7: when the move's stage is an approval stage, `set_description` with `hand_over_description(moved, Git.log("HEAD", since="origin/main"))` for a story, or `acceptance_description(moved, role)` for an acceptance, the role of the stage that ran; a `HostingServiceError` there is logged (`pull request #<number>: description not written before the push: <error>`) and the push goes on. Its *The hand-over at the approval* says that the description is already in place when the hand-over runs, that the handler writes it again with the same text, and that the hand-over stays the place that marks the pull request ready, posts the cost table and records `handed_over`. The operator guide's *What a stage run shows* says, in its list, that a stage that moves the work item to an approval writes the pull request's description after the result commit and before its push, so the description is complete when the board first shows the approval, and that if that push fails the description may already show the reports while the work item stays at its stage. Its *The hand-over at the approval* says that the description is written by the stage that reaches the approval, before its push, and again, unchanged, by the hand-over on the next tick, which then marks the pull request ready and posts the cost table; the same holds for an acceptance. The decision log gets an entry, "An approval's description is written before the push that shows the approval", with the cause seen at the shakedown of 2026-10-18 (the board showed an acceptance at `approval` about 25 seconds before its description held the report, because the description came from the next tick's hand-over), that stories had the same gap, and the rejected alternatives with their reasons (FEATURE decision 7): the whole hand-over in the finisher; `handed_over` recorded in the result commit; the description written after the push in the same tick; and the board showing an approval only once it is handed over. No other document changes, no word that the document check refuses is used outside a `## Replaced from v1` section, and `python -m factory.entry.check_documents` still prints `documents ok`.
