# A command stopped at its time limit leaves no process running

## Goal

A fault F0024's acceptance found (`factory/features/F0024-mutation-testing-per-story/done/F0024-A0001-acceptance.md`, section 2 and decision 1 of its section 6). `MakeProjectCommands(...).run("mutants", time_limit=3 s)` returned `time_limit` after 3 s, and right after it `ps` showed `timeout 60 uv run mutmut run factory.entry.inputs.*`, `uv run mutmut run ...` and mutmut's Python still running, all in the process group of `timeout` (335851), writing `mutants/`. F0024's decision 4 says the opposite: "the factory waits until `timeout` ends it". The fault lies in the factory's kill, and the recipe's `timeout` is what triggers it. `run_process` starts every command in a session of its own and, at the time limit, kills the command's process group (`_kill_group` in `src/factory/adapters/process.py`, whose comment says "its group holds everything it started"). GNU `timeout` without `--foreground` moves itself and its command into a group of its own, and the `mutants` recipe runs `timeout $(MUTANTS_SECONDS) uv run mutmut run $$names 2>&1 | tee "$$temporary/run.txt"`. The KILL ends `make`, the recipe's `bash` and `tee`, not `timeout` and mutmut. The factory then waits only for `make` and for the end of its pipe, and mutmut writes into `tee`'s pipe, so the call returns at once. Decision 4's observation (a 12-second limit returned after the recipe's own 30-second stop) holds only for a command that writes into the factory's pipe itself. The drafting agent reproduced both on 2026-10-19 in a throwaway container of `factory-self-factory`, with `sleep` stand-ins under a `Makefile` with the recipe's shell settings and the real `MakeProjectCommands`. With `| tee`, the call returned after 3.0 s and left `timeout`, its `sh` and two `sleep`s running in `timeout`'s group, in `make`'s session (sid 9). Without `tee`, it returned after 30.0 s. With `timeout --foreground`, it returned after 3.0 s and left nothing. `uv run` kept its Python in the group and session of its caller. The fix is in the factory: whatever a descendant does with its process group, it stays in the command's session unless it calls `setsid`. With a prototype that kills the session's processes in rounds until none is left, the same `Makefile` returned after 3.1 s and left nothing. A grandchild in a group of its own was gone when `run_process` and `run_streaming` returned, at 10.1 s for a 10-second limit, and one that called `setsid` was not. This feature is for every stage that runs a project command and for the reviewers who read `mutants/` after a stopped report. On 2026-10-19 the human took the `mutants` report out of the coder's stage (`factory/pipeline.yml`), so today the fault matters for the acceptance's `make mutants` and for the report's return. When it is done, a project command stopped at its time limit leaves no process of its session running, and the factory goes on only after they are gone. Done when every story below is merged and `make check` is green. The real check with mutmut is the human's change 2.

## Decisions taken for the human

1. **The fault lies in the factory's kill; the recipe's `timeout` triggers it** (from the code and the drafting agent's container runs of 2026-10-19). `_kill_group` kills one process group and relies on the comment "its group holds everything it started", which any descendant breaks with `setpgid`. `run_process` then waits for its child and its pipe, not for what the child started. `timeout` without `--foreground` calls `setpgid(0, 0)`, so it is the recipe that shows the fault, and any project's recipe with a `timeout`, a job-control shell or a tool that groups its workers would show it too. So the fix is in `factory.adapters.process`, for every command. (S0001)
2. **The factory, not the recipe.** `timeout --foreground` in the `Makefile` alone makes this one recipe's mutmut die with `make`'s group (seen: 3.0 s, nothing left). But it mends one recipe of one project, and with `--foreground` `timeout`'s own stop at `MUTANTS_SECONDS` ends only mutmut's first process, not what it started (GNU coreutils: "children of COMMAND will not be timed out"). That depends on how mutmut ends its workers, which is for the talk with the human (decision 12). Without `--foreground`, `timeout`'s own stop kills its whole group, which is what the recipe wants. So the recipe stays as it is, and S0001 makes the factory's kill reach every group of the session. (S0001)
3. **The session, not a walk of parent ids, a cgroup or a subreaper.** A session holds every descendant that has not called `setsid`, also after its parent died and it was handed to PID 1; a walk of parent ids loses those at the first kill. A cgroup per command needs a delegated cgroup that the factory's user does not have under rootless Podman, which the factory must run under. `PR_SET_CHILD_SUBREAPER` would make the factory reap every orphan of every run, the job `init: true` gives the container's init (decision log, 2026-10-18). The kernel's table `/proc/<pid>/stat` gives the session of every process, a zombie included, with no new dependency (no `psutil`). (S0001)
4. **The group kill stays first, unchanged, and another user's process is not waited for.** Under `sudo` the group's leader is root's `sudo`, the factory's kill raises `PermissionError` there today, and the agent's own `timeout --signal=KILL` ends the call (decision log, 2026-10-17; `SUDO_GRACE`). The sudoers file keeps the agent in the factory's session (`!use_pty`), so the agent's processes are in the session; a kill of one gives `PermissionError`, and the rounds leave it out (`refused`). The tests run as one user, so this side is a row of `left_to_kill`'s test (criterion 3), and the runs under `sudo` are pinned by their own tests, unchanged (criterion 7). (S0001)
5. **The rounds end when nothing is left, with no time limit of their own.** Each round reads the table, kills what is left and waits 0.05 s. A process forked between the read and the kill is in the session and found by the next round, and a killed process forks no more, so the rounds end. A zombie counts as gone: it has ended, and the container's init reaps it. A process that does not end after SIGKILL (uninterruptible in the kernel) would hold `communicate()` already today, so a limit of the rounds' own would add a rule that no test can reach and change nothing. A process that called `setsid` is in another session and stays: a row of criterion 4 pins that edge, so that a later change of it is seen. (S0001)
6. **One kill for every caller.** `run_process` and `run_streaming` share it at the time limit, at a stop and at an error of the callback: git, make, both runtimes. A run without `FACTORY_AGENT_USER` (the tests, an operator's run without `sudo`) gains it; a run under `sudo` is unchanged (decision 4). The `ProcessResult` of a killed command is unchanged. (S0001)
7. **The pure part in the domain.** Reading one line of `/proc/<pid>/stat` (the name in parentheses may hold spaces and `)`, so the fields are read after the last `)`) and choosing what is left to kill are rules on data, so they are `factory.domain.sessions`, tested as rows; the adapter reads the folders and sends the signals. It is the same split as `parse_results` for mutmut's lines (F0024 decision 8). (S0001)
8. **The tests wait for the kill with room, and read the end at once.** A child must start its grandchild and write the pid file before the kill, so the tests take `ROOMY_LIMIT` and `ROOMY_BOUND_SECONDS` from F0029-S0002; hence F0030 comes after it. They read the grandchild's end with `is_gone(pid, within=0)`: the rule is that it is gone when the call returns, and the 5 s of `GONE_WITHIN_SECONDS` would let a kill that does not wait pass. The grandchild writes to `/dev/null`, as mutmut writes into `tee`'s pipe; a grandchild on the child's pipe would hold `run_process` until it ends and hide the fault behind the elapsed time. (S0001)
9. **No leave to change an earlier test.** S0001 adds new modules and changes no test another story wrote; F0029-S0002's changes to `tests/adapters/test_process.py`, `tests/adapters/test_process_streaming.py` and `tests/adapters/test_make_commands.py` do not meet its own. `test_grandchild_is_killed_with_the_child_at_the_time_limit` stays as it is; the row `group` of criterion 4 checks the same with `is_gone(pid, within=0)`. (S0001)
10. **One story.** The domain module is about thirty lines and the adapter's change about thirty more; a domain story alone would leave nothing running for a user. The coder's part and the tester's part each fit the 40-minute `time_limit`. (Feature)
11. **The number and the name.** F0030 is the first number above every folder in `factory/features/` (F0018 to F0026) and `planning/overnight/stories/` (F0001 to F0029). The folder name says what the feature makes true. (Feature)

Decisions 12 to 15 depend on how mutmut 3.8 runs and stops, which the human will discuss in detail. Each is open, with a recommended answer that this feature already follows, so none blocks S0001.

12. **Open, for the talk on mutmut: `timeout --foreground` in the recipe, for the acceptance's `make mutants`.** The acceptance reviewer runs `make mutants` in its own shell tool, as `agent`; the factory's kill does not reach that (decision 4). If the shell tool's limit or the run's own kill ends `make`'s group before the recipe's 540 s stop, mutmut goes on in `timeout`'s group, and a second `make mutants` of the same run would meet it in `mutants/`. `--foreground` would keep mutmut in `make`'s group, but `timeout`'s own stop would then end only mutmut's first process. Options: keep the recipe (recommended: the recipe stops itself at 540 s, inside the shell tool's 10 minutes, and the acceptance passes the shell tool 600000 ms, as `CLAUDE.md` says for every make target); `--foreground` plus `--kill-after`, once the talk has shown that mutmut ends its workers when it is stopped; or a recipe step that kills its own `timeout` group on `EXIT`, which helps only when `bash` gets to run its trap.

13. **Open, for the talk on mutmut: a TERM before the KILL.** Seen in the drafting agent's container: `bash` runs its `EXIT` trap on a TERM. A TERM to the session, a grace, then the KILL would let the recipe remove its temporary folder and make `mutants/` group-writable again (F0024 decision 13). But a TERM reaches mutmut and its tests too, and what mutmut writes into `mutants/` when it is stopped mid-run is for the talk. Options: KILL only, as today (recommended now: the trap's repair is documented, and a TERM changes every command's end, the runtimes' included); a TERM with a grace for project commands only, after the talk.

14. **Open, for the talk on mutmut: does mutmut, or a test it runs, leave the session?** mutmut 3.8 forks a worker per mutant; the drafting agent could not run mutmut (the image has none) and saw only that `uv run` keeps its Python in the session. A worker that calls `setsid` would escape S0001's kill as a `setsid` grandchild does. Recommended: the human's change 2 reads the `SID` column of one real stopped run, and only a process found outside the session gets a story.

15. **Open, for the talk on mutmut: the order with F0024-S0005 and the report's return.** F0024-S0005 would document the fault ("goes on until its own stop"). Recommended: F0030 first, and the human's change 1 drops that part of S0005, so the documents never describe a fault that is about to go. The `mutants` report's return to the coder's stage needs nothing more from this feature; whether it returns is for the talk.
