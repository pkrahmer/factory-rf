# The first start's findings

## Goal

v1.1 started for the first time on 2026-10-17, as instance `shakedown` under Docker Desktop and `shakedown-podman` under rootless Podman 5.8.3, both on the todo demo's empty project (plan step 2, `planning/overnight/restructure-after-f0011.md`; the results in `planning/overnight/first-start-checklist.md`, "Results"). Both became healthy, and most of the operator guide's observations held, but the start found four faults, a fifth was found while this feature was drafted, and a sixth route at the pre-check. The agent cannot use git in the shared checkout (`detected dubious ownership`). The agent can write the checkout's git hooks, which the factory's git runs as the user who can read the hosting token. Every new instance needs an interactive `claude` login as `agent`. The operator guide is wrong or silent in three places. The agent can write the checkout's whole `.git`, its configuration included, so a `core.fsmonitor` line it writes makes the factory's own git run a command. And a git repository the agent makes inside the work tree, once the factory commits it as a gitlink, makes the factory's `git status` start a child git that runs that repository's `core.fsmonitor` (the pre-check, decision 30). The human added one more item on the same day, for the status map, a viewer that reads GitHub only: a journal record does not say when, in which stage or from which run it was written, and a cost record does not say which instance ran it. This feature fixes them, built by v1 before the shakedown run (plan step 4), which needs agents that can read a diff, a factory whose git cannot be made to run an agent's code, and instances that start with no login. It is for the human, who runs the shakedown next, and for every operator after: credentials are injected from outside, never typed into an instance, and stand on no command line. Done when every story below is merged, `make check` is green, the factory's git runs no hooks and no `core.fsmonitor`, the factory alone writes the checkout's `.git` and checks it around every agent run, no git repository stays inside the work tree after an agent run, the image trusts the checkout for the agent's git, the agent runs get their login token from a mounted file that the agent's own shell reads, the operator guide says what the first start saw, and every new journal record carries `at` and `stage` (and `run` when it came from a run) and every new cost record `instance`.

## Out of scope

- An API key (`ANTHROPIC_API_KEY`) injected the same way: it would fit the mechanism (one more file and one more name in the runtime), but it is left out. The factory runs agents under the operator's own subscription login (R12), an API key bills by use instead, and Claude Code prefers an API key it finds over the subscription, so a stray key file would change who pays without a word. Nothing in v1.1 needs it now; a team setup that wants it gets its own story (decision 15).
- The work tree's own `.gitattributes`, `.gitignore` and `.gitmodules`: they stay writable by the agent, like the rest of the work tree. They name no command git runs without a driver or command defined in the configuration, which only the factory writes now (S0006; decision 17 is superseded by decision 19).
- An agent process that outlives its run and writes after the check: the time limit ends the run's processes, and the guide's time-limit observation checks that none is left (no `claude` process of `agent` after the limit). The seal's guarantee holds from one check to the next agent run (decision 21).

- A real agent run end to end and a `time_limit` under `sudo`: the tiny story of plan step 2's item 5, run after F0014 at the start of step 4.
- A real `git status` as `agent`, a real probe run under the token, and the token's survival of a new instance: observed by hand at step 4, as the docs criteria of S0002 and S0004 write the observations.
- The project commands, which run as the factory's user and can read the hosting token: left for v2 (F0010, the human's decision of 2026-10-14).
- A preflight item of its own for the login file: the probe makes the call that needs the token and names the file when it fails (decision 13).
- The hosting token: unchanged (the human's answer 3, "the hosting token as today").
- The status map itself, markers in a work item's body and any change to the pull request (the human's word on item 6: "No markers in the body, no change to the pull request"). A migration of the records written before S0007 and S0008: they stay valid without the new fields (decision 25).

20. How, taken by the session for the human, to confirm (S0006):
    - `core.sharedRepository` becomes `0640`, git's documented setting for a repository the group can read and not write. It overrides the umask for what git creates in `.git`: folders become `750` (`2750` under the setgid `/work`) and files `640`. Git writes the work tree under the umask alone, so the entrypoint's `umask 002` still makes it group-writable, and `group` never served the work tree.
    - Git leaves some files outside that setting (to this session's reading, `FETCH_HEAD` and `COMMIT_EDITMSG`, written under the umask; not checked with a running git, because this session ran none), so `Git.seal()` takes the group's and others' write bits from `.git` and every entry in it, and the guarantee does not rest on git's internals.
    - The agent can still rename `.git` itself, because the work tree's root is group-writable, and put a folder in its place. That folder is its own, or one of the factory's work-tree folders, which are group-writable and which the agent cannot `chmod`. `Git.check_seal()` refuses a `.git` that is a symbolic link, is not a directory, belongs to another user or is open to the group's or others' writes. Such a folder is never repaired where an agent may have run since the last check, since a repair would make an agent's folder the factory's repository.
    - Git's own `dubious ownership` refusal of an agent-owned `.git` stays as a backstop: the factory's git has no `safe.directory`.
    - Rejected:
      - a sticky bit on `/work/checkout`, which would also stop the agent from removing, renaming or replacing by rename any of the factory's files at the root (`uv.lock`, `.venv`), against "the work tree stays group-writable"
      - a git folder outside the work tree under `GIT_DIR` in a folder only the factory writes: the clone, a gitfile for the agent's git, every existing checkout, a larger change than one story
      - a volume mounted at `.git`: mounts nested in another, and a clone into a non-empty folder
      - `umask 022` for the factory's git, which would close the work tree too
      - a check before every git command: only the folder's root can change, and only while an agent runs
21. Where the seal runs, taken by the session for the human, to confirm (S0006):
    - `CheckoutPreparer.prepare`, at the start of every iteration and before the tick's first git command, checks an existing checkout. If the check fails, it removes the checkout and clones it again, with the log line `cloning the checkout again: ...`; then it seals.
    - `run_sealed` seals before every agent run (the stage's and the probe's) and checks after it, in a `finally` (S0009 since decision 30).
    - The dispatcher lets `RepositoryUnsealed` pass uncounted, so no other handler of the tick runs git in that checkout. The scheduler logs the failed iteration, and the next iteration clones afresh.
    - The removal is the repair the human asked for: it repairs every instance cloned before S0006 (its `.git` is `2775`), and a crash mid-run cannot leave an agent's `.git` in place.
    - It narrows the decision log's "A checkout whose clone was killed half-way is not recognised": the factory removes a checkout whose `.git` fails the check (the checkout is disposable, R18), and still refuses a folder without `.git`, unchanged (its pinned test stays).
    - Rejected:

      - repairing the root of an existing checkout: a checkout from an earlier image cannot be told from a swap after a crash
    - A seal before a run may repair the root, because no agent has run since the last check.
