# Nothing a run leaves behind reaches the checks

## Goal

The security review of 2026-10-19 (`planning/overnight/security-review-2026-10-19.md`) found, from reading only, two ways an agent run can reach past its own stage. Both are confirmed here (decision 1). First, the git-ignored state of the checkout is never removed. That covers `.venv/`, `__pycache__/` and `*.pyc`, the tool caches (`.mypy_cache/`, `.ruff_cache/`, `.import_linter_cache/`), `mutants/` and `.reports/`, and whatever a nested `.gitignore` an agent adds hides. The undo does not see that state, the result commit does not hold it and the restore's `git clean -f -d` keeps it. So it stays across stages and stories and never shows in a pull request. Every later `make check` runs in that `.venv`, loads what its `site-packages` hold, loads a `.pyc` whose header matches its source, and reads those caches. Second, nothing ends what the agent's user still runs after a run. A process that left the run's process group (a new session) outlives both a run that ends normally and the time limit's kill. It keeps its write rules and the network, and it can write its stage's write paths, the tool paths and `~/.claude` during later stages, their undo and their checks. This feature closes both routes into the checks. After every agent call the runtime ends every process of the agent's user, through a small program that runs as that user. After every agent run, and at the restore at the start of every tick, the factory removes every git-ignored path of the checkout. So what a stage's checks run on is what git shows, plus what the checks build themselves. A project's own `uv run` rebuilds `.venv` from `uv.lock`. No ignored folder is kept: mutation testing runs only as sweeps outside the factory (decision 3, answer B). It is for the operator and the human, who read a green check as a statement about the code in the pull request. Done when every story below is merged and `make check` is green. The real check is the human's change 4, in the container, after the feature.

## Out of scope

- The project commands running as the factory's user, with the hosting token readable (the review's first row and story 1; `docs/decisions.md`, "The project commands run as the factory's user and are left for v2"). This feature keeps what an agent left out of the checks. What an agent writes into the code the checks run, in its write paths, stays visible in the diff and is that row's concern.
- Network egress from a run (the review's story 3), the agent's own files in `~/.claude` and a nested `CLAUDE.md` (story 4), opencode's `~/.cache/opencode`, `/dev/shm` between runs, and `.reports/*`.
- The agent's home: `~/.cache/*` (the agent's uv, pip and pre-commit caches) is a tool path and stays across runs. It reaches only later agent runs, never the factory's checks: the checks run as `factory`, whose uv cache lies in `/home/factory`, which the agent cannot write (decision 1). Closing it belongs to story 4's line.
- Processes of the factory's own user that a project command leaves (part of the first row).
- Verifying the content of `.venv` against `uv.lock`: uv checks package metadata, not files (decision 2).
- A folder an agent makes that the factory cannot empty: it stops the repository with `checkout_restore_failed`, as an untracked one in a write path does today (decision 11).
- Every paid call: no story and no smoke test makes one.

## Decisions taken for the human

1. **The review's claims, verified before drafting.** Both stories the brief names stand, and none is dropped.
   - Story 2, ignored state, confirmed by reading and by a test of the factory's cleanup. `GitCli.reset_to` runs `git clean --quiet --force -d`, without `-x` (`src/factory/adapters/git_cli.py`). The tick's restore calls it (`Tick._restore_checkout`). The undo's candidates come from `changed_paths`, whose untracked list is `git ls-files --others --exclude-standard`, so it never sees an ignored path. The result commit stages with `git add --all`, which leaves ignored paths out (`tests/application/test_stage_run.py` pins that a check's `ignored/` file is not committed). The opening resets the branch to the remote's. Nothing else removes them. The prototype ran on 2026-10-19 in a throwaway container of `factory-self-factory` (git 2.39.5), with stand-in files and factory-rf's `.gitignore`. It placed stand-ins in `.venv/lib/python3.12/site-packages/`, `src/pkg/__pycache__/`, `.mypy_cache/`, `.ruff_cache/`, `.import_linter_cache/`, `mutants/` and `.reports/`. It added a nested `tests/hidden/.gitignore` holding `*`, with a `tests/hidden/conftest.py` beside it, and a visible nested `src/.gitignore` that hides `src/secret.py`. `git status` (what the undo and the commit see) showed only `src/.gitignore` and a new `src/pkg/new.py`, and `git clean -n -f -d` would have removed only those two. `git clean -f -d -X` removed all nine ignored entries, `tests/hidden/` with its `.gitignore` included. It kept the tracked files, the new visible file and the visible nested `.gitignore`. The factory's own `run_sealed` of today's image, with the fake runtime writing `.venv/lib/standin.pth`, a `.pyc` under `src/__pycache__/` and the hidden `tests/hidden/`, left every one of them in the checkout (S0003's second smoke test, run before the change). Not tested, but taken from the tools' documented behaviour, never from an exploit: `make check` runs everything through `uv run` in the checkout's `.venv` (the `Makefile`). Python runs the `import` lines of every `.pth` file in `site-packages` at start-up. A `.pyc` whose header holds its source's modification time and size is loaded without reading the source (the default invalidation, PEP 552). pytest collects every `conftest.py` below `testpaths = ["tests"]`. mypy, ruff and import-linter trust their caches by design. So a hidden file can make a later check pass. Who can write what: every role writes the tool paths (`.venv/*`, the caches, `.pytest_cache/*`, `.reports/*`); `mutants/*` is no tool path any more (`factory/pipeline.yml`), so the kernel refuses an agent's write there. The coder writes `src/**/__pycache__`, and the tester writes `tests/**`, a hidden `conftest.py` included. The review's goals b and e hold. Goals c and d hold only through the first row (Out of scope).
   - Story 5, a leftover process, confirmed by reading and in a container. After a call, both runtimes' `_call` remove only the run's temporary folder. `run_process` kills the call's process group only at its time limit, and under `sudo` the agent's `timeout --signal=KILL` kills its own group at the limit. Nothing ends a process that left the group. In a throwaway container (`--init`, `--network none`), a run as `agent` that started a stand-in `setsid sleep 300` and ended at once left that `sleep` running with parent 1. A run under `timeout --signal=KILL 2s` ended with status 137, and its plain `sleep` died, but the `setsid` one lived on. Such a process keeps its Landlock rules (inherited, by design) and the network (Landlock restricts writes only). So it can write its own stage's write paths, the tool paths and `~/.claude` while later stages run, after their undo, and while their checks run. It can also swap `.git` after the seal's check, the window F0014 decision 21 left open. The review's goal b holds, and e through the first story.
2. **Ignored state is removed, not verified** (open, the human's: answer A recommended). A: remove every ignored path after every agent run and at the restore, and let the project's commands build what they need (`uv run` creates and syncs `.venv` from `uv.lock`; mypy and ruff rebuild their caches). B: keep `.venv` and check it against `uv.lock` (`uv sync --check`). uv compares the installed packages' metadata, not their files, so a dropped `.pth` or a changed module passes the check. That is no verification. C: the factory's checks use an environment of their own outside the checkout (`UV_PROJECT_ENVIRONMENT`). That is a uv-specific rule the engine would have to learn (R8, R11), and it leaves the other caches. A is generic (git's ignore rules), and it is the only one that leaves the checks nothing but what git shows. Recommended: A. (S0003)

4. **What the removal costs** (open, the human's: accept, recommended). Every stage's agent run starts without a `.venv`, because the restore removed it. Its first `uv run` builds one, as `agent`, from the agent's warm uv cache. Every stage's checks rebuild it again, as `factory`, from the factory's cache. That is two builds per stage with an agent and checks, one per stage without checks. Not measured: the throwaway containers have no network, and an offline build needs a warm cache they lack. The host's Windows `.venv` of factory-rf is 428 MB in 7,610 files, a rough upper bound. Copy mode (`UV_LINK_MODE=copy`, the image's) from a warm cache is a matter of seconds, against a `make check` of about 46 s on average (F0023's measurement). The factory's cache (`/home/factory/.cache/uv`) lies in the container's layer, so after each rebuild of `self` the first check downloads every package once. Moving it to `/state` (`UV_CACHE_DIR`) would keep it, at a cost in the state volume. Not done now. Recommended: accept, and read the cost at the human's change 4, step 4.
5. **The removal runs after every agent run and at every restore.** In `run_sealed`, after `check_seal()` and `remove_nested_repositories()`, and only when the run returned. So it comes before the undo and before the same stage's checks: a file the coder hides is gone before the coder's own `check`, not one stage later. It also covers the preflight's probe run. A run that raised leaves the removal to the next tick's restore. A `GitError` there would otherwise replace the run's own error. In the tick's restore, after `reset_to("HEAD")` and before the switch to `main`, so that a branch's own nested `.gitignore` still applies (after the switch, the files it hid would be untracked and not ignored, and `reset_to` has already run). That covers a crashed stage, whose undo never ran, and the preflight's probe of `main`. The restore logs no line for it: it would name `.venv` on every tick. Recommended as built. (S0003)
6. **`git clean -ffdX` does the removal.** `-X` removes only what the ignore rules match (`.gitignore` at any depth and `.git/info/exclude`), `-d` takes folders whole, and the second `-f` also removes an ignored folder that holds a repository. A symbolic link is removed as a link: git never follows it, and a link named like an ignored folder (`.mypy_cache -> /etc`) is not matched by a folder rule (`.mypy_cache/`), so the undo treats it as an untracked file outside the write paths (prototype). A path git cannot remove (a folder the agent closed, mode `0555`) makes `git clean` exit 1 (prototype: `failed to remove ... Permission denied`), and the wrapper raises `GitError`. No git process reads a nested repository's configuration for this: `git clean` reads only the ignore rules. A nested repository is in any case removed first by `remove_nested_repositories`. Chosen over a listing and Python's `shutil` (a second removal with its own rules for links and permissions). (S0003)
7. **An agent can un-ignore a path inside its write paths, and that is accepted.** A nested `.gitignore` with `!__pycache__/` in `src/` makes a `.pyc` there untracked and not ignored. It then stays, is committed with the result and shows in the pull request's diff, where the reviewer and the human see it. The undo removes it when it lies outside the stage's write paths. Inside the tool paths no `.gitignore` takes effect, since git does not read the rules of an ignored folder. The protected root `.gitignore` and `.git/info/exclude` cannot be written by an agent (the kernel's rules and the seal). Nothing is hidden this way, so no rule is added. (S0003)
8. **The kill ends every process of the agent's user** (open, the human's: answer A recommended). A: the program runs as `agent` and sends `SIGKILL` to every process it may signal (`kill(-1)`), which is exactly the agent's own processes: a new session, a `nohup`, a double fork. Then it waits until the process table holds none but itself, at most 50 rounds of 0.1 s, signalling again each round so that a fork between two rounds is caught too. B: end only the call's process group or session. It misses the very processes the review names, which leave both. C: a cgroup per run. It needs privileges or a container-runtime feature that rootless Podman does not give the factory's user. Under A, the agent's user must serve agent runs only. It does: one instance per container, one tick at a time, and `factory` becomes `agent` only for agent runs, their temporary folder's removal and this program. Recommended: A. (S0001, S0002)
9. **The program is a module of the factory, run as the agent through the one `sudo` rule.** `sudo -n -u agent -- /opt/factory/.venv/bin/python -I -m factory.entry.leftovers --user agent`, started from `/`. `-I` and the folder `/` keep the checkout, and anything an agent wrote, off its import path. In the image, `sudo -n -u agent -- /opt/factory/.venv/bin/python -I -c 'import factory.entry.confine'` from `/` imported the image's package (prototype). It needs no console script in `pyproject.toml` (no change of the human's) and no new `sudo` rule. It waits by reading the process table through F0030-S0001's reader (`/proc/<pid>/stat`, and as the user the owner of the folder `/proc/<pid>`, not of a file in it: a process that is not dumpable keeps its folder's owner but gets root-owned files; the human, 2026-10-20), never by `kill -0 -1`: in the prototype, `kill -0 -1` as `agent` returned 0 although no process of `agent` was left, because Linux counts a target it may not signal as found. A stand-in of the program ended six stand-in `sleep`s in its first round, in 0.3 ms, left the factory's processes alone, and refused when run as `factory` with `--user agent`. Zombies and dead entries do not count: a zombie runs nothing, and the runtime's init reaps it (`init: true`). The program's two calls to the operating system, `own_identity` and `signal_every_other`, live in `factory.adapters.process` beside the reader, and there is no module `factory.adapters.own_processes` (the human, 2026-10-20). (S0001)
10. **Three guards keep the program from ending the wrong user's processes.** The program refuses to run as root (`kill(-1)` as root would end the whole container) and refuses unless it runs as the user `--user` names. So a stand-in `sudo` in a test, which does not switch users, makes it refuse before its first signal. The runtime starts it only when it was built with a command (`build_boundaries` does, a runtime built by a test does not), only for a request with an operating-system user, and never when that user is the factory process's own: in an agent's `make test` that user is `agent`, and the run would end itself. The human's change 1 states the rule for tests. `signal_every_other` is called by no test and no smoke test. 11. **A failure fails closed** (open, the human's: answer A recommended). A: when the program exits non-zero or does not end within 30 s after a call that itself ended without an error, the run raises `AgentRuntimeError` (`cannot end the agent's processes: <its line>`). The stage then ends with a counted error and its claim held, and the probe item fails (`preflight_failed`). B: ignore its status, as the removal of the temporary folder does. Then a process that survived 50 kills, which only a process stuck in the kernel does, writes on during the undo and the checks. When the call itself raised, or `sudo` refused it, that error stands, and the program's result is not read. Likewise, a folder the factory cannot empty after a run raises `GitError` from `run_sealed`. At the restore it raises the existing stop `checkout_restore_failed`, as an agent-made folder in a write path does today. Recommended: A. (S0002, S0003)

13. **`kept_ignored` keeps only a folder that git lists whole** (withdrawn with S0004, decision 3 answered B; kept as the record, and wrong for git 2.39.5 by the pre-check of round 1). A pattern is `<folder>/*` in the checkout (no `~/`, no wildcard before `/*`, no `.` or `..` segment), the tool paths' first form. The removal lists the ignored entries (`git ls-files --others --ignored --exclude-standard --directory`), drops each entry that is a kept folder or lies beneath one, and passes the rest to `git clean -ffdX -- <entries>`. An exclude pathspec does not work: `git clean -X -- . ':(exclude)mutants'` still removed `mutants/` (prototype). The entries go to git as literal pathspecs (`--literal-pathspecs`): in the prototype, the plain pathspec `[a].log` made `git clean -n -ffdX` list every ignored entry, `.venv/` and `mutants/` included, and the literal one listed only the file `[a].log`. A kept folder inside a larger ignored entry is removed with that entry, because keeping the larger one would keep more than the project named. The operator guide says to name the folder that `.gitignore` ignores. The preflight's probe run removes every ignored path: the preflight knows no pipeline definition. It runs once per image build, so `mutants/` is lost once per rebuild of `self`. (S0004)
