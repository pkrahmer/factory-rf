# opencode starts in a fresh home, and no test races its time limit

## Goal

Two faults found on 2026-10-19 (the night log, `docs/runs/2026-10-12-overnight/night-log.md`, the rows of 14:19 and 14:42). (1) Every new container of an instance on opencode stops at its first preflight. The probe ends `died` because opencode 1.19.3 makes `~/.config/opencode` on its first run, and the kernel's write guard (F0019) refuses that write: `RUNTIME_FOLDERS` allows `.local/share/opencode`, `.local/state/opencode` and `.cache/opencode` and nothing under `.config`, on purpose. The agent's home outside `.claude` is not a volume, so every recreated container starts with a fresh home and stops again. The drafting agent reproduced it in a throwaway container of `factory-self-factory` (offline, a stand-in key) on 2026-10-19. Under `factory-confine` with the runtime's three folders, `opencode run` in a fresh home ends at once with exit 1 and `EACCES: permission denied, mkdir '/home/agent/.config'`. When the folder exists, empty and owned by `factory` with mode `0755`, the same run gets past configuration and reaches the provider, as an unconfined run does; `opencode debug config` gives exit 1 and exit 0 for the two cases. An unconfined first run writes `opencode.jsonc` and `.gitignore` into the folder: a configuration file that every later run reads. (2) One row, `tests/adapters/test_claude_runtime_confinement.py::test_the_temporary_folder_is_empty_at_each_call_and_gone_after_the_run[time-limit]`, failed under a loaded `make check` with `assert 0 == 1` at `len(calls) == len(steps)` and passes alone. Its 3-second limit (`SHORT_LIMIT`) killed the probe before it wrote its call record. The probe starts through the real `factory-confine` (a Python entry point, about 0.2 s on an idle core) and then a Python stand-in. Seventeen more tests in eleven modules, that one's own among them, give a child that must do something before the limit (write a record or a pid file, print a line, finish a first call) a limit of 1 to 5 seconds. This feature is for the operator who runs an instance on opencode, and for every stage that runs `make check`. When it is done, the image makes opencode's configuration folder, read-only to the agent, so the first probe in a fresh home passes and no run can write what the next run reads. Every test whose child must act before its limit gives it ten seconds (`ROOMY_LIMIT` in `tests/time_limits.py`) and an elapsed bound with room above, so a loaded machine no longer fails them. Done when every story below is merged and `make check` is green. The real check of S0001 is the human's change 1: a recreated opencode instance passes its first probe.

## Decisions taken for the human

1. **opencode's configuration folder is made by the image, not allowed to the run** (the question of the night log, answered by reading `opencode_runtime.py`, the image and opencode's own first run). `RUNTIME_FOLDERS` leaves `.config` out on purpose: its comment says *its own configuration folder stays outside the rules, so an agent cannot rewrite what the next run is told*, and the operator guide and the project guide (`agents.md`, *opencode's folders*) say the same. An unconfined first run writes `opencode.jsonc` there, and opencode reads that global configuration on every later run, beside the factory's own `OPENCODE_CONFIG`. A run allowed to write the folder could add agents, plugins, instructions or permissions for the runs after it. So `.config/opencode` in `RUNTIME_FOLDERS` is rejected. The folder only has to exist: in the drafting agent's experiment an empty folder that the agent cannot write let `opencode run` reach the provider and `opencode debug config` exit 0. opencode ignores the failed write of its default `opencode.jsonc`, and it dies only on the failed `mkdir`. (S0001)
2. **The image, not the entrypoint.** The entrypoint runs as `factory`, and `/home/agent` belongs to `agent` with mode `0755`, so it could make the folder only through `sudo -u agent`. The folder would then be the agent's own, writable to the agent by its owner's bits, with only the kernel's guard to refuse the write. It would also be made again at every start. The Dockerfile already lays out the agent's home (`/home/agent/.claude`) as root before `USER factory`. Made there, the folder is in every new container, since the home outside `.claude` is no volume, and it is owned by `factory` with mode `0755`: the agent, in the group `factory-work`, can read it and cannot write it, guard or no guard. A build under rootless Podman sets owners the same way as the image's other folders. So the fix is the image alone, not both. (S0001)
3. **`/home/agent/.config` stays the agent's** (`agent:factory-work`, `0755`). A root `mkdir -p` would leave it root's. `factory-confine` makes each folder of a run's rules as the agent before it confines the run (`_make_folders`), and an operator's build names folders such as `.config/sso-opencode` in `FACTORY_OPENCODE_FOLDERS` (the operator guide's example). With a root- or factory-owned `.config` that `mkdir` would fail, and every run of such an instance would stop. The kernel's guard still refuses every write under `.config` that the rules do not name. (S0001)
4. **Rejected: `XDG_CONFIG_HOME` set to the run's temporary folder.** opencode would then make its configuration folder there, and the folder would go with the run. But the variable moves every tool's configuration, and it would move where an operator's build looks for the single sign-on login it keeps under `.config` (the reason `FACTORY_OPENCODE_FOLDERS` exists). (S0001)
5. **The smoke test shows the mechanism, the human's change 1 the image.** The smoke tester runs in a container of the image built before the story, so it cannot see the new folder. Its first block reads the Dockerfile. Its second runs the image's `opencode debug config` under `factory-confine` in two temporary homes, offline and free: one fresh (exit 1, `EACCES`) and one with a read-only `.config/opencode` (exit 0). The drafting agent ran that block as `agent` in a throwaway container on 2026-10-19 and got `fresh 1`, `made 0`, `1`. (S0001)
6. **Ten seconds for a child that must act before its limit, and a bound of 25.** The failed row had three seconds and lost. On an idle core in the image the chain takes about 0.2 s, so ten seconds is about fifty times that. A runtime's kill is measured from its own start, whatever the child's start costs, so a killed run still ends near ten seconds. The bound of 25 leaves fifteen seconds above it. Every stand-in that the limit must end waits 30 or 60 seconds, longer than the bound, so a missed kill still fails. The cost: eighteen tests wait about ten seconds instead of one to five, and two rows of the `sudo` test 11.5 s instead of 4.5, roughly 160 more worker seconds spread over every core, a few seconds of a parallel `make test`. Rejected: waiting for the child's record before the limit counts (the night log's second idea). The limit is the runtime's own, measured from its start, and a test cannot move it without changing the code under test. Rejected: five seconds, which is barely more than the three that failed. (S0002)
7. **Which tests change, and which keep a short limit.** The drafting agent read every test with a limit of five seconds or less around a process. A test changes when the child must do something before the kill for the test to pass or to mean anything. That is the eighteen of decision 9, two of them in the modules F0020-S0010 added after the draft; three of them would still pass with a child killed too early but would then check nothing (the rows that print a reply before the kill, and the opencode wrapper's `time-limit` row, whose temporary folder `factory-confine` makes only once it runs). The rest keep their short limits, because a child that is never started is killed just the same: `test_call_over_its_time_limit_is_killed_with_unknown_measures`, `test_version_query_over_its_limit_is_a_runtime_error`, the two `os_user`/`sudo` tests whose `sudo` line is written before the inner one-second `timeout` starts (the outer limit has `SUDO_GRACE`, 30 s, on top), `test_with_a_user_the_inner_kill_at_the_limit_is_a_time_limit_without_measures`, `test_command_that_reaches_its_time_limit_raises_without_exit_status`, the `timed-out` row of `test_the_state_directory_holds_no_file_after_a_run`, `test_a_version_that_cannot_be_read_is_a_runtime_error`, and `test_a_removal_that_outlasts_its_time_limit_is_ended_and_changes_no_result`. (S0002)
