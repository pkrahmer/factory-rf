# Stalls

## Assignment (as of log entry 1)

Build the stall: the one way a stage ends without a result the factory can keep. A stall costs one attempt, never a crash. Whatever ended the agent run, the undo and the restore are applied to what it wrote (the service of F0004), the writes inside the write paths are kept and committed so the next attempt continues from them, the claim is released in the stall's own commit, a stall entry is written by code, the commit is pushed and only then the stall note is posted on the pull request with a key. The stall note says "retrying" only while the attempts cap is not reached (ST1.4's rule for this note). A `HostingServiceError` is not a stall: it propagates (before anything is written when the pull request is ensured, after the push when the note is posted). The module `factory.domain.decisions` is created here with the stall reasons and the mapping from an agent run's end reason to a reason; later stories call the stall service for their reasons (the branch, the decision, the form, a red check, a merge conflict). Covers GH2.5 (the stall side of the kill-point table of handover section 7.2). Keeps kept thing 14 (a stall counts attempts, a rework counts rounds, apart), kept thing 12 (a stall is said on the pull request) and R23 (a stall, not a crash).

`src/factory/application/stalls.py`

```python
class StallContext(BaseModel):
    work_item: WorkItemId
    stage: Name
    branch: str
    path: str
    stage_start: StageStart | None
    document: WorkItemDocument | None = None
    pull_request: PullRequestView | None = None

class StallResult(BaseModel):
    reason: StallReason
    attempts: PositiveInt
    attempts_cap: PositiveInt
    commit: CommitId
    pull_request: PositiveInt
    note: PostOutcome
    undo: UndoReport | None

class StallService:
    def __init__(
        self, boundaries: Boundaries, instance: str, definition: PipelineDefinition
    ) -> None: ...
    def stall(
        self, context: StallContext, reason: StallReason, detail: str = ""
    ) -> StallResult: ...
```

Types: `AgentRunResult` from `factory.domain.agent_runs`, `StageStart` from `factory.application.claims`, `UndoReport` from `factory.application.undo`, `PostOutcome` and `PostKey` from `factory.domain.hosting`. Both models are frozen and forbid unknown keys, and `StallResult` refuses `attempts`, `attempts_cap` and `pull_request` below 1 (criterion 21). `StallReason` adds `check_red` and `merge_conflict` to the interface sheet's seven reasons.

- `stall_reason_of(result)` maps the end reason `died`, `time_limit`, `budget` and `no_result` to the stall reason of the same name and `completed` to `None`.
- `stall_cause(reason, detail)` returns the reason's sentence, and `<sentence>: <detail>` when `detail` is not empty. The sentences are: `died` "the agent run died without a result"; `time_limit` "the agent run reached its time limit"; `budget` "the agent run spent its budget, and the resume too"; `no_result` "the agent gave no valid decision and entry"; `decision_not_allowed` "the agent's decision is not an allowed one"; `left_branch` "the agent left the work item's branch"; `form_invalid` "the work item's form broke during the stage"; `check_red` "a check is red after the stage"; `merge_conflict` "merging the main branch conflicts and the merge was aborted".
- `stall_note` returns `Stalled (attempt <attempts> of <attempts_cap>): <cause>. ` followed by `Retrying on the next tick.` when `attempts < attempts_cap` and by `The attempts cap is reached; the factory asks you next.` otherwise.
- `StallService.stall` does these steps in this order. (1) When `context.stage_start` is not `None`: if the checkout is not on `context.branch`, what the agent left on the branch it switched to is discarded with `reset_to("HEAD")` (that branch keeps its head) and `context.branch` is checked out at the stage-start commit (`checkout(branch, start_point=<commit>)`); then `UndoService.undo(stage_start, path)` runs, whatever the reason, and its report is `StallResult.undo`. When `stage_start` is `None` nothing is undone and `undo` is `None`. (2) The document is `context.document` when given, else the work item file read from the work tree. (3) The pull request is `context.pull_request`, else `WorkItemOpening.ensure_pull_request`. (4) The new state has `attempts` + 1, `claim` released with `ClaimService.release` and `pull_request` set; `stage`, `blocked`, `round`, `crashes`, `comments_read` and `handed_over` are unchanged. One entry is appended: `NewEntry(speaker="factory", kind="stall", text="Stage <stage> stalled (attempt <n> of <cap>): <cause>")`, with the cause from `stall_cause(reason, detail)` and `<cap>` the pipeline definition's `attempts_cap`. (5) The file is written, everything in the work tree is committed in one commit and pushed; any push outcome but `pushed` raises `PushFailed`. (6) After the push the note is posted with `post_comment(pull_request, stall_note(reason, n, cap, detail=detail), PostKey(work_item=..., kind="stall", n=<the stall entry's journal number as decimal digits>))`.
- A stall is a value, never an exception. `PushFailed` ends `stall` early. A `HostingServiceError` propagates unchanged: from step 3 (`ensure_pull_request`) before the file is written, committed or pushed, so the remote is unchanged; from step 6 (`post_comment`) after the push, so the stall commit stays on the remote and no note is posted.
- The stall adds exactly one commit: its parent is the stage-start commit when the agent committed nothing, and the agent's last commit when it committed (the agent's commits stay in the history, F0004 decision 15); when the agent left the branch, nothing it left is kept and the parent is the stage-start commit.

Tests: `tests/domain/test_decisions.py` (new; `stall_reason_of`), `tests/domain/test_stall_texts.py` (new; `stall_cause` and `stall_note`, so that F0003's `tests/domain/test_post_texts.py` stays as it is), `tests/application/test_stalls.py`. The last module starts stages with `StageLauncher` and the fake agent runtime (scripted writes and results); a subclass of `ObservingRuntime` in this story's own test module switches the checkout to another branch while it runs; `tests/observing_runtime.py` stays as S0003 wrote it.

## Acceptance criteria

1. `stall_reason_of` returns `died`, `time_limit`, `budget` and `no_result` for a result with that end reason and `None` for `completed`.
2. `stall_cause` returns, for each of the nine reasons (parametrised), exactly the sentence the Interface gives, none of them containing the word "retry"; with a detail it returns `<sentence>: <detail>`, without one the sentence alone.
3. `stall_note("died", 1, 2)` returns exactly `Stalled (attempt 1 of 2): the agent run died without a result. Retrying on the next tick.`
4. With the attempts cap 2, a note for attempt 1 contains "retrying" (compared without regard to case), and a note for attempt 2 and one for attempt 3 contain no "retry" in any case and end with `The attempts cap is reached; the factory asks you next.`
5. For a run that ended `died`, `time_limit`, `budget` or `no_result` alike, after `stall` the commit pushed to the work item's branch holds the scripted write inside the write paths (`tests/test_a.py` for the role `tester`) and holds no write outside them (`src/b.py` is gone from the tree and from the commit).
6. An agent that rewrote the work item file's state and journal (a lower `attempts`, another `stage`, an extra journal record) gets them put back: in the pushed file `stage` is the stage-start state's stage and the journal holds the stage-start records plus the stall record only.
7. `attempts` rises by one: from 0 to 1 and from 1 to 2 in two stalls of one work item, and `StallResult.attempts` is the new value and `attempts_cap` is the pipeline definition's cap.
8. `stage`, `blocked`, `round`, `crashes`, `comments_read` and `handed_over` of the pushed state are equal to the stage-start state's (a stage-start state with `crashes` 1, `comments_read` 3 and a `handed_over` of 2): a stall touches the attempts counter only.
9. The pushed state has `claim` equal to `None`, so a later tick does not take the stalled stage for a crash.
10. The journal gains exactly one record, number n+1 for n records before, speaker `factory`, kind `stall`; its displayed text starts with `Stage tests stalled (attempt 1 of 2): ` followed by the cause.
11. The pushed state's `pull_request` is the number in `context.pull_request`; when the context has none, an open pull request of the branch is used, and when there is none, a draft is created first and its number is recorded.
12. `StallResult.commit` equals the head of `origin/<branch>`; for an agent that committed nothing, that commit is exactly one commit above the stage-start commit.
13. For an agent that committed a file inside its write paths, its commit stays in the history and the stall commit's parent is that commit: the stall adds exactly one commit above the agent's last commit.
14. When the push is rejected (another clone pushed to the branch first), `stall` raises `PushFailed` and no stall note has been posted (`factory_posts` is empty).
15. The note is posted once on the pull request: `factory_posts` holds one comment whose key is `PostKey(work_item, "stall", <the stall entry's number>)` and whose text contains `stall_note(...)`; `StallResult.note` is `posted`.
16. A `stage_start` of `None` (the stage never started, a merge conflict at the preparation) undoes nothing: `StallResult.undo` is `None`, the stall is committed with `attempts` + 1 and the note is posted.
17. When the agent left the work item's branch (a file written on another branch, the checkout switched), the checkout is on the work item's branch again after `stall`, the head is the stall commit and its parent is the stage-start commit, the file written on the other branch is not in the tree, and the other branch still has the head it had.
18. When `context.document` is given, its journal records stay and the stall record follows them: a document with the agent's entry appended before `stall` is pushed with that entry above the stall entry.
19. A `HostingServiceError` from `ensure_pull_request` (armed with `fail_next("create_pull_request")`, a context without a pull request and a branch without one) propagates from `stall`, and `origin/<branch>` is still the stage-start commit.
20. A `HostingServiceError` from the note (armed with `fail_next("post_comment")`) propagates from `stall`; `origin/<branch>` holds the stall commit and `factory_posts` is empty.
21. `StallResult` refuses what its types refuse, on both sides: `attempts=1`, `attempts_cap=1` and `pull_request=1` are accepted and each of the three set to 0 raises `ValidationError`; `commit="a" * 40` is accepted and `"a" * 39` raises `ValidationError`; `StallResult` and `StallContext` are frozen (assigning to `reason` and to `branch`, through `setattr` with the field's name in a variable, raises `ValidationError`) and each refuses an unknown key (built through a variable typed `type[BaseModel]`).
22. make check stays green.
23. docs: `docs/operator-guide.md` explains the stall note on the pull request (attempt n of the cap, the cause, "retrying" only before the cap) and what the operator does when the cap is reached; `docs/project-guide.md` lists the stall reasons and says that a stall releases the claim, keeps writes inside the write paths and undoes the rest, and that a hosting-service error during a stall propagates.
