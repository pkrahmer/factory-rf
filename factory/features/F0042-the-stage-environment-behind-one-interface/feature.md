# The stage environment behind one interface

## Goal

v1.2 replaces v1.1's many layers of protection (the second user with `sudo`, the kernel's write guard, the undo, the leftovers program, the fresh home, the removal of ignored files) with one mechanism, decided by the human on 2026-10-24 and written in `planning/v1.2-plan.md`: every stage runs its steps in throwaway Podman containers on one ZFS dataset, mounted at `/work` in every container and at a configured path on the host. A stage rolls the dataset back to its base snapshot, runs a sync container (a fetch from the host's own repository through a read-only mount, the checkout of the stage-start commit, the project's `make sync`), moves the base forward, runs the agent's container, and then **takes** from the dataset only what the role may write into the factory's own work tree on the host: the write-path refusal rule applied the other way round, in place of the undo. The dataset is rolled back again and the project's commands run in a container on the taken result. Git stays the only state between stages, by construction and not by cleaning. This feature is the first of v1.2: it puts the cycle behind one interface, `StageEnvironment`, with fakes for the suite, and keeps v1.1's own way (the agent in the factory's container, the undo) as the second implementation, `InlineEnvironment`, so that `self` keeps building on Docker while the container environment grows and until F0044 (the layers go) removes it. It is for the human, who wants a factory with fewer moving parts, and for the operator of the VM that F0043 (the machine and the stage image) builds. When it is done, the generic factory (the claims, the stage protocol, the decisions, the stalls, the hosting service, the costs) behaves as before under `inline`, and an instance with `FACTORY_STAGE_ENVIRONMENT=container` runs the whole cycle on real `podman` and `zfs`, which the suite never needs. Done when every story below is merged and `make check` is green; the real proof is F0043's story 4, the first stage on the VM.

## Decisions taken for the human

1. **Two environments behind one interface, chosen by a setting; the environment's pieces live in the boundaries** (S0005, S0007, S0010). `StageEnvironment` is the abstract base class in `factory.application.stage_environment` with three operations, `prepare(commit, branch, *, sync_time_limit)`, `run_agent(request, *, run=None) -> SealedRun` and `take(stage_start, work_item_path) -> TakeReport`. The brief names `agent_runtime` and `project_commands` as members too; they are not, because `PatientRuns`, the preflight's version item, `KnownResults` and `RecordingProjectCommands` already read `boundaries.agent_runtime` and `boundaries.project_commands`, and one place for each is simpler than two. The wiring puts the container-started runtime and `ContainerMakeCommands` into those two fields for a `container` instance, so every caller keeps its call path. `Boundaries` gains `snapshots: Snapshots | None = None` and `containers: ContainerRuns | None = None`, as it has `agent_home`; `stage_environment_of(boundaries)` builds `ContainerEnvironment(boundaries, snapshots, containers)` when both are set and `InlineEnvironment(boundaries)` otherwise. The environment is built from the boundaries and not stored in them because both environments need the boundaries themselves (the `WritePathService`, the readers, the git), and a field cannot hold what holds it. `StageRunner` builds one environment and hands it to `StageLauncher` and `AfterAgent` through a new keyword `stage_environment` (default `None`: built from the boundaries), so one timing line can carry the reset, the sync, the advance and the take of one stage. Options: A, this (taken); B, the environment as a field of `Boundaries` built by the wiring with every reader passed one by one (eight constructor arguments and a `pyproject.toml` change); C, the environment given to `StageRunner` by the wiring (every test that builds a runner changes).
2. **`run_agent` wraps the whole patient run and returns `SealedRun`** (S0005). `run_sealed` takes a `run` callable so that the seal and the home reset happen once around `PatientRuns.run`, however often it resumes a session; the interface keeps that shape: `run_agent(request, *, run=None)`, `run` defaulting to the boundaries' runtime. It returns the existing `SealedRun` (`factory.application.sealed_runs`), the result and the nested repositories, so that `LaunchedStage.nested_repositories` and the early stall `nested_repository` stay as they are under `inline`; the container environment returns an empty list, since a repository the agent leaves on the dataset is rolled back. F0044's story 7 (the inline environment goes) moves the type when `sealed_runs` goes. No second DTO is made for it.
3. **The sync container's time limit comes from the pipeline definition's `sync` command, read by the launcher** (S0005, S0006, S0007). `prepare` takes `sync_time_limit`; `StageLauncher` passes `definition.project_commands["sync"].time_limit` in minutes and, when the definition has no `sync`, the default of a project command (`ProjectCommandDefinition().time_limit`, 10 minutes); the preflight passes its `PROBE_TIME_LIMIT`. The environment reads no definition of its own. The human's change 1 sets 5 minutes for this repository.
4. **`prepare` takes a commit and a branch, not a `StageStart`** (S0005, S0007). The preflight's probes prepare the dataset for `origin/main` without any claim, so the operation takes what both callers have: the commit to reset to and the branch to check out. The launcher passes the stage-start commit and the work item's branch.
5. **The sync container fetches every branch of the host repository, checks the branch out and resets it hard to the commit** (S0007). The brief says `git fetch /upstream <branch>` and `git checkout -f <commit>`; a detached checkout would leave the agent without `main` and without its branch, and the coder's and reviewer's instructions read `git diff main` and the branch's log (the human's decision 5: the agents read history and diffs as today). So the script fetches `+refs/heads/*:refs/heads/*` with `--prune` and `--update-head-ok` from `/upstream` (a fresh `git init` has `main` checked out, which a plain fetch into `refs/heads/main` refuses; the S0007 pre-check, 2026-10-24), checks the branch out and resets it to the commit. The container paths the script uses are passed as its own argument words (`/work/checkout`, `/work/home`, `/upstream`, `/etc/factory/claude`, the branch, the commit), never written into the script text, so that `FakeContainerRuns` can map them to host folders.
6. **The agent files reach `/work/home/.claude` through the sync container** (S0007). The sync container mounts `FACTORY_CLAUDE_HOME` read-only at `/etc/factory/claude` (the place F0043's image will hold them) and replaces `/work/home/.claude` with a copy before the base moves, so one run cannot widen the tools of the next, and the factory process copies no files itself. One source for the agents on the host: the preflight's `agents` item and the sync read the same folder.
7. **The check container copies what differs from `HEAD` on the host, not a remembered list of taken paths** (S0009). After the take, the host's work tree differs from the stage-start commit (`HEAD`) by exactly the taken files, the restored work item and the cost record the factory wrote; `git.changed_paths("HEAD")` names them, ignored paths left out. `ContainerMakeCommands` resets the dataset, copies those paths from the host's work tree into the dataset's checkout (deletions mirrored) and runs `make sync && make <command>`. No state is shared between the take and the checks, the preflight's `lint` on `main` copies nothing, and `TakeReport` needs no `taken` list. The copying is one function, `copy_changed(source, target, changed)` in `factory.application.take`, used by the take and by the check container alike.
8. **`ContainerMakeCommands` lives in `factory.adapters.make_commands`** (S0009). It is the second make-based implementation of `ProjectCommands` (R11), it reads a command's output exactly as `MakeProjectCommands` does (the last line that is no `make:` message, the tail of 30 lines, the `<target>: green` times) and shares that reading instead of copying it, and `tests/test_make_search.py` allows the word `make` in that module and in the preflight only.
9. **The journal sentence stays `The factory undid changes outside the write paths: ...`** (S0005). The inline environment undoes; the container environment leaves out. One sentence for both would be `The factory left out changes outside the write paths: ...`, which touches the pinned constant in `factory.domain.decisions` and the tests `tests/domain/test_agent_entry.py`, `tests/application/test_after_agent.py` (`UNDONE_PARAGRAPH`) and `tests/application/test_costs.py` (`UNDONE_PARAGRAPH`). This feature is built by `self` on `inline`, where the sentence is true; F0044's story 5 (the undo goes) changes it with the leave for those three modules. Options: A, keep it (taken); B, `left out` now, with the leave for the three modules in S0005.
10. **`TakeService.take` takes the work item's path, and the service takes the dataset's mount point** (S0004). The brief writes `take(stage_start, settings, changed_paths)`; the undo's second rule (every other file directly in an `in-progress/` folder is refused) needs the stage's own work item path, and the work item's restore needs it too, so the signature is `take(stage_start, work_item_path, changed_paths)` and the service reads the write paths through `WritePathService.at`, as the undo does. The dataset's path on the host comes from `Snapshots.mount_point`, an abstract property of the interface, so that the environment, the take and the check container read the files of the same dataset the snapshots roll back.
11. **`ContainerRuns` has two operations, `launch` and `run`** (S0001, S0003, S0008). The runtimes read stdout and stderr apart and opencode streams its lines through `run_streaming`, so a merged `run` result cannot carry an agent's call; the runtimes need the words that start a command in a container, as they take the words of `sudo` today. `launch(...)` gives them as a `ContainerLaunch` (words, environment, time limit), and `run(...)` is `launch` run through the process module with its output merged, for the sync container and the check container. `PodmanRuns.launch` adds 30 seconds of grace to the time limit (podman's `--timeout` kills first, as the agent's own `timeout` does under `sudo`); `FakeContainerRuns.launch` adds none, since nothing kills inside. The host-side `podman` process inherits the factory's own environment (the S0003 pre-check, 2026-10-24: podman passes none of it into the container, which gets `--env` entries only, and rootless podman itself reads `HOME`, `XDG_RUNTIME_DIR` and `PATH`): `ContainerLaunch.env` is `dict[str, str] | None`, `None` being the process's own environment; `PodmanRuns.launch` returns `None`, `FakeContainerRuns.launch` its mapped dict; `agent_launch.Launch.env` becomes `dict[str, str] | None` in S0008.
12. **`FakeContainerRuns(workspace)` maps container paths to host folders by the mounts** (S0001). Every word of the command, every value of the environment and the working directory that equals a mount's target, or starts with it and a slash, gets the mount's source in its place; `/work` is always mapped to `workspace`, as `PodmanRuns` always mounts it. A mount whose target is `/work` or lies under it is refused by both implementations. The fake cannot make a mount read-only; it records every call (`calls`) so that a test can read the mounts a caller asked for, the `:ro` ones included.
13. **`zfs diff -FH`, not `zfs diff -H`** (S0002). `-F` adds the entry's kind, and a directory (`/`) is listed by `zfs diff` whenever an entry inside it changes; `changed_paths()` lists files, links and other non-directory entries only, so the take never meets a folder. The brief's four letters (`M`, `+`, `-`, `R`) are read as it says.
14. **`FACTORY_ZFS` and `FACTORY_PODMAN` are one executable each** (S0010). The brief leaves room for `sudo -n zfs`; one word keeps the setting like `FACTORY_CLAUDE`. Where the rollback needs root (the human's decision 3), the operator writes a one-line wrapper script (`exec sudo -n /sbin/zfs "$@"`) and names it in `FACTORY_ZFS`; the `sudoers` line names the four commands that need root on the one dataset (`snapshot`, `destroy`, `rollback -r`, `diff -FH`), and the wrapper routes only those four through `sudo -n` and runs `list` and `--version` plain (F0043's decision 7, which writes the wrapper in `vm/setup.sh`). F0043's story 2 writes what was found.
15. **A `container` instance runs no second user, and three preflight items are not run for it** (S0010, S0011). `FACTORY_AGENT_USER` set together with `FACTORY_STAGE_ENVIRONMENT=container` is `SettingsInvalid`: the container is the second user, and the runtime refuses a request with an `os_user` when it has a container. The items `agent-user`, `tool:sudo`, `confinement` and `agent-environment` are not run for `container`: the first three check layers the container replaces, and the fourth checks that the agent's `HOME` is a directory on the host, while the container's `HOME` is `/work/home`, a path inside the dataset's mount. The `opencode` item checks the model aliases only under `container`: the executable is the stage image's, and `agent-runtime-version` runs it there. Decision 15 is the brief's requirement 8 completed by the two items it did not name. Also (the F0043 draft, 2026-10-24): the items `tool:claude` and `tool:opencode` look for the runtime's executable on the host's `PATH`, where a `container` instance has none (the runtimes live in the stage image), so they are not run for `container` either; `agent-runtime-version` runs the executable in a container and is the check of its presence. The item `tool:make` is not run for `container` either: the host runs no `make`, the sync and the check run it in containers (the S0011 pre-check, 2026-10-24).
16. **The agent's container gets the request's environment less the logins, and the runtime's switches** (S0008). As under `sudo`: `env -i` becomes `--env NAME=value` for each entry; the login shell inside the container reads the mounted login files, so no token is in any argument. `HOME` is `/work/home` because the wiring sets it so for a `container` instance (`agent_run_environment`); `PATH` stays the one the factory builds (`/usr/local/bin:/usr/bin:/bin` is in it, where the stage image installs its tools). The `CLAUDE_CONFIG_DIR` switch and the rules file belong to the kernel's guard and are not set in a container, so Claude Code keeps its state under `/work/home`, which the rollback clears.
17. **Errors.** `SnapshotError(command, detail)` and `ContainerError(command, detail)` are `BoundaryError`s in `factory.domain.errors` (S0001). A failed `prepare` or `take` raises them out of the stage like an `AgentRuntimeError`: the dispatcher counts an error of the event, no code of the dispatcher changes. `ContainerMakeCommands` turns both into `ProjectCommandError`, so the preflight's `lint` on `main` reports `the probe on main could not run: ...` as it does for a refused `sudo` (S0009); `Preflight.run` catches them around the probes too (S0011).
