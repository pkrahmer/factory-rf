# opencode as a second agent runtime

## Goal

Today every agent run is one `claude -p` call under the subscription. This feature adds opencode (`opencode run --format json`, opencode-ai 1.19.3) as a second implementation of the agent-runtime interface (R12), chosen per instance by the operator, so that a project can run on another provider's models, on an API key alone, or on an operator's own opencode build with its own login (single sign-on at the human's work). Both runtimes share what is not the tool's own: the login shell, which now hands over an API key when its file holds one; the start under `sudo`, `timeout` and `factory-confine`, so the kernel's write guard of F0019 confines opencode exactly as it confines Claude Code, with no opencode plugin; and a new end reason, `provider_limit`, for a provider's spend limit (HTTP 428 behind the gateway at the human's work), which the application layer waits out and resumes by session, unattended and without counting an attempt, on either runtime. opencode has no budget flag and no structured-output flag, so the factory sums its cost while the run streams and stops it at the budget, and the agent ends with a fixed result block the runtime parses strictly. It is for the operator, who can run the factory on opencode or on a key and leave it unattended behind a spend limit, and for the human, whose pipeline rules stay in one place, `claude/agents/*.md`. Done when every story below is merged and `make check` is green; the real test is the todo demo built by an instance on opencode through the API (the human's change 6), which only the human starts.

- Reaching a provider through a gateway's own address (a base URL, `ANTHROPIC_BASE_URL` for Claude Code): the agent run's environment holds only the allowed names, so a Claude Code instance on an API key cannot be pointed at a gateway yet; the company build of opencode at the human's work knows its own endpoint and needs none. A later story (decision 21).

## Decisions taken for the human

1. **The API key wins over the token when its file holds one, and the file is always mounted.** Compose cannot mount a file only when it exists, so the bind is required like `claude-token` (`create_host_path: false`; Docker would otherwise make a folder in its place) and an empty file means no key; the host path is `${FACTORY_API_KEY_FILE:-./secrets/anthropic-api-key}`, so one instance on a machine can run on a key (opencode, or an instance the operator puts on the key at work) while `self` keeps an empty file and stays on the subscription. A key in the file is handed over as `ANTHROPIC_API_KEY` and the token is then not read: Claude Code would otherwise choose between the two itself, and the record must say which one paid. (S0001)
2. **The factory never reads the key.** The call's own shell reads the file at every call, as it reads the token today, so the key stands in no argument, run file, result, journal, cost record or log, and not in the factory's environment; a file the shell cannot read, or one that is not ASCII, stops the run with `AgentRuntimeError` before the runtime starts. The preflight's item `opencode` does not look at the key file: an API key is optional for opencode, whose operator's build may log in through single sign-on with a login it keeps in the agent's home (the human's fact of 2026-10-18), and whether a run can log in is the agent-run probe's to show, whose detail names the login in force. (S0001, S0008)
3. **The login in force is recorded from the shell's own report**, one line `factory-login-used: <login>` on standard error: the run's `login` (`api_key`, `subscription`, `none`), its cost record's `login`, and the preflight's log line `preflight: agent-run-probe: ...` after a passing probe. The factory learns which login was used without opening either file. (S0001)
4. **What both runtimes share lies in `factory.adapters.agent_launch`, and the summing of a resumed run in the domain** (`resumed_result`), so the opencode runtime copies no helper of the Claude Code runtime's. The module builds words and texts only and does not import the process module: each runtime keeps its own `run_process` or `run_streaming` call, and every name an earlier test imports from `factory.adapters.claude_runtime` or sets on it (`SWITCHES`, `ENTRY_DESCRIPTION`, `FINISH_MESSAGE`, `VERSION_TIME_LIMIT`, `resume_budget`, `CLEANUP_SCRIPT`, `CONFIG_VARIABLE`, `SUDO_EXECUTABLE`, `LOGIN_SCRIPT`, `LOGIN_VARIABLE`, `SHELL_EXECUTABLE`, `DEVICE_FILES`, `DEVICE_FOLDERS`, `CLEANUP_TIME_LIMIT`, `run_process`) stays a name of that module that it reads at the call, defined there or imported and listed in its `__all__` (never `import X as X`: ruff's `PLC0414`), so no earlier test changes. (S0001, S0002)
5. **The output is streamed by the one process module.** `run_streaming` hands every line of standard output and standard error to a callback while the process runs and kills the whole process group when the callback says stop; it shares the one `subprocess.Popen` line with `run_process`, so `tests/test_process_search.py` and CLAUDE.md's exception stay as they are. Streaming is needed for the budget and for a limit that would otherwise hang until the stage's `time_limit`. (S0003)
6. **opencode's agent is generated per run from the same `AgentDefinition` the Claude Code runtime uses, not kept beside the shipped agents.** The runtime writes a configuration file per run, `/state/runs/opencode-<run>.json` (mode `0640`, removed after the run), and names it in `OPENCODE_CONFIG`: one agent `factory-<name>` whose prompt is the agent file's body and the result block's instructions, whose tools are the agent file's `tools` mapped to opencode's names (every other opencode tool off), and whose `bash` permission denies the `Bash(...)` patterns of the installed `settings.json` (`permissions.deny`). So `claude/agents/*.md` and `claude/settings.json` stay the one source of the pipeline's rules (R14 and the others): the Claude Code runtime already ignores Claude Code's agent files in print mode and applies the keys itself, and a second set of files beside them would drift. R14's sentence about the hook is then not true under opencode; the kernel's guard and the undo are. (S0004)
7. **The decision and entry without a schema flag: a fixed final block, parsed strictly.** The runtime appends to the agent's instructions the block it must end its final message with (`<factory-result>`, a `decision:` line, an `entry:` line, the entry, `</factory-result>`), with the allowed decisions named; it parses only the last `text` event, which must end with the closing line. A missing or malformed block, a decision outside the allowed ones or a blank entry is a run without a usable reply (`no_result`), as for Claude Code without its structured output. The block's instructions belong to the runtime, not to the agent files, because Claude Code's runs get their form from the schema flag. (S0004)
8. **opencode's measures**: the cost and the tokens are the sums over the `step_finish` events (output tokens include the reasoning tokens; cache read and write are `cache_read` and `cache_creation`); the turns are the number of `step_finish` events; the model time is the sum of each step's span (its `step_start` to its `step_finish`) less the spans of the tool calls within it; the refused tool calls are the `tool_use` events with `status` `error` whose error names a permission or a denial. A step the factory's stop cuts short has no `step_finish`, so its cost is unknown, not zero (R24); the budget stop comes right after a `step_finish`, so at most the step just begun is lost. (S0004, S0006)
9. **Models and effort under opencode.** The agent files keep Claude Code's aliases; the operator setting `FACTORY_OPENCODE_MODELS` maps each alias to a `provider/model` id (the image sets the three Anthropic ones), a model with a `/` is passed as it is, and an alias without a mapping stops the run before it starts and fails the preflight's item `opencode`. The effort is not passed: opencode's `--variant` was seen in the probe but not its values, and a wrong one would end every run; the todo-demo run's cost tables show whether it matters, and a later story maps it. (S0004, S0008)
10. **opencode's own state in the agent's home**: the runtime's own folders, which the confinement allows like Claude Code's `<HOME>/.claude` (F0019's decision 9), are `<HOME>/.local/share/opencode` (its sessions, needed to resume), `<HOME>/.local/state/opencode` and `<HOME>/.cache/opencode`; `factory-confine` makes them when they are missing. `<HOME>/.config/opencode` is not allowed, so a run cannot write a global configuration that later runs would merge. The snapshot repository (165 MB after four runs in the probe) is turned off by the setting `"snapshot": false` in the run's configuration, chosen over a tool path (it would keep growing) and over a cleanup after every run (a second mechanism); `"share": "disabled"` keeps sessions off opencode's sharing service and `"autoupdate": false` keeps the pinned version. Whether 1.19.3 honours each key, and whether it writes anywhere else, only the hand probe and the real run show (change 6). An operator's own build may keep its state, its single sign-on login above all, in other folders of the home and refresh the login during a run: the operator names them in `FACTORY_OPENCODE_FOLDERS` (relative to the home), which the confinement allows after the three. The one-time login as the agent user is the operator's step, as `claude setup-token` is for Claude Code, and so is its repetition after the container is recreated, since no volume holds these folders (or the operator mounts the folder with a compose override file). opencode is called with `--auto`, which approves every permission not explicitly denied, because a permission prompt with standard input closed would end or hang the run. (S0004, S0008)
11. **opencode's budget**: the factory sums the cost of the `step_finish` events while the run streams and stops the run when the sum passes the agent's budget (strictly above it); it then resumes the session once with `--session <id>`, the finish message and the share the Claude Code runtime gives a resume (`resume_budget`: a quarter, at least $0.50), within what is left of the time limit, as the Claude Code runtime does with its own budget flag. A stand-in shows the stop, the resume's arguments and the sums; only the real run shows how far a real step overshoots. (S0006)
12. **Recognizing a provider limit**: an operator setting, because the gateway's exact text and event are not known here: `FACTORY_PROVIDER_LIMIT_STATUS` (default 428) and an optional `FACTORY_PROVIDER_LIMIT_MESSAGE` (a regular expression). The status is matched in a structured field where the tool gives one (opencode's `error` event, its `statusCode`) and as a whole number in an error's text (Claude Code's error result, a line of standard error), never in the agent's own text or tool output, where "428" may be anything. A message that names a wait ("try again in 7 minutes", "retry after 120 seconds", `Retry-After: 120`) gives the run's `limit_wait`. (S0005, S0006)
13. **The end reason `provider_limit` keeps the session**: the result carries the runtime's session id on every run, and a request may name a session to resume (`resume_session`), so the application layer can continue the same session on either runtime without a new interface operation (`AgentRuntime` keeps `run` and `version`). A run that resumes gets the request's prompt and budget; a limit that hits before any session exists starts afresh. (S0005)
14. **The wait lies in the application layer, around a stage's run** (`PatientRuns`, used by the stage launch; not by the preflight's probe, which reports a limit as a failed probe): after a `provider_limit` it waits the named wait or the cool-down (`FACTORY_PROVIDER_LIMIT_COOLDOWN_MINUTES`, default 10) without any agent process running, then resumes the session with a short continue prompt, the budget that is left and the time limit that is left; the waits count toward neither the `time_limit` nor the attempts, crashes or stalls, and every wait is a line in the factory log. Repeated limits keep waiting until the waits reach the ceiling (`FACTORY_PROVIDER_LIMIT_CEILING_MINUTES`, default 120); then the run ends `provider_limit` and the stage stalls with that reason, one attempt counted, its note on the pull request; at the attempts cap the human is asked as for every stall. The claim stays held while waiting: v1.1 renews no lease, so a stage that waits may hold its claim for its time limit, the ceiling and its checks (about 180 minutes for the coder, against a lease of 60); the lease's age then passes `lease_duration`, which only another instance on the same repository could act on, and one repository has one instance; a restart or stop during a wait is a crash of the factory's own claim: it reruns the stage at once and counts toward `crash_cap` (2), not toward the attempts. Chosen over a machine stop at the ceiling, which would need its own clearing rule (a machine stop `provider_limit` that the next passing probe clears). The human's answer of 2026-10-18: yes, the claim stays held while waiting. (S0007)
15. **The spend window (throttling) is recommended and opt-in**: `FACTORY_SPEND_WINDOW` (`<dollars>/<minutes>`, such as `3/10`; unset by default). Before every run and every resume of a stage, the factory sums the spend of the window just past and waits until it is below the window's dollars. It avoids most limits but cannot prevent one inside a long run, so it adds to decision 14 and replaces nothing. The spend is kept in a log of its own in the state directory (`/state/spend-records.jsonl`), not summed from the cost records, which lie in sidecars on every work item's branch. The human's answer of 2026-10-18: not yet. S0009's file lies in `deferred/` beside `backlog/`, so the factory does not start it; it is built only when a later run at the human's work shows that the waits matter, and F0020's acceptance does not wait for it. (S0009, deferred)
16. **The runtime is chosen per instance**: `FACTORY_AGENT_RUNTIME` (`claude`, the default, or `opencode`), set per compose call like `FACTORY_INSTANCE`. Recommended because a runtime is the machine's and the operator's (its login, its image, its pin), not the project's, and one runtime per instance keeps one version item, one probe and one login in force; it is also all the human's work needs (one instance on opencode behind the gateway). The alternative, a `runtime` key per role in the pipeline definition, would allow mixing (Claude Code for the coder, opencode for the reviewer), at the price of a pipeline definition that names a tool (against R8's spirit), both runtimes' preflight items on every instance and a probe per runtime. The human's answer of 2026-10-18: yes, the runtime per instance. (S0008)
