# The machine and the stage image

## Goal

v1.2 runs every stage in throwaway Podman containers on one ZFS dataset (`planning/v1.2-plan.md`, decided by the human on 2026-10-24). F0042 (the stage environment behind one interface) builds the code of that cycle behind `StageEnvironment`; this feature builds the machine it runs on and the image the containers start from, so that an operator takes a fresh Ubuntu 24.04 VM with a spare disk to a running `container` instance in under an hour of their own time, with one script and one guide chapter. It is for the human, who makes the VM on GCP by the runbook (`planning/overnight/gcp-runbook-2026-10-24.md`) and runs the first stage on it, and for any later operator of such a machine. When it is done, `vm/Dockerfile` builds the stage image (today's image without the factory, the second user, `sudo`, the entrypoint and the sealed folders; the agent files at `/etc/factory/claude`), `vm/setup.sh` prepares the machine idempotently as root (the pool, the datasets, the user `factory` with linger and the ZFS delegation, the factory's own virtual environment from a git ref, the secrets folder, the environment file and the systemd service), `vm/factory.service` runs the factory as a service under `factory`, the checkout and the state directory are settings so that both live under `/srv/factory/<instance>`, and the operator guide's chapter "The machine" says how, on GCP and on any Ubuntu 24.04 VM. The old image under `image/` stays until F0044 (the layers go). Done when every story below is merged and `make check` is green; the proof is the human's first stage on the VM (*The human's changes*, change 4).

## Scope

- `vm/Dockerfile`: the stage image, built on the VM with `podman build -f vm/Dockerfile -t <FACTORY_STAGE_IMAGE> .` from a checkout; its tests `tests/test_stage_image*.py` (S0001).
- `factory.domain.settings`: `FACTORY_CHECKOUT` and `FACTORY_STATE`, the checkout and the state directory as settings with their faults; `factory.entry.run`: the stop of invalid settings goes to the directory `FACTORY_STATE` names (S0002).
- `vm/setup.sh`: the idempotent root script that prepares a fresh Ubuntu 24.04 with the facts of the runbook's sections 4 and 5, and `vm/factory.service`: the template unit `factory@.service`; their text tests `tests/test_vm_setup*.py` and `tests/test_vm_service*.py` (S0003).
- The operator guide's chapter "The machine": GCP in numbered steps, the same for any Ubuntu 24.04 VM, what the container can and cannot see, the costs, the metadata server, where the logs are; the decision-log entry of the machine (S0004, with the subsections S0001 and S0003 write).
- The tests each story names, under `tests/`.

## Out of scope

- Removing any file under `image/`, any test that pins it (`tests/test_image*.py`, `tests/test_compose*.py`, `tests/test_entrypoint*.py`, `tests/test_opencode_image.py`, their support modules), or any layer of v1.1: F0044 (the layers go). `self` keeps running on the old image throughout.
- Any code of the stage environment: the interfaces, the adapters, the take, the settings `FACTORY_STAGE_ENVIRONMENT`, `FACTORY_DATASET`, `FACTORY_WORKSPACE`, `FACTORY_STAGE_IMAGE`, `FACTORY_PODMAN` and `FACTORY_ZFS`, the preflight's items: F0042 (the stage environment behind one interface). This feature uses them as F0042 defines them.
- Any change to an agent text under `claude/agents/`, to the forms, or to `factory/pipeline.yml` beyond the human's change 1 below.
- Creating anything on GCP: the project, the budget alert, the network, the VM and the disk are the human's, by the runbook. No story and no smoke test runs `gcloud`, `podman`, `zfs`, `zpool`, `systemctl` or `apt-get`: the suite and the smoke tests run in v1.1's container, which has none of them, so they check texts and `sh -n` only.
- The first stage on the VM and the plan's measures (the start of a stage to the agent's first step, the reset, the sync, the take): the human's story 4 of the plan, change 4 below.
- A second machine type, a second cloud, a host without ZFS (the workplace's Podman Desktop; the plan's question 7): the chapter says what the script needs and names what it does not run on.
- Every paid call: no story and no smoke test makes one.

## Decisions taken for the human

1. **The checkout and the state directory become settings** (S0002). Today both are fixed (`/work/checkout`, `/state`; the operator guide says "not settings you can change"), and the brief's environment file names `FACTORY_STATE=/srv/factory/<instance>/state`. The plan puts the factory's own clone at `/srv/factory/<instance>/repo` and `/state` as "a folder of the service on the host". So `read_settings` reads `FACTORY_CHECKOUT` and `FACTORY_STATE` as absolute paths with today's values as defaults, `InstanceSettings.checkout` and `state_directory` take them, `factory-run` writes the stop of invalid settings to the directory `FACTORY_STATE` names, and `factory-health` keeps its `--state-directory` option (the operator passes it over SSH). The entrypoint already reads `FACTORY_STATE` for `/state/runs`, so the name is the one the image uses, and a compose instance that sets neither is unchanged. Options: A, this (taken: the smallest change that makes the brief's environment file true, and two instances on one machine stay possible); B, no story: the script makes `/work` and `/state` on the host, owned by `factory`, and the environment file holds neither variable (nothing of the code changes, the host grows two root folders, one instance per machine). If the human prefers B, S0002 is dropped and S0003's environment file loses the two lines `FACTORY_CHECKOUT=...` and `FACTORY_STATE=...`, its script makes the two folders instead of `/srv/factory/<instance>/repo` and `/srv/factory/<instance>/state`, and the guide's `factory-health` line loses its option.
2. **The chapter "The machine" is a story of its own, S0004, and the code stories write their own subsections first** (S0001, S0003, S0004). S0001's documenter writes `### The stage image`, S0003's writes `### The script` and `### The service`, each under a chapter `## The machine` that the first of them creates; S0004 writes the GCP steps, the steps for any Ubuntu 24.04 VM, what the container can and cannot see, the costs, the metadata server and where the logs are, and reads the whole chapter against the code once. The brief leaves the choice open; a documents-only story at the end is the pattern F0042's S0012 (the documents describe the stage environment) uses, and it keeps S0001 and S0003 inside one coder's forty minutes.
3. **The unit is a template unit, `factory@.service`, and the instance is its `%i`** (S0003). The brief writes `WorkingDirectory=/srv/factory/<instance>`; systemd's template units are the standard way to write `<instance>` once (`/srv/factory/%i`, `/srv/factory/%i/factory.env`, `/srv/factory/%i/factory/.venv/bin/factory-run`), so the script installs the file unchanged as `/etc/systemd/system/factory@.service` and enables `factory@<instance>`. No `sed` over the unit, and a second instance on the same machine is `factory@<other>`. The unit has `After=network-online.target zfs.target` and `Wants=network-online.target`, so the factory starts when the dataset is mounted and the network is up, and nothing else.
4. **The script runs in two passes when the hosting token is not there yet** (S0003, S0004). The checkout of the private repository (the factory's own code, under `/srv/factory/<instance>/factory`) needs the hosting token, and the brief places the secrets after the script. So the script does every step that needs no token, and at the checkout step, when `/home/factory/.secrets/hosting-token` is missing, prints one line that names the file and says to run the script again after placing it, and ends with status 0 without the checkout, the virtual environment, the environment file and the unit (all four need the checkout). The second run finds the first steps done and makes the four. The clone runs as `factory` with git's `GIT_ASKPASS` set to a four-line script the setup script writes to `/srv/factory/<instance>/askpass` (it answers a `Username` prompt with `x-access-token`, as `git-credential-factory` does, and any other prompt with the token file's content), and the checkout gets `core.askPass` set to that script, so the rebuild's `git pull` needs no second mechanism. The token is never written anywhere but its own file. Options: A, this (taken); B, the operator clones by hand before the script (a token in a URL, or a helper typed by hand: the thing the runbook forbids); C, the script takes the token as an argument (it would land in the shell's history and in `ps`).
5. **The pins reach the host from `vm/Dockerfile`, one source** (S0001, S0003). The factory process on the host compares `FACTORY_CLAUDE_VERSION` and `FACTORY_OPENCODE_VERSION` with what the runtime in the container reports (`agent-runtime-version`), and `FACTORY_OPENCODE_MODELS` is its setting too. The script reads `CLAUDE_CODE_VERSION`, `OPENCODE_VERSION` and `UV_VERSION` from the `ARG` lines and `FACTORY_OPENCODE_MODELS` from the `ENV` line of the checkout's `vm/Dockerfile` and writes them into the environment file, so a pin changes in one line and the rebuild (the chapter's step) runs the script again to carry it over. The stage image keeps the three `ENV` lines as a record an operator can read (`podman run --rm <image> printenv FACTORY_CLAUDE_VERSION`). Until F0044 removes `image/`, `tests/test_stage_image.py` pins that `vm/Dockerfile` and `image/Dockerfile` carry the same base digest, the same three tool pins (`ARG`s), the same Debian package versions and the same model ids (the S0001 pre-check, 2026-10-24), so the two images cannot drift apart.
6. **The image identity on the VM is a file the operator renews at every rebuild** (S0003, S0004). Today's image writes `/opt/factory/image-id` at build; the stage image carries no factory and the factory on the host has no `/opt/factory`. The brief says "the image carries the label `factory.image` as today (the preflight reads it)": the label stays, but the preflight reads the identity file, never the label (`docs/decisions.md`, "The image identity is read from a file the image build generates"). So the environment file sets `FACTORY_IMAGE_ID_FILE=/srv/factory/<instance>/image-id`, the script writes that file once from `/proc/sys/kernel/random/uuid` (owner `factory`, so the operator can renew it), and the chapter's rebuild step renews it after `podman build`, so the machine's items run again for the new image. Options: A, this (taken); B, the stage image's own id from `podman image inspect` (the factory's code can change without the image, and the operator would still have to write the file); C, a timer on the stamp (rejected by the decision log).
7. **The `sudoers` fallback names the four `zfs` commands exactly as `ZfsSnapshots` runs them, and the wrapper routes only those four through `sudo`** (S0003). F0042's S0002 (ZFS snapshots roll back, advance and diff the dataset) runs `rollback -r <dataset>@base`, `destroy <dataset>@base`, `snapshot <dataset>@base`, `diff -FH <dataset>@base`, and also `list -H -o name -t snapshot <dataset>@base`, `list -H -o name <dataset>` and `--version` through the one executable `FACTORY_ZFS` names (F0042's decision 14). The runbook's `sudoers` line writes `diff -H`; the code runs `diff -FH` (F0042's decision 13), so the script writes `-FH`. The wrapper `/usr/local/bin/zfs-factory` runs `rollback`, `destroy`, `snapshot` and `diff` as `sudo -n /usr/sbin/zfs "$@"` and every other first word as `/usr/sbin/zfs "$@"`, so `list` and `--version` need no `sudo` right and the `sudoers` file stays four exact commands on the one dataset. Both files are written only with `--sudoers`; without it `FACTORY_ZFS` is `zfs`.
8. **`uv` on the host comes from `pip` in a virtual environment of its own, and the service's `PATH` names it** (S0003). The runbook installs no `uv`; the preflight's `tool:uv` and the operator's `uv sync` need one on the host. The script makes `/srv/factory/<instance>/tools` with `python3 -m venv` and installs `uv==<UV_VERSION of vm/Dockerfile>` into it with `pip`, never with a download piped into a shell (the rule of `tests/test_image.py` holds for the script too), and the environment file sets `PATH=/srv/factory/<instance>/tools/bin:/usr/local/bin:/usr/bin:/bin:/usr/sbin:/sbin` (`/usr/sbin` for `zfs`), so `factory-run`, the preflight and the operator's rebuild find the same `uv`.
9. **The agent files have one source on the host, the checkout's `claude/`** (S0003). F0042's decision 6 mounts `FACTORY_CLAUDE_HOME` read-only at `/etc/factory/claude` in the sync container and the preflight's `agents` item reads the same folder; the stage image carries a copy at `/etc/factory/claude` as the brief asks, which the mount covers in the sync container. The environment file sets `FACTORY_CLAUDE_HOME=/srv/factory/<instance>/factory/claude`, so the agents an instance runs are the ones of the ref it was installed from, and a rebuild carries a changed agent file over without a new image.
10. **The three secrets are files in `/home/factory/.secrets`** (S0003, S0004): `hosting-token` (read by the factory process and git's helper on the host, never mounted), `claude-token` (`FACTORY_CLAUDE_LOGIN_FILE`) and `anthropic-api-key` (`FACTORY_API_LOGIN_FILE`), the two logins mounted read-only into the agent's container at their own paths by F0042's S0008. Today the logins lie outside the token's folder because a second user had to read them; on the VM one user reads all three, and the folder's mode `0700` keeps every other host user out. An empty `anthropic-api-key` is no key; a missing one stops every agent run at podman's mount (podman refuses to mount a missing file, exit status 125, and the factory mounts every login file that is set), so all three files must exist, as Compose demands today with `create_host_path: false` (the S0003 round-2 pre-check, 2026-10-25; the human's recommended answer A). A `claude-token` that is empty means no login from a file, which the preflight's probe reports.
11. **The stage image has no `WORKDIR`, no `USER`, no `ENTRYPOINT`, no `CMD`** (S0001). Every container gets `--workdir` from `PodmanRuns` (F0042's S0003) and runs as the host's `factory` through `--userns=keep-id`; a default in the image would only be a second place to be wrong.
12. **The datasets' properties live on `<pool>/factory` and the quota on the instance's dataset** (S0003). `compression=lz4` and `atime=off` are set on the pool at creation (the runbook) and again on `<pool>/factory` by `zfs set`, so a pool made by hand before the script gets them too; `quota=<quota>` (default `30G`) is set on `<pool>/factory/<instance>`, so a second instance has its own. `ashift=12` at `zpool create`, as the runbook.
13. **The script enables the service and does not start it** (S0003, S0004). The first start needs the secrets and the image; the chapter's "first start" step is `systemctl start factory@<instance>`. `Restart=always` with `RestartSec=15` then keeps it up, and systemd's start rate limit never trips at that spacing.
14. **The script's argument faults and its root check are run for real in the suite; its steps are pinned by text** (S0003). `sh -n` and the text order are what the brief asks for; the usage line, a missing required option, an unknown option and the refusal to run as another user than root cost nothing to run in the container (as the factory user, every run ends before the first step), so they are criteria with exact exit statuses.
15. **The leaves to change tests other stories wrote: one, in S0002.** S0001 adds tests beside `tests/test_image*.py` and changes none of them; the tester may move the Dockerfile readers of `tests/test_image.py` (`floating_references`, `_instructions`, `_commands`, `_env`, `_path_settings` and their helpers) into `tests/dockerfile_support.py` under the standing leave of `CLAUDE.md` (*Tests*), every earlier test keeping its name and assertions. S0002 changes one settings test and no run test: `test_the_checkout_and_state_directory_are_not_read_from_the_environment` of `tests/domain/test_settings.py` pins that `FACTORY_CHECKOUT` is ignored, so the tester removes that entry and renames the test `test_a_variable_the_settings_do_not_name_is_not_read`, keeping its `FACTORY_STATE_DIRECTORY` and `SOMETHING_ELSE` entries and both assertions (the human's leave, 2026-10-24, from the S0002 pre-check); `tests/entry/test_run.py` passes `state_directory` and is unaffected by the new default. S0003 and S0004 add modules only.
16. **The number and the name.** F0043 is the next free number after F0042 in `factory/features/` and in `planning/overnight/stories/`; the plan names it. The name says what is true when it is done: a machine, and the stage image.
17. **The setup script writes as `factory` from its own standard input, S0005** (the first real run of `vm/setup.sh` on the local VM, 2026-10-25). Every write under `$base` was `as_factory install -m <mode> /dev/stdin <target>`; `install` reopens `/dev/stdin` by name, which a process started by `runuser` may not do for root's pipe, so the first run ended at the `checkout` step with `install: cannot open '/dev/stdin' for reading: Permission denied` on every machine. S0005 makes the three writes read their inherited standard input with `cat` as `factory` and set the mode after it. It is built before S0004, so the guide describes the fixed script, and before the first stage on the VM. No earlier test changes.
