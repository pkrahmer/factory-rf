## Questions

1. **Version.** `opencode --version`; and whether this is upstream opencode or the company's fork, and its line.
2. **Skills.** Does this opencode load skills (`SKILL.md` files with a front matter, as Claude Code's), and from where (`.opencode/skill/`, `.claude/skills/`, `~/.config/opencode/...`)? Is there a tool that loads one on demand? If yes, try a tiny one in a temporary folder outside any repository and say what happened.
3. **Agents and commands.** Custom agents (`.opencode/agent/*.md`?) and custom commands (`.opencode/command/*.md`?): where they live, project-level and user-level, their front-matter keys, and whether a command can take arguments (for example `/operator merge off`).

5. **A turn that waits.** Inside one turn, call a shell command that sleeps two minutes and prints `continue`, three times in a row. Does the turn stay open, can the human interrupt it, and what did the three calls cost (if opencode shows it)?
6. **Context and compaction.** How large is the model's context window here, and does opencode compact a long session by itself? At what point?
7. **Toggles.** Which settings of opencode itself does the human already switch (the config file's keys), and can a command change a value in a file the agent then reads? A plain JSON or TOML file in `~/.config/factory-operator/` would do; say whether anything speaks against that.
8. **GitHub and the cloud from here.** Is `gh` installed and logged in for the company's GitHub? Is `gcloud` logged in with an identity that may read Cloud Logging of the factory's job and run `gcloud run jobs execute`? Which of these needs the proxy?

**2. Skills.** Yes. Scanned folders: project `.opencode/skills/<name>/SKILL.md` (also `skill/`), global `~/.config/opencode/skills/<name>/SKILL.md`, the auto-loaded external `~/.claude/skills/` and `~/.agents/skills/`, and the config's `skills.paths` and `skills.urls`. Front matter: `name` (lowercase, hyphens, the folder's name) and `description` are required (a skill without a description is never shown to the model); `license`, `compatibility` and `metadata` are optional. A tool, `skill`, loads one by name on demand and returns its body. **Tried:** a tiny skill in a temporary folder that is not a git repository, then a fresh headless `opencode run` there: the log showed `Skill "tiny-probe"` and the model answered with the word the skill held, 7 s in all. The skill list is read when opencode starts (the built-in help says config is not hot-reloaded), so a skill added in the middle of a session needs a restart to be seen; a new process sees it at once.

**3. Agents and commands.** Agents: `.opencode/agent(s)/<name>.md` in a project, `~/.config/opencode/agent(s)/<name>.md` for the user, or inline under `agent` in the config. Front-matter keys: `name, model, variant, description, mode (primary, subagent or all), hidden, color, steps, options, permission, disable, temperature, top_p`; unknown keys land in `options`; the file's body is the prompt. Commands: `.opencode/command(s)/<name>.md`, `~/.config/opencode/command(s)/<name>.md`, or inline under `command`; keys `description, agent, model, variant, subtask`; the body is the prompt. **A command takes arguments: tried** with `opencode run --command echo-args merge off`: `$ARGUMENTS` became `merge off`, `$1` became `merge` and `$2` became `off` (the quoted one-word form gave `$1` as the whole string).
