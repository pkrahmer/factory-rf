# v1.2: one snapshot instead of many layers (a proposed plan, 2026-10-24)

This is a proposal, written for the human after v1.1 was tagged. Nothing in it is decided until the human says so; the questions at the end are the decisions it needs. It continues `planning/v1.2-candidates.md`, whose first section holds the thinking of 2026-10-20 and 2026-10-21, and takes the human's design of 2026-10-24 as its ground.

## The idea

A stage of v1.1 runs inside one long-lived container, and the factory protects itself from what the agent does there with many layers: a second user with `sudo`, a umask and a group, a sealed git folder, the kernel's write guard, the undo, the removal of ignored files and nested repositories, the end of leftover processes, the fresh agent home, the re-clone of a damaged checkout. Each layer cleans one thing, and the stops of the night of 2026-10-20 came from layers meeting each other.

v1.2 replaces them with one mechanism. The factory runs on a small Linux VM with ZFS. Every stage runs in a throwaway Podman container that mounts one ZFS dataset. The stage begins by bringing the dataset up to date (a pull and the project's own sync, `uv sync` for Python, something else for another stack), and the dataset's snapshot is then pulled forward to that state. The agent works; the container ends; the factory takes from the dataset only what the role may write, commits and pushes it with its own token, and the next stage starts from the snapshot again. The container's root file system is the image plus a layer that is thrown away, so nothing the agent did in the container survives either. Git is the only state between stages, by construction, not by cleaning.

The generic factory stays as it is: the work items, the pipeline definition, the roles and write paths, the claim, the stage protocol, the decision rules, the stalls, the acceptance, the costs and records, the board, the hosting service. Only the boundary "run the agent and the project's commands, and keep the checkout clean" changes, and the code that existed only for that boundary goes.

## The cycle of a stage

Three places take part: the host (the VM, where the factory runs as the user `factory` with the hosting token, the state and the podman and zfs commands), the dataset (`<pool>/factory/<instance>`, mounted at `/srv/factory/<instance>/work` on the host and at `/work` in every container; it holds `checkout/`, the agent's `home/` and the caches), and the container (the stage image, started with `--rm`, one per step).

```
host: the factory                     the dataset (ZFS)                      the container (thrown away)
1 fetch, prepare, claim, push         .                                      .
2 zfs rollback -r @base               back to the base                       .
3 podman run ... sync        ------>  /work                         <------  git fetch /upstream <branch>; git checkout <stage start>; make sync
4 zfs destroy @base; zfs snapshot     the base moves forward                 .
5 podman run ... the agent   ------>  /work (HOME=/work/home)       <------  the agent works; the container ends (--timeout = the time limit)
6 zfs diff @base; take the write paths into the host's work tree             .
7 zfs rollback -r @base; copy the taken files in; podman run ... make check  the project's commands on the taken result
8 the entry, the one result commit, the push, the labels (as today)          .
```

1. **As today.** The tick fetches, the opening merges `main` in and the claim pushes the stage-start commit, from the factory's own clone on the host (`/srv/factory/<instance>/repo`, which today is `/work/checkout`). The hosting token is on the host and nowhere else.
2. **The reset.** `zfs rollback -r <dataset>@base` puts the dataset back to the base: a checkout of a recent commit with its `.venv`, the uv cache and an empty agent home. Whatever the last stage left is gone, files and all.
3. **The sync.** A container runs, with the dataset at `/work` and the host's git directory mounted read-only at `/upstream`: `git -C /work/checkout fetch /upstream <branch>`, `git checkout -f <stage-start commit>`, then the project's sync command, `make sync`. The container has no credentials: the repository is private, and it never talks to the hosting service; the host's repository is its upstream. For Python `make sync` is `uv sync --frozen`; a Java or TypeScript project names its own command in the same target. The base is close to `main`, so the fetch moves a few commits and the sync changes little or nothing.
4. **The base moves.** `zfs destroy <dataset>@base; zfs snapshot <dataset>@base`. From now on the base holds this stage's start, synced. The dataset is never cloned; one snapshot is enough.
5. **The agent.** A container runs the agent as today's chain minus `sudo`, `env -i` and `factory-confine`: the stage image, `/work` mounted, the login file mounted read-only, the request's allow-list environment as `-e` entries, the instructions file mounted read-only, `HOME=/work/home`, `--timeout <time limit>` so that the container runtime ends the run at its limit, and `--rm`. The agent may write anywhere it reaches: nothing outside the dataset survives the container, and the dataset is rolled back. The agent's home lies on the dataset so that a run resumed after a provider limit finds its session; the rollback gives every stage a fresh home.
6. **The take.** `zfs diff <dataset>@base` lists every path the run changed, without any git command on the dataset. The factory keeps the refusal rule of the write paths exactly as it is (`refusal(path, settings)`, the protected paths, the other work items in `in-progress/`) and applies it the other way round: a changed path the role may write is copied into the host's work tree (a deletion is mirrored), a path it may not write is left where it is and named in the journal, as the undo names it today. The state and the journal of the work item are put back from the stage-start commit, as today. No undo, no kernel guard: what the agent wrote outside its paths never reaches the repository, because it is never read.
7. **The checks.** Rule 6 only, as today. The dataset is rolled back to the base again, the taken files are copied in, and a container runs each check and report (`make sync && make <command>`, with `--timeout` as the command's time limit). The checks see the taken result on a clean base, which is what "the work tree after the undo" meant. A passed result is reused through `KnownResults` as today.
8. **As today.** The entry with the checks' lines, the one result commit on the branch, the push, the labels. The result commit holds exactly the taken files: a file a check made stays in its container.

A stall (steps 6 to 8 with a stall instead of a decision) changes nothing here: the taken files are committed with the stall entry, as today. The preflight's agent-run probe uses the same cycle. The host's git never runs inside the dataset: the container's `.git` is the agent's, to read history and diffs (the coder reads `git diff main`), and nothing the agent does to it can reach the factory's git.

**Where the factory runs.** As a systemd service on the VM, under the user `factory`, from its own virtual environment: `Restart=always` replaces Compose's restart policy, the health file stays as it is. `podman` runs rootless as that user; `--userns=keep-id` makes the container's user the host's `factory`, so the dataset's files have one owner. The ZFS operations the factory needs (`snapshot`, `destroy`, `rollback`, `diff`) are delegated to that user with `zfs allow`; where Linux refuses a delegated remount at the rollback, one `sudoers` line for exactly those four commands on exactly that dataset stands in (question 3). `/state` is a folder of the service on the host.

**The stage image.** Today's image without the factory: Python, uv, git, make, node, Claude Code and opencode, pinned as today. No second user, no `sudoers`, no entrypoint, no sealed folders. The agent files (`claude/agents`, `settings.json`) are copied into the image's `/etc/factory/claude` and the factory places them into `/work/home/.claude` before the base snapshot (step 3), so one run cannot widen the tools of the next. A project with another stack adds its toolchain to the image, as today.

**Stays unchanged** (the generic factory): `factory.domain` apart from `confinement` and `leftovers`; the application use cases of the tick, the watcher, the dispatcher, the claims, the opening, the stage protocol, the stalls, the decisions, the acceptance, the costs and bills, the hosting service, the known results, the stops and the health, the records, the write paths with their refusal rule; the adapters for git, the hosting service, the work item files, the pipeline definition, the records and logs; the entry points `factory-run`, `factory-watch`, `factory-bill`, `factory-health`, `factory-check-story`; the agent files, the forms, the documents' contracts.

**Goes** (the code that exists only for the long-lived container): the second user with `sudo`, the umask and the group (`CommandUser`, the `sudo` chain in `agent_launch`, `sudoers-factory-agent`, the users and modes of the Dockerfile, the `sudo:` line reading of both runtimes, the preflight item `agent-user`); the kernel's write guard (`factory-confine`, `factory.adapters.landlock`, `factory.domain.confinement`, the kernel's targets, the `tool_paths` of the pipeline definition, the `factory-confine:` line reading, the Landlock tests that need the real kernel); the undo (`UndoService`; the refusal rule stays, the take uses it); the leftovers program (`factory.entry.leftovers`, `factory.domain.leftovers`, the process table reading); the fresh home (`factory.entry.fresh_home`, `agent_home`, `home_files`, the `claude-home` volume); the removal of ignored files and of nested repositories, the seal of the checkout's `.git`, the re-clone rule and the restore's `remove_ignored`; the entrypoint and `compose.yml`; the decision-log entries and operator-guide sections that describe these, each closed by one line that says what replaced it. The inventory below gives the sizes.

**New** (small, behind interfaces with fakes, so that the suite runs on Windows and in `self` as today):
- `Snapshots` (application interface): `reset()` (rollback to the base), `advance()` (the base moves to the dataset's state), `changed_paths()` (what differs from the base). Adapter: `ZfsSnapshots(dataset)` over `zfs rollback -r`, `zfs destroy` + `zfs snapshot`, `zfs diff -H`. Fake: a folder copied and compared.
- `ContainerRuns` (application interface): `run(command, *, mounts, environment, time_limit, working_directory) -> ProcessResult`. Adapter: `PodmanRuns(image)` over `podman run --rm --userns=keep-id --timeout ...`. Fake: runs the command in a child process on the host, as `FakeAgentRuntime` does today.
- `StageEnvironment` (application): the cycle above as one object the stage protocol calls: `prepare(stage_start)` (steps 2 to 4), `run_agent(request)` (step 5), `take(stage_start, settings) -> TakeReport` (step 6), `run_command(command, time_limit)` (step 7, used by `ProjectCommands`). `TakeReport` replaces `UndoReport` with the same two lists, so the journal's sentence keeps its place.
- `make sync` as a fourth target of the project contract (`check`, `lint`, `test`, `sync`), in the template and in `factory/pipeline.yml`'s `project_commands` with a time limit.
- `vm/`: the machine's files: `setup.sh` (the pool on the data disk, the dataset, `zfs allow`, rootless podman, the service), `factory.service`, the stage image's Dockerfile (moved from `image/`), the operator guide's chapter "The machine".

**Removed more than added.** v1.1's layers are about 1,800 lines of source (of 19,000 under `src/factory`), 8,400 to 8,900 lines of tests, about 800 lines of documents and most of the image (the inventory at the end); the new parts are estimated at 600 to 900 lines of source with perhaps 1,500 lines of tests. The guiding principle of 2026-10-20 asks for exactly this measure, and the acceptance of the last feature reports it.

## The machine

- **Compute Engine**, x86, Ubuntu 24.04 LTS (its kernel ships the ZFS module; `apt install zfsutils-linux podman`), `e2-standard-2` (2 vCPU, 8 GB) at about $50 a month, or `e2-standard-4` at about $100; a 50 GB `pd-balanced` data disk for the pool at about $5. No inbound port; the operator connects with `gcloud compute ssh --tunnel-through-iap`. The VM gets no service account (or one with no rights), so the metadata server at `169.254.169.254` hands out nothing a container could use; the factory needs no Google API.
- **Not GCP-bound.** The same `vm/setup.sh` runs on any Ubuntu 24.04 with a spare disk: a Hyper-V VM at home, a VM on TrueNAS SCALE. What it needs is a Linux kernel with ZFS and rootless Podman, which `podman machine` and WSL2 do not give; the workplace's Podman Desktop is therefore not a host for v1.2 as it stands (question 7).
- **The secrets** stay files on the host, readable by `factory` only: the hosting token (never mounted into a container), the agent's login (mounted read-only into the agent's container as today). opencode works unchanged on the VM; its login, if ever an API key, is a file the same way.
- **The budget** is the human's: nothing is created on GCP before the human approves the machine, its size and a monthly cap.

Estimated size: about 25 stories and 4 acceptances; by v1.1's costs ($398 for 24 features, 191 runs) about $100 to $150 in agent runs, plus the machine's month.

## The measures (the guiding principle of 2026-10-20)

- **Simple:** moving parts of the cycle (target: podman, zfs, git, make; nothing else) and lines removed against added (target: at least three removed per one added).
- **Fast:** the start of a stage to the agent's first step with a warm base (target under 20 s; today about 10 s plus the home reset); the reset (target under 2 s); no `.venv` rebuild unless the lock changed.
- **Clean:** no stall reason and no stop reason left that names a layer; a stage's result commit holds only taken files.

## Risks, and what the first prototype measures

- **ZFS rights without root.** `zfs allow` delegates `snapshot`, `destroy` and `diff` cleanly; `rollback` of a mounted dataset may need the `mount` right, which Linux grants only partly to a user. The prototype's first hour: `zfs rollback -r` as `factory` on a mounted dataset with a container running on it before. Fallback: one `sudoers` line for the four commands on the one dataset (question 3). F0043's story 2 writes what was found.
- **Podman's `--timeout`** ends the container at the limit; the run's result must read that as `time_limit`, as the kill does today. Checked in F0042's story 3 on a recorder and in F0043's story 4 for real.
- **The resume after a provider limit** needs the session on the dataset's `home/`; the preflight's probe and `PatientRuns` are tested with the fake. A home on the dataset also means that an operator's `claude setup-token` runs outside the dataset: the login file stays a mounted host file, as today.
- **`zfs diff` and renames** report `R`; the take treats a rename as a deletion and an addition, as the undo does today.
- **The private repository** is reached only by the host; the container fetches from the host's git directory through a read-only mount. A rootless container cannot write a `:ro` bind mount; the mount is the whole protection, and F0042's story 3 pins it in the command line.
- **The agent's reach inside the container** is wide on purpose: it may fill the dataset, which the disk check sees (the dataset gets a `quota`), or run anything the image holds. What it cannot do is reach the token, the host, or the next stage.

## The human's decisions (2026-10-24, asked and answered in one sitting)

1. The factory runs directly on the VM as a systemd service under `factory`, rootless Podman, `zfs allow`.
2. The factory on the host pushes, from the files it takes; no container holds the hosting token.
3. `zfs allow` first; one `sudoers` line for the four `zfs` commands on the one dataset if the rollback needs it.
4. Landlock goes with the other layers.
5. The dataset holds a full clone, fetched from the host's repository through a read-only mount.
6. The machine's files live in a new top-level `vm/`, added to the coder's write paths.
7. One `Snapshots` adapter in v1.2, ZFS; the interface leaves room for another.
8. The instance on the VM is `vm` (the human's choice over the recommended `gcp`); `e2-standard-2`; `europe-west3` (Frankfurt); the budget alert's cap is $120 a month (room for an `e2-standard-4` later).
9. The build order is add, switch, remove: F0042 and F0043 by `self` on Docker with the inline fallback, the first VM stage, then F0044 and F0045 by `vm`.

The questions as they were asked follow, for the record.

1. **Where the factory process runs.** (a) *Recommended:* directly on the VM as a systemd service under `factory`, rootless podman and `zfs allow`; the fewest parts, and the host's git never meets a container's file system. (b) In its own long-lived container with the podman socket and `zfs` through `sudo`: one more container, a socket that is nearly root, no gain.
2. **Who pushes.** (a) *Recommended:* the factory on the host, from the files it takes; no container ever holds the hosting token (your design of 2026-10-20). (b) The stage container pushes with a token: simpler to describe, but the agent runs in that container.
3. **The ZFS rights.** (a) *Recommended:* `zfs allow` first; if the rollback needs root on Linux, one `sudoers` line for `zfs snapshot|destroy|rollback|diff` on the one dataset, checked by `visudo`. (b) The factory as root on the VM: no rights question, but a container escape is root. (c) Give up rootless podman too and run everything as root: the simplest machine, the weakest.
4. **Landlock.** (a) *Recommended:* it goes with the other layers (F0044 story 1); the container and the take are the guard, and the write paths keep their meaning through the take. (b) Keep `factory-confine` inside the stage container as a second fence: about 1,500 lines of code and tests stay, and the kernel ABI stays a requirement of the image's host.
5. **The agent's git.** (a) *Recommended:* the dataset holds a full clone fetched from the host's repository; the agents read history and diffs as today. (b) The dataset holds the work tree only: the coder's and reviewer's instructions change, and `git diff main` is gone.
6. **Where the machine's files live.** (a) *Recommended:* a new top-level `vm/` (`setup.sh`, `factory.service`, `Dockerfile`), added to the coder's write paths; `image/` goes with the Docker path. (b) Under `image/` as it is: no write-path change, a folder whose name no longer says what it holds.
7. **Portability beyond ZFS.** (a) *Recommended:* one `Snapshots` adapter in v1.2 (ZFS); the interface leaves room for btrfs or a copying adapter when a host without ZFS (the workplace) is wanted. (b) Build a second adapter in v1.2: more to test before the first proof.
8. **The instance on the VM.** Its name (`gcp`? `vm`? or `self` again once the Docker `self` is stopped), the machine type (`e2-standard-2` recommended for the start), the region, and the monthly cap for the budget alert. These need your word; nothing is created before it.
9. **The build order.** (a) *Recommended:* F0042 and F0043 by `self` on Docker, the first VM stage, then F0044 and F0045 by the VM instance. (b) Everything on `self`, the switch last: the removals would run on the very layers they remove.
