## Facts checked

- **The walk as built.** `_nested_repositories` is `os.walk(root, followlinks=False)`. It appends `here / ".git"` for every folder but the root that lists `.git` among its folders or files, then removes `.git` from `folders`, so it never enters the root's `.git` or a nested one. A symbolic link to a folder shows up in `folders` and is not entered. `remove_nested_repositories` removes each entry (`rmtree` for a real folder, `unlink` otherwise) and returns the relative paths sorted. The Interface's three rules and its "sorted" hold in the code.
- **The three texts.** `_early_stall` returns `("nested_repository", ", ".join(launched.nested_repositories))`, and `stall_cause` gives `the agent left a git repository in the work tree, which the factory removed: <detail>`. The probe's detail is `the probe run left a git repository in the work tree, which the factory removed: ` + `", ".join(...)`. The preparer's log line is `removed nested repositories: {', '.join(removed)}`. Each text keeps the order `remove_nested_repositories` returns. The Interface quotes all three correctly.
- **Criterion 1 (links).** The three drafted rows pass on today's code inside today's test body. The body already checks everything the criterion asks for: `removed == expected`, the snapshot of the whole `tmp_path` (the remote `origin`, the checkout and any target folder beside it) minus the removed paths, the root's `.git` and `resolve("HEAD")`. So "nothing outside the checkout changes" needs no new assertion. Against `followlinks=True` all three rows fail. The link to the root makes the walk find 41 paths (`self/.git`, `self/self/.git`, ...), and its removal deletes the root's own `.git`. **The rows kill the surviving mutant.**
- **Criterion 2 (`.git/extra/.git`).** It passes today. Against the no-pruning mutant it fails (the inner `.git` is removed). The mutant is killed.
- **Criterion 3 (`notes/.git/modules/m/.git`).** It passes today. Against the no-pruning mutant it fails: both paths are found, and the second removal raises `RepositoryUnsealed`. Killed.
- **Criterion 4 (sorted).** It passes today. The no-`sorted` mutant passes it too on NTFS, which lists folders by name. The walk's order is the file system's listing order, so "made in that order" pins the sorting only on a file system that lists `b` before `a`. Nothing pins `sorted` today either (the `two-levels` row finds `a/.git` before `a/b/.git`, which is already sorted). A row that pins it on every file system: a repository at `a` and another at `a/.cache`. The walk is top-down, so it always meets `a/.git` before `a/.cache/.git`. Sorted, `a/.cache/.git` comes first, because `.c` sorts before `.g`. Probed: walk order `['a/.git', 'a/.cache/.git']`, result `['a/.cache/.git', 'a/.git']`. The no-`sorted` mutant fails it (edit 2).
- **Criteria 5 to 7 (two paths).** The texts take the sorted list, so two repositories at `a` and `b` give `a/.git, b/.git` in each. Criterion 5's "contains" is right, because the note carries the marker. Each S0010 test removes one repository today. A second row or test is what kills the `", "` mutants.
- **Which tests change.** Criterion 1 says "new rows of the parametrized test of `remove_nested_repositories()`". That test is `test_remove_nested_repositories_removes_and_reports_each_nested_git_entry`, written by F0014-S0010's tester. Criteria 5 to 7 name no test. The natural homes of 6 and 7 are new rows of S0010's `test_a_probe_run_that_leaves_a_nested_repository_fails_the_item` and `test_the_preparer_removes_the_nested_repositories_of_a_kept_checkout`. Adding a row changes a test another story wrote. `CLAUDE.md` puts that under "Not without asking", and FEATURE decision 32 ends "Any other change to an earlier test is a question". No FEATURE decision gives S0011 the leave. Criterion 5 does not fit S0010's stage test as a row: that test is parametrized on `switched` only and asserts the one path `NESTED` throughout. So it is a new test function in the same module, reusing `_launch`, `_stalled` and `_note` from `application.test_after_agent` and the module's `_nesting` (edit 1).
- **Decision 31 and a link to a repository.** Today a symbolic link to a folder that holds a `.git` is kept, and so is the `.git` behind it. That is right, and the story should pin it (criterion 1 does). Git records a link as a link (mode `120000`) and never looks behind it, so neither `git status` nor `git add --all` starts a child git there. A repository inside the work tree behind such a link is found at its own path anyway. One outside the work tree is never read by the factory's git, and removing it would be a write outside the checkout. Removing the link itself would delete the agent's work, which the undo and the write paths judge like any other file. Only an entry named `.git` counts, a link included (S0010's `link-outside` row). **Recommended: a link to a nested repository does not count.** Edit 1's decision says so in one sentence.
- **Test data under the built code.** The `directory` fixture clones the `remote` fixture into `tmp_path / "checkout"`, so the checkout's parent is `tmp_path`. A link `deep/up` to it is inside the snapshot, and the snapshot's `os.walk` does not follow it. The fixture's teardown reopens only `closed` and `locked`, which no new row uses. pytest's cleanup does not follow links. The arrange functions are `Callable[[Path], None]` (`Arrange`) and pass `mypy --strict`. There are no secrets, no network, no sleep, and nothing outside `tmp_path`.
