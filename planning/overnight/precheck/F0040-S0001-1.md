**The real chain, real `sudo`, as `agent`** (the same prototype, `/usr/bin/sudo`, the agent run's environment):

- `check` passed. Its output tail was `sudo: unable to resolve host <id>: ...`, `agent`, `home=/home/agent token=unset`, `ls: cannot open directory '/home/factory/.secrets': Permission denied`, `check: green`. So the user switch closes the token's folder, as decision 1 says.
- `slow` with 3 s, refusal judged first (the order a coder reading the Interface top-down may pick): **`ProjectCommandError: /usr/bin/sudo refused the command: sudo: unable to resolve host ...`**. The killed command printed nothing but `sudo`'s warning, so "every non-blank line starts with `sudo:`" held and the kill was taken for a refusal. With the kill at the limit judged first: `time_limit None 0:00:03.0`.
- `os_user="nobody"`: `refused: /usr/bin/sudo refused the command: sudo: a password is required`.

`sudo` prints the host warning wherever the container's host name does not resolve (here because of `--network none`). The Interface does not order the two rules, so either order passes every criterion. Edit 1 orders them.

## Verdict

`F0040-S0001: accepted at intake; edit 1 required (a command killed at its limit is time_limit even when sudo printed a warning, so the kill is judged before the refusal); edit 2 required (the refused sudo executable with a user has no criterion).`

Edit 1 (required, *Interface*). Replace

```
- With `user`, a command with an exit status other than 0 whose output holds at least one non-blank line, every non-blank line starting with `sudo:`, raises `ProjectCommandError(command, "<sudo_executable> refused the command: <the last such line>")`. A `sudo:` line beside other output is output like any other line, and a status of 0 is never a refusal.
```

with

```
- With `user`, a command that the rule above does not judge `time_limit`, with an exit status other than 0 and whose output holds at least one non-blank line, every non-blank line starting with `sudo:`, raises `ProjectCommandError(command, "<sudo_executable> refused the command: <the last such line>")`. The kill at the limit is judged first: a command killed by its own `timeout` whose only output is a `sudo:` warning (`sudo: unable to resolve host x`) is `time_limit`, not a refusal. A `sudo:` line beside other output is output like any other line, and a status of 0 is never a refusal.
```

and in *Acceptance criteria* replace

```
4. The kill at the limit: a target `slow` whose recipe is `@sleep 60`, run with the stand-in `sudo` and `time_limit` 3 seconds, gives `status` `time_limit` and `exit_status` `None`, after at least 3 and less than 25 seconds.
```

with

```
4. The kill at the limit (rows of one parametrized test): a target `slow` whose recipe is `@sleep 60`, run with the stand-in `sudo` and `time_limit` 3 seconds, gives `status` `time_limit` and `exit_status` `None`, after at least 3 and less than 25 seconds; the same with a stand-in `sudo` that first writes `sudo: unable to resolve host x` to standard error and then runs what follows `--` gives `time_limit` too and raises nothing.
```

```

with

```
7. Before anything starts, with a `CommandUser`: `time_limit` 0 raises `ValueError`, and the command name `Check` raises `ProjectCommandError`, and the stand-in `sudo` records no call (rows of one parametrized test). A `CommandUser` whose `sudo_executable` does not exist raises `ProjectCommandError` whose `detail` starts with `[Errno 2] No such file or directory`.
