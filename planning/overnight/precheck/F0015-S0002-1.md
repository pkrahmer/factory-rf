- **The entrypoint's `exec`.** The last non-blank line of `image/entrypoint.sh` is `exec python -m factory.entry.run` today. The Dockerfile's `ENTRYPOINT ["/opt/factory/entrypoint.sh"]` is the exec form, so with `init: true` the chain is init → `/bin/sh entrypoint.sh` → `exec` → the factory's Python. The factory is the init's direct child. `tests/test_entrypoint.py::test_the_entrypoint_hands_over_to_the_run_module` already pins the arguments (`-m factory.entry.run`) through a stand-in, but not the `exec`. The new test adds that, so it is not a second copy.
- **Signals.** `factory.entry.run` installs handlers for `SIGTERM` and `SIGINT` (`src/factory/entry/run.py:64-70`). With the init forwarding `docker stop`'s `SIGTERM`, the factory stops as it does today as PID 1 with a handler. Nothing changes for the stop.
- **Why the zombies appear (finding 2).**
  - The factory runs `sudo -n -u agent -- timeout --signal=KILL …` (operator guide).
  - Unless it runs with `--foreground`, `timeout` makes itself the leader of its own process group. At the limit it sends the signal to its child and then to its own group, and `SIGKILL` cannot be caught, so `timeout` dies with it. This is consistent with the guide's "status 137" and the coreutils manual's note on `KILL`.
  - `claude` and its children die as orphans and are re-parented to PID 1, and the factory's Python waits only for `sudo`. The night log's 06:09 row observed `[claude] <defunct>` with parent 1.
  - Debian's `sudo` sets no child subreaper, as far as I know. The observation of parent 1 agrees.
  - An init as PID 1 reaps them, and touches no child the factory's `subprocess` waits for, because those are the factory's children, not the init's.
- **Does Docker Compose honour `init: true`?** Yes, from what I know: `init` is a service key of the Compose specification, and docker compose v2 passes it as the container's `HostConfig.Init`. Docker then mounts its `docker-init` (tini) at `/sbin/docker-init` and runs it as PID 1 with the entrypoint as its child. Docker Desktop ships `docker-init`. I did not run it here: there was no container runtime in this session, and none was allowed.
- **Does Podman with the docker-compose provider honour it?** Expected, but I cannot check it here. docker-compose talks to Podman's Docker-compatible API, which maps `HostConfig.Init` to Podman's `--init`. That runs `catatonit` (the `init_path` of `containers.conf`, normally `/usr/libexec/podman/catatonit`), mounted in the container at `/run/podman-init`. Two things this session cannot see:
  - whether the compatible API of the Podman machine in use (5.8.3) honours the flag;
  - whether `catatonit` is installed in that machine. If it is missing, `--init` makes the container fail to start instead of starting without an init.

  Both are first seen at the shakedown under Podman (point H1, edit E2).
