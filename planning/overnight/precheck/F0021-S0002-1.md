## The commits on `main` (the brief's particular check)

- Within one tick there is no collision: the publish pushes `main` before the evaluation, `git push` moves `origin/main` with it, and every later push of the tick (the archive after a merge, an acceptance's booking, a discard) checks out `main` at the new `origin/main` and fast-forwards. The rule never to push between a merge and its archive is the session's rule for its own planning pushes (`docs/runs/2026-10-12-overnight/night-log.md`, 2026-10-14 06:26, and `safe_to_push.sh`); the factory's own push comes before the archive in the same process and does not break it.
- The human's pushes to `main` (planning commits) can now be refused for a `stops recorded` commit the human has not fetched: pull before pushing. `safe_to_push.sh` should also fetch first. The publisher's own refused push (criterion 11) is a log line and a retry, as designed.
- A running story's branch merges `origin/main` at each stage start; a stops commit changes only `factory/stops.jsonl`, which no branch touches, so the merge is always clean. It adds a merge commit more often; the reviewer's diff (`':!factory'`), `make secrets` on a branch (files changed since the merge base) and `make mutants` (commit subjects `work item <feature>-S...`) are unaffected.
- `make secrets` on `main` reads every tracked file, `factory/stops.jsonl` included: event, scope, reason, a time and the instance name hold nothing detect-secrets flags; decision 2 keeps the detail out. Unaffected.
- The preflight: each stops commit is a new `origin/main`, so the next tick's preflight runs the `lint` probe again (decision 1 says so). And one effect decision 1 does not name: while `preflight_failed` stands, `_clear_stale_failing_stop` clears a standing `main_branch_failing` as soon as `origin/main` is no longer the failing commit. A stops commit is such a commit, so the factory's own record of `preflight_failed` clears `main_branch_failing` (and writes a `cleared` record for it) although `main` is still red; it is raised again only when the machine's items pass. See the feature's pre-check, point 3.

Refusal 3. A `GitError` from the publish is hard to provoke inside a whole tick with real git (the restore before it would fail first), and the drafted rule misses a third failure that is easy to provoke and would otherwise crash every tick: an `OSError` of the write (the human pushed a folder `factory/stops.jsonl/`; `show_file` then reads it as no file, and `write_text` raises `IsADirectoryError`). Replace the `Tick.run` paragraph of the Interface (this text also carries point 2 (b)) with:

```markdown
`factory.application.tick.Tick.run` (`application`): right after the restore succeeded (the checkout clean on `main` at `origin/main`), before the preflight, the tick calls `StopPublisher(boundaries).publish()`. A `GitError`, `PushFailed` or `OSError` from it writes `cannot publish the stop records: <error>` to the factory log, and the tick goes on as if it had published nothing. A tick that stops before the restore succeeds (`disk_low`, `fetch_failed`, `pipeline_definition_invalid`, `agent_definition_invalid`, `checkout_restore_failed`) publishes nothing; the records wait in the state directory for the next tick that gets past the restore.
```

and criterion 13 with:

```markdown
13. `Tick.run` when the publish fails, rows of one parametrized test: the publish's push is refused (a hook of the remote refuses `main`); `origin/main` holds a folder `factory/stops.jsonl/`, so that the write raises `OSError`. In both the factory log holds a line starting `cannot publish the stop records: `, the local records stay, and the tick still evaluates and dispatches its event.
14. `StopPublisher.publish` with a local record, on a checkout whose `origin/main` does not resolve (a bare remote with no `main`, fetched): it raises `GitError`, and the local record log holds the same records afterwards.
```

(The later criteria 14 to 20 become 15 to 21.)
