## Checked against the built code and tests

- **The cause (finding 3).** As the draft says:
  - `finish` builds `moved`, calls `_commit_and_push` (write the file, `git.commit`, `git.push`, `PushFailed` if not `pushed`) and then `set_labels`. It never calls `set_description`.
  - In `src/`, only `HandOverHandler._show` and `AcceptanceHandOver._show` call it.
  - The `hand_over` event comes from `_signal_of_observation` on a later tick: approval stage and `handed_over != stage`, checked before comments and asks.
  - After an active tick the scheduler pauses `FIRST_PAUSE` (15 s), then fetches and evaluates. That makes about 25 s, as observed.
  - Decision 8's gap for stories is the same code path.
- **The same text, before and after.**
  - The hand-over reads the document from `origin/<branch>` after `check_out` and the commits from `Git.log("origin/<branch>", since="origin/main")`, both before its own `handed over at` commit.
  - Right after the push, `HEAD` of the checkout is `origin/<branch>`, and the file on it is `moved` as written. So `Git.log("HEAD", since="origin/main")` before the push is the same list, and the document is the same unless the writer and reader's round trip changes a section's text.
  - `FrontmatterWorkItemWriter.render` strips the body after an empty line, but `section_text` and `entry_text` read inside the sections, so I expect equality. Criterion 3 ("the description is unchanged" after the hand-over) is the test that would show a difference. If it does, the coder can describe from the file it just wrote (`work_item_reader.read`) instead of `moved`. The Interface's "the document the result commit holds" allows that.
  - For an acceptance, `self._definition.stages[started.stage].role` is the acceptance stage's role, which is what `_reviewer_role` gives the hand-over.
- **Kill points.**
  - `GitCli.push` reaches `BEFORE_PUSH` once per push. A stage tick of a work item waiting unclaimed makes two pushes: the claim ("Nothing reaches the remote but the claim" before the run) and the result.
  - So `arm(BEFORE_PUSH, after=1)` kills the result push. `tests/test_fault_paths.py` arms `AFTER_PUSH, after=1` in the same situation for the same reason (`drive_to(world, work_item, "docs")`, killed "after move back push").
  - `InjectedKill` is a `BaseException`. The new `try` catches `HostingServiceError` only, so a kill passes through.
  - A kill before the result push now leaves the description showing the killed run's reports while the stage reruns. That is decision 7's stated cost, the same as for a failed push.
- **Fault paths and the error cap.**
  - The finisher's failure is logged and not counted: the dispatcher's count for the `run` event does not see it, and the hand-over's own count is unchanged.
  - `PyGithubHostingService` turns `GithubException` and `OSError` into `HostingServiceError` (`_failing_as`), and everything else "is a bug and passes through". So `HostingServiceError` is the whole contract of a failed `set_description`. "Every other exception propagates" adds nothing a test could pin (E2).
- **Which tests turn red.** The moved `fail_next` line in `test_hand_over_that_fails_every_time_is_reported_once_after_the_error_cap` is the only test the change turns red. Today its three injected failures meet three hand-over attempts. After the change the finisher's write would take the first one, and the error post would never come. With the line after the first `run_ticks(world)`, the finisher's write succeeds and the three failures meet the hand-over again. That is the same count and the same assertions as today. Every other test was checked against the change:

## Replacement texts

### E1 (recommended): a question writes no description either

In `## Interface`, in the first bullet, replace

```text
For every other move it writes no description.
```

with

```text
For every other move (a forward move, a rework, a question) it writes no description.
```

In `## Interface`, *Tests*, first test, replace

```text
three rows of (from stage, decision, written): `approval` (`smoke-test`, `approval`, true), `rework` (`smoke-test`, `doing`, false), `forward` (`review`, `docs`, false).
```

with

```text
four rows of (from stage, decision, written): `approval` (`smoke-test`, `approval`, true), `rework` (`smoke-test`, `doing`, false), `forward` (`review`, `docs`, false), `question` (`smoke-test`, `question`, false).
```

Replace criterion 2 with

```text
2. A stage that moves a work item anywhere else, or asks, writes no description: a rework from `smoke-test` to `doing`, a forward move from `review` to `docs` and a question at `smoke-test`, each killed at the result push, leave the description as it was before the tick. Rows `rework`, `forward` and `question` of the same test.
```

### E2 (recommended): no rule without a criterion

In `## Interface`, replace the first paragraph

```text
`src/factory/application/stage.py`, `StageFinisher`. Only the forward path of `finish` changes (the path that ends in a result commit); a stall (`_stall_red`) changes nothing.
```

with

```text
`src/factory/application/stage.py`, `StageFinisher`. Only the path of `finish` that ends in a result commit changes; `_stall_red` is not touched.
```

and in the third bullet, delete the sentence

```text
Every other exception propagates as today.
```

so that the bullet reads

```text
- A `HostingServiceError` from that `set_description` is caught: the finisher writes the line `pull request #<number>: description not written before the push: <error>` to `self._boundaries.log` (the `FactoryLog`) and goes on with the push and the label as today.
```
