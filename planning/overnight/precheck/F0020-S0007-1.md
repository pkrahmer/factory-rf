## The lease and the claim while waiting (the brief's question)

- **There is no lease renewal in v1.1.**
  - `lease_age` is measured from `claim.started_at`, which is set once, when the claim is made.
  - The coder's lease is exactly its time limit (40 minutes) plus its stage's check (15) and report (5): 60 minutes.
  - So any wait outlives the lease whenever the run uses its whole time limit, and a 10-minute wait outlives it once the run and its checks take more than 50 minutes.
  - At the ceiling, a stage can hold its claim for about 40 + 120 + 20 = 180 minutes.
- **The same instance never acts on its own expired lease.** `claim_status` returns `own` "whatever its age". Only another instance would see `expired` and take the stage over as an expiry. One repository has one instance (`self` builds factory-rf alone), so decision 14 is right.
  - The operator guide must say this, though, because it breaks the rule the pipeline loader checks (the lease outlasts the run and its checks). E2 adds that to the docs criterion.
- **A restart during a wait.** It is a crash of the instance's own claim, and the stage reruns at once. It counts toward `crash_cap` (2), not toward the attempts. Two restarts during waits ask the human.
- **A stop signal during a wait.**
  - `SleepingWaiter` sleeps with `time.sleep`, which a SIGTERM does not end (PEP 475). `docker stop` then kills the factory after its grace period, which a 40-minute agent run already does today. The restart is a crash rerun, as above.
  - Waiting on the run loop's stop event instead would wake on SIGTERM. But `PatientRuns` would then have to tell a stop from an elapsed wait, which is a second mechanism.
  - Recommended: **keep `time.sleep`** and name the behaviour in the operator guide (E2).
- **The stall past the ceiling.** It stalls `provider_limit` with one attempt counted, and the next tick retries the stage, which waits up to the ceiling again. At the attempts cap (2) the human is asked. That is about 4 to 5 hours of limits before a human hears, which fits "unattended" and decision 14.
- **The waits count toward no attempt and no cap.** That is true by design: one patient run is one result, so one attempt at most. The waits are not part of `time_limit`, because the time left sums only the calls' durations (criterion 5: 55 seconds after one call of 5 seconds).

## Checked against the built code and tests

- **The tick blocks during a wait.** No comment, merge or other work item is handled for up to two hours. That is the same as during a 40-minute agent run today, so no story needs to change it.
- **The cost record.** It is begun before and completed after the whole patient run (criterion 13), so a resumed run is one record. Its `cost_usd` is the joined result's sum.
- **Settings.** `ProviderLimit` gains the two durations in the domain, and `read_settings` adds the two variables. The "ceiling below the cool-down" rule raises `SettingsInvalid`, naming the ceiling's variable.
- **Size.** About 150 lines over eight modules and 18 criteria. Within one pass, but the test list is long.
