## Facts checked

### What git writes under `core.sharedRepository=0640` and `umask 002`, in a setgid parent

- **Clone honours the `GIT_CONFIG_*` pair.** `.git` and every folder in it are `2750`. `config`, `HEAD`, `index`, `description`, `info/exclude`, `packed-refs` and `logs/HEAD` are `640`.
- **Clone writes the setting into `.git/config`** (`sharedrepository = 0640` under `[core]`). So the operator's own `git` in the shell keeps the modes too. That is harmless, and it is useful for the morning observation.
- **Fetch, switch, commit, push, reset and clean, merge, `mv`, branch delete, prune, `gc`.** Everything they create follows `0640`: `ORIG_HEAD` is `640`, `logs/` and `refs/` folders are `2750`, packs are `440`. The exceptions are files git writes under the umask alone: `FETCH_HEAD` and `COMMIT_EDITMSG` (`664`), and during a conflict `MERGE_MSG`, `MERGE_HEAD`, `MERGE_MODE` and `AUTO_MERGE` (`664`, removed again by the abort). The Assignment's reading was right, and the conflict files are the same kind.
- **A clone by local path** (what the tests do with `clone` and `GitCli.clone(str(remote))`) leaves the loose-object folders `.git/objects/xx` at `2775`, because they are copied, not created through the setting. A `file://` or https clone (production) leaves none. `gc` repacks them away.
- **After a seal, git keeps the mode of a file it rewrites.** After a `chmod g-w,o-w` over `.git`, a later fetch and commit leave `FETCH_HEAD` and `COMMIT_EDITMSG` at `644`, so `find .git -perm /022` stays empty. Only a file git creates anew is group-writable again, until the next seal. That covers `FETCH_HEAD` after the first fetch of a fresh clone, and the merge files.
- **The work tree stays group-writable.** `checkout` is `2775`, `factory/` `2775`, `factory/pipeline.yml` and new files `664`.
- **The seal as drafted catches everything.** Every group- or others-writable entry is a regular file or a folder inside `.git`, and nothing is a symbolic link. After the emulated seal the count is `0`, at every point measured.
- **A refused write looks as drafted.** With the write bit off `.git`, `git config --local factory.sealcheck agent` prints `error: could not lock config file .git/config: Permission denied`. `touch` and `mv` print exactly the lines of the docs criterion.

### The swap that `check_seal` lets through (from the route analysis; confirmed)

`check_seal` reads only the root of `.git`. Suppose the agent renames a folder of the factory's that is not writable by the group into `checkout/.git` (the work tree's root is group-writable, so the rename is allowed). It passes: it is a directory, the factory's, with no `022`. If it is not a git repository, git's discovery goes on upward. I tested this with an empty `755` folder of my own as `checkout/.git` and a repository at `work/.git` whose config sets `core.fsmonitor`: the factory's `git status` in the checkout used `work/.git` and ran the command.

`/work` is `2775`, so the agent can put a folder there. To pass git's `dubious ownership` check it must be the factory's: one of the factory's group-writable work-tree folders, renamed to `/work/.git` and filled by the agent. With `GIT_CEILING_DIRECTORIES=<the checkout's parent>`, git stops and prints `fatal: not a git repository`.

A fresh `uv venv` under `umask 002` holds no folder without the group's write bit, so I found no such folder in today's checkout. The route depends on one existing, but the guarantee should not rest on that.

The ceiling alone turns the case into a standing `fetch_failed` stop: the check passes, so the checkout is never cloned again. The check therefore also needs to refuse a `.git` without a `HEAD` file, so that the checkout is cloned again.

### Hardening only, outside this story

- `clone` runs with `cwd` set to the checkout's parent (`/work`), which the agent can write. A ceiling does not stop discovery in the cwd itself (tested). Git reads only pager settings there early, and only on a terminal.
- `GitCli._environment` spreads `os.environ` first. The agent cannot set the factory's environment.

### A route this story does not close (for the route analysis and the human)

A nested repository in the work tree. The agent can make one with `uv run …`, which `claude/settings.json` allows, under any write path. The factory's own `commit` (`git add --all`) adds it as a gitlink, with only a warning. From then on the factory's `git status` and `git diff` start a `git status` inside it, and that child reads the nested repository's own `.git/config`.

Tested on git 2.39.5 with S0001's environment: the nested repository's `core.fsmonitor` ran as the factory's user, on `status` and on `diff`. `git clean -f -d` keeps a nested repository, so the restore does not remove it. `diff.ignoreSubmodules=all` did not stop it. A fourth pair, `core.fsmonitor=false`, did, because the child inherits the `GIT_CONFIG_*` pairs. A filter driver in the nested configuration did not run on `status` in my test, but I did not try every key.

Neither S0001 nor S0006 covers this. It is not a defect of this draft, but it contradicts the feature's goal ("a factory whose git cannot be made to run an agent's code").

## S0001 and S0006 together: can anything an agent writes in the checkout make the factory's git run a command as `factory`?

**No as drafted. Yes after three changes.** Real git 2.39.5 was used here (the image's pinned version). The S0006 probes ran in a scratch folder as one user, and another owner was stood in by the owner check of the code under test.

What S0001 and S0006 close, as drafted:
- **Hooks**, in `.git/hooks` or a `core.hooksPath` the agent writes into `.git/config`. S0001's `core.hooksPath=/dev/null` pair is command-line configuration and wins over the repository's file. Fifteen operations ran with all 28 hook names installed, and no hook ran.
- **`.git/config`** (`core.fsmonitor`, filter, diff and merge drivers, `diff.external`, `core.sshCommand`, `core.pager`, `include.path`), **`.git/info/attributes`**, `.git/info/exclude`, `objects/info/alternates`, `packed-refs`, `commondir`. Each one is written only inside `.git`, and after S0006 `.git` is `2750`/`640`, the factory's own. `seal()` runs before every agent run and takes the write bits git leaves (`FETCH_HEAD`, `COMMIT_EDITMSG`, `MERGE_*`, `AUTO_MERGE`, local-clone `objects/xx` at `2775`). So the agent cannot change anything in it while it runs.
- **A renamed `.git`.** The agent can rename it, because the root of the work tree is group-writable. In its place the agent can put:
  - a folder of its own: refused by `check_seal()`, wrong owner, and git's `dubious ownership` check refuses it too;
  - one of the factory's group-writable work-tree folders: refused, group-writable;
  - a symbolic link or a gitfile: refused, not a directory.

  No factory git command runs between an agent run and the check in `run_sealed`'s `finally`. `CostRecorder.complete` runs no git, and the stage's commit comes after. Nor does one run between the start of an iteration and `prepare`'s check.
- **`.gitattributes`, `.gitignore` and `.gitmodules` in the work tree.** They name no command git runs unless the configuration defines a driver or command, and only the factory writes the configuration now. The built-in drivers run nothing.

What stays open:
1. **A factory folder that is not group-writable, swapped in for `.git`** (S0006 pre-check, tested). `check_seal()` looks only at the root. An empty factory-owned `755` folder at `checkout/.git` passes it. Git ignores a `.git` that is not a repository and searches on upward to `/work` (`2775`, group-writable). There the agent can rename one of the factory's group-writable work-tree folders to `/work/.git` and fill it. That folder belongs to the factory, so the ownership check passes. Git then ran that repository's `core.fsmonitor`. No such folder exists in a fresh checkout today (a `uv venv` makes none), but the guarantee should not rest on that. Fix, in S0006 (its edits 1, 2 and 5): `GIT_CEILING_DIRECTORIES` set to the checkout's parent in `GitCli`'s environment, and `seal`/`check_seal` refuse a `.git` without a `HEAD` file.
2. **A nested repository in the work tree, committed by the factory as a gitlink** (S0006 pre-check, tested on 2.39.5 with S0001's environment). The agent makes a repository in any write path. If it rename-reuses one of the factory's group-writable folders as `sub/.git`, the folder is the factory's and passes `dubious ownership`. The factory's `commit` (`git add --all`) adds it as a gitlink, with only a warning.
