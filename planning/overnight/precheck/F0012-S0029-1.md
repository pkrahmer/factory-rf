## Facts checked

- **The branch half of `mutants` matches v1.1.** An acceptance's branch is `work-item/F0003-A0001` (`branch_name(acceptance_id(...))`), and the stage checks out the named branch, so `git rev-parse --abbrev-ref HEAD` gives it and the `sed` takes `F0003`. A story's branch `work-item/F0003-S0002` gives nothing, as criterion 10 says.
- **The subject half does not.** The template's `MUTATED` keeps the commits on `origin/main` whose subject starts with `work item <feature>-S<nnnn>:`. In a v1.1 project the commit that carries the coder's source is `doing ends: review` (`stage.py`), and the other commits on a story's branch are `<stage> starts as <instance>`, `<stage> ends: <next>` and `<stage> stalled`; none carries the id. The only `work item <id>: ...` commits are the handlers' and recovery's records, which change the work item and its cost records and never a module. So on a real v1.1 project `make mutants` on an acceptance's branch always prints `mutants: no module under src/<package> changed by F0003` and exits 0: the acceptance reviewer reports no mutants, and the todo run (which this template starts) measures nothing. Criterion 10 passes all the same, because its test writes its own commits with subjects v1.1 never writes. FEATURE decision 50's "its `mutants` reads v1.1's commit subjects (`work item <id>: ...`)" is wrong about the code. - A stall's commit (`src/factory/application/stalls.py`) is `commit_subject(<the context's work item>, f"{context.stage} stalled")`.
