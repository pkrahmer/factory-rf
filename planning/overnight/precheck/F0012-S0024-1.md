## Facts checked

- **The mechanism works as the Interface reads it.** `timeout` without `--foreground` kills its whole group at the limit, itself included, so the process the runtime started (the stand-in's `execvp` makes it `timeout`; in production `sudo`, which ends by the same signal) ends by `SIGKILL`: Python reports `-9`, a shell `137`. What the agent printed before the kill is kept. The draft's "137 or -9" covers both.
- **The stand-in finds `timeout`.** `SUDO_SCRIPT` runs with an empty environment; `os.execvp` then searches `os.defpath` (`/bin:/usr/bin`), where `timeout` is, as it finds `env` today. The sudoers rule allows any command as `agent`, and Debian's `secure_path` holds `/usr/bin`.
- **The inner limit is never below the limit.** Rounded up, `timeout` fires at `ceil(limit)` after its own start, so the call's `duration` is at least the limit whenever the inner kill fired. The rule "`137` or `-9` after at least its time limit" therefore holds for every inner kill.
- **`_sudo_refusal` must change**, as the Interface says: after an inner kill the reply printed before the wait parses and `timed_out` is false, so today's rule would return no refusal and `_result` would book a `completed` run. The existing timed-out test (1 s) becomes the inner-kill test once `timeout` is in the call; criterion 4 maps to it.
- **Four clauses have no criterion** (intake step 3):
  1. The grace: "The outer `ProcessRequest`'s `time_limit` is the call's time limit plus `SUDO_GRACE`." Criterion 2's "less than the 31 s" passes with or without the grace, because the inner kill fires first either way.
  2. The resume: "The resume of a budget stop goes through the same call, with what is left of the time limit as its limit." Criterion 6 names only the existing resume tests, which run without an `os_user`.
  3. The branches of the rule: criterion 3 has `137` before the limit (`died`) and a death by `SIGKILL` after it (`time_limit`, which is `-9`). `137` after the limit, `-9` before it, another status after it, and the same status without an `os_user` (the rule is for calls with one) have no row. With real processes `137` after the limit cannot be made reliably (the inner kill comes first), so these rows need the process result itself.
  4. Criterion 5's "its process request's time limit is the request's time limit" cannot be observed through the stand-ins: the process request is private to the runtime.
- **One way covers 1, 3 and 4 deterministically**: replace `run_process` of `factory.adapters.claude_runtime` through `monkeypatch` with a recorder that keeps each `ProcessRequest` and returns a given `ProcessResult` (the module imports `run_process` by name). `run_process` is a dependency of the code under test, not the code under test, and `tests/adapters/test_git_cli_arguments.py` replaces a module function the same way. ## Points for the human

1. **Testing through a recorder of `run_process`.** Recommended: yes (edit 1); it is the only deterministic way to the outer limit and to `137` after the limit.
2. **A harmless `sudo:` line at a time limit.** Today's rule (F0010-S0022, kept by the draft's criterion 4) makes a run that reaches its limit while `sudo` printed `sudo: unable to resolve host x` an `AgentRuntimeError`. That rule was kept partly because the kill under `sudo` was not enforced; now it is, so every time-limited run on a machine whose `/etc/hosts` lacks the host name would take the error path. Recommended: keep the rule (Docker writes the container's host name into `/etc/hosts`, and a real refusal hidden as `time_limit` would be worse); look for the line at step 3's morning observation.
3. **What `timeout` does not reach.** It kills its own process group. A process the agent starts in a new session or group (a detached server) survives the kill. Recommended: accept; the morning observation (`ps` after the limit) shows it.
