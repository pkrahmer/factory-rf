## The seven points against the built code

1. **The summaries.** True. `README.md:3` says "nothing starts a stage before F0006", and the operator guide's opening (`:3`) names no evaluation, tick, dispatcher or run handler and says "there is nothing else to start". `factory-run` and `factory-health` are declared in `pyproject.toml`, and `src/factory/entry/` has no `run.py` or `health.py`. Run on the host, both end with exit 1 and `ModuleNotFoundError: No module named 'factory.entry.run'` (resp. `'factory.entry.health'`). `factory-watch` ends with exit 2 and `factory-watch: no instance settings are wired yet`. F0010-S0004 and F0010-S0006 build the two modules, so "until F0010" holds. `README.md:12` already names the four commands that exist.
2. **The way out of an unreadable file.** True. `RemoteWorkItems.read` builds a snapshot of every story in `in-progress/` on `origin/main` (`work_items.py:51-57`) before the watcher looks up any pull request, and `_branch_document` and `_started_document` raise `WorkItemFormatError`. The project guide says the tick does not catch it (`project-guide.md:547`). Closing the pull request changes nothing that `read` looks at. Both named ways out work:
   - repairing the file on its branch, or on `main` for a story without a branch;
   - moving the story out of `in-progress/`.
3. **`reject` is not "only recorded".** True. `reject` is in `NOT_YET_HANDLED` (`wiring.py:34-46`). The evaluation returns it in tier 1 for the first illegal change, every tick (`evaluation.py:90-96`), so after three errors it is reported once and then answered `capped`, and no other work item runs. One detail the criterion's "until a push" does not say: a push only retries. If the newest commit beyond `origin/main` that touched the story's file is still the illegal change, the `reject` returns and is reported again after three more ticks.
4. **The kinds without a handler.** True for the three named kinds, but the list is short of the ones an operator meets most:
   - **`ask`.** An agent's `question` sets `blocked` (`decisions.py:91-93`). While no handler posts the question, `question_posted` is false and the waiting work item gives `ask` (`evaluation.py:202-203`). That is a counted error that caps and holds back all new work, after the first question of any stage. The attempts cap's `ask` is point 6.
   - **`comment`.** The human's answer on that pull request gives `comment` (`evaluation.py:195-201`), which is unhandled too. It shares the report key of its work item and remote state, so it ends without a second post.
   - **`hand_over` and `merged`.** `hand_over` arises at an approval stage whose pull request is open. `merged` arises only for the first waiting work item, which is in practice the one at the approval.
   - **`crash`.** `crash` follows any own claim left on the remote. That includes a rejected result push, every boundary error after the stage-start commit (F0005 decision 8), and a restart after the process died during a stage. The criterion names only "after a rejected result push".
5. **`StopService.post` is called.** True: `Dispatcher._report` calls it (`dispatcher.py:97`), and `StopService.post` opens a draft when no pull request is recorded and none is open on the branch (`stops.py:191-205`). One more sentence of the same section goes stale with it. `operator-guide.md:81` says "The factory records the pull request's number in the work item's state when it opened or found the pull request". The dispatcher does not record it (F0006 decision 9; acceptance, section 4, S0003 reviewer). A later stop finds the draft by its branch (`stops.py:200-202`). Neither the Assignment nor the criterion names this line.
6. **The attempts cap.** True: `_new_work` returns `ask` with the detail `attempts cap` at `attempts >= attempts_cap` (`evaluation.py:229-230`), and `ask` is unhandled. Both stale places are `operator-guide.md:108` ("the evaluation arrives with F0006") and `:131` ("F0006's evaluation, F0007's question").
7. **A branch made by hand.** True for the stage the branch starts with, but "never judged" overstates it. The probe pushed a first commit at `stage: approval` on a hand-made `work-item/F0001-S0001`, and `last_stage_change` gave `None`. A second hand commit, approval to intake, gave `from_stage='approval' to_stage='intake' correction=False`, so it is judged. The rule (`work_items.py:66-80`) skips only a commit whose parent is on `origin/main` or whose previous version has no readable state. Later changes on such a branch are judged as on any other. The acceptance's item A is documented as today's behaviour, as the brief asks. No F0007 to F0011 draft changes the opening-commit rule: F0007-S0006 keeps it, and its tests push a legal commit first.
