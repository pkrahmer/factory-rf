## What I ran

**Form check.** `factory-check-story` (`python -m factory.entry.check_story`, on a copy): `ok`, exit 0.

**Code facts on today's `main`.**

- The test is `tests/entry/test_watch.py:286-294`, `test_no_source_file_knows_the_follow_mode(text: bytes)`, rows `--follow` and `factory-last-line`. It lists `SRC.rglob("*")` at line 290 and leaves out the files that `_names_the_replaced_phrases(path)` (lines 279-283) names: `SRC / "domain" / "documents.py"` and the files of `domain/__pycache__/` whose names start with `documents.`. `SRC` is `Path(factory.__file__).parent` (`tests/source_search.py:8`). F0006-S0006 wrote the test; F0011-S0005 added the exception (F0011 decision 21). The module holds 14 tests today (12 apart from the two rows).
- Under `src/` only `domain/documents.py:24-25` holds the two phrases (and its bytecode, where one exists). No other test scans `src/factory` with `rglob("*")`; `source_search.modules()` and the others read `*.py`.
- Python 3.12's `rglob` ignores every `OSError` on a folder (a folder it cannot list is skipped). So the scan can fail in only two ways: a file holds a phrase, or `read_bytes` raises.
- `make test` (`Makefile:78`) runs `pytest -q --tb=short -n auto --dist load --cov --cov-report=term-missing:skip-covered`. The image sets `PYTHONDONTWRITEBYTECODE=1` for every process (`image/Dockerfile:66`). The factory's project commands inherit it (`make_commands._environment`), and so do the agents' runs (the runtimes' switches). So neither user's own pytest writes bytecode.

**The cause, traced.** Exactly one test starts a Python that imports `factory` with the switch dropped: `tests/test_tests_umask.py::test_the_tests_umask_holds_whatever_umask_pytest_was_started_under` (F0033-S0001, on `main` since 2026-10-20 05:15, a few hours before S0002). Each of its four rows runs `sh -c 'umask <row>; exec python -m pytest ...'` in the real checkout. The child's environment holds only `PATH`, `HOME` and `TMPDIR` (lines 52-56). The child's `conftest.py` imports most of the package, so it writes 113 bytecode files under `src/factory/**/__pycache__/`, before `pytest_configure` sets the tests' umask. The row `077` writes them with mode `0600`. The four rows run at the same time on different workers, so which mode each file ends with depends on which row wrote it last. The other test children either keep `os.environ` or import only the standard library.

On `self`, the coder's `make check` runs as `agent` and the factory's runs as `factory`, in one checkout shared through the group `factory-work` (`/work` is `2775`). A `0600` file of one user cannot be read by the other, and `read_bytes` raises `PermissionError`. Both rows fail, because the same file stays unreadable for both. Python itself does not mind: it compiles again and replaces the file. That is why the next check of the same user passes, and why the failure moves between the users.

This fits S0002:
- The factory's check (entry 16) ran right after the coder's checks as `agent` and failed.
- The coder's first check (entry 15) came after the factory's check of the tester's stage, and failed too.
- The coder's reruns passed.

The cause is not a race of writes, as the story guesses, and no phrase was ever found.

**Reproduced.** I ran this in throwaway containers of `factory-self-factory` (`--network none --cpus 1`), on a copy of the tracked tree under `Temp/pc41` without `image/`. I used the image's `/opt/factory/.venv` Python. From the host I took only pure-Python packages (`pytest`, `_pytest`, `pluggy`, `iniconfig`, `packaging`, `py.py`, `pygments`, `xdist`, `execnet`), because the image has no pytest. For the shared checkout I used a group-writable copy with setgid folders, owned by `factory:factory-work`, as `/work` is. As `root` in that throwaway container I added one `.pth` file to the image's venv, so that the child `pytest` (which drops `PYTHONPATH`) finds the copy and pytest. `ruff` and `mypy` are not in the image, and I did not run them.

- Today's code, `agent` runs `pytest -n 4 tests/test_tests_umask.py` (`5 passed`). Then `factory` runs the follow-mode test. Three rounds: 39, 29 and 29 of 113 bytecode files are `0600` and owned by `agent`. Every round printed `2 failed, 12 deselected` with:
  ```
  E   PermissionError: [Errno 13] Permission denied: '/w/src/factory/entry/__pycache__/wiring.cpython-312.pyc'
  ```
  (in the other rounds, `application/__pycache__/preflight.cpython-312.pyc`, `costs.` or `watcher.`). In an earlier run the third round passed (`0 of 113` were `0600`): that is the flake.
- The same steps with a prototype of the story's test (`rglob("*.py")`): `2 passed, 17 deselected` in all three rounds, with 25, 24 and 1 unreadable files in place. **The story's change removes the failure.**
- The same steps with today's test, but with `"PYTHONDONTWRITEBYTECODE": "1"` added to the child's environment in `test_tests_umask.py`: no bytecode file under `src/` at all, and `2 passed, 12 deselected` in all three rounds. **That removes the cause.**
- Without the second user (one user, the copy on the container's overlay filesystem), I ran 1,200 to 1,700 scans with `rglob("*")` while children rewrote the bytecode. None of them raised. On a Windows bind mount one scan in 16 raised `FileNotFoundError`. So a race of writes is possible but rare. It does not explain two failed rows, twice.
- **Beyond this story:** after the `agent`'s children, `git clean -ffdX src` as `factory` exited 1 in every round, with 11 to 102 `Permission denied`. The agent's `__pycache__` folders (6, written under `022` or `077`) cannot be changed by `factory`. With the switch in the child's environment it exited 0. F0027-S0003 ("the factory removes the git-ignored files after every agent run") does exactly this removal, as the factory. F0027's decision 19 and its pre-checks found the same problem for `python -I` children, but not for this child. See point 2.

**Smoke blocks.**

- With the prototype, run as `factory` and as `root`: block 1 printed `7 passed, 12 deselected` and block 2 printed `0`, exactly as `Expect:` says.

I recommend `docs: none` with a true reason: that entry is the record of F0011 decision 21, and F0041 keeps older entries as history. That is edit 5. A line in the decision log for a test detail would cost a documenter run for little gain.

**Clashes.** No story or draft names `test_no_source_file_knows_the_follow_mode` or `test_tests_umask.py`. F0039-S0002 and S0003 (drafts in `planning/overnight/stories/`) touch other parts of `tests/entry/test_watch.py`. No conflict.

**The stall's output and the `E` lines (acceptance point 4).**
- The stall entry keeps the last `STALL_TAIL_LINES = 15` lines (`src/factory/application/stage.py:38`) of the check's 30-line tail (`OUTPUT_TAIL_LINES`, `src/factory/domain/checks.py:12`).
- In `make test` the coverage table follows the failures, so those 15 lines start inside the table. In my reproduction the `E` line stood four lines above the short summary.
- The summary's `FAILED` lines lose their ` - PermissionError: ...` part, because pytest cuts them to the 80 columns of a non-terminal. With `COLUMNS=200` they carried the error.

**My recommendation: this does not belong in this story.** It is the factory's record of a red check (a change under `src/`, the coder's), or the human's `Makefile`, while this story changes tests only, under a tests-only leave. It is also tool-neutral code (R8), where picking pytest's `E` lines would not fit. The cheapest fix is the human's: `COLUMNS=200` before `uv run pytest` in the `test` recipe, so every `FAILED` line in the tail names its error. A factory story to keep more of the tail is the other way. Point 3 leaves the choice to the human.

2. **The cause itself (story edits 7 to 10, feature edit B).** The story's change ends the flaky failure, but the umask test's child still writes bytecode into `src/` as whichever user runs `make check`. That stops F0027-S0003's removal of ignored files (`git clean -ffdX` as `factory` exits 1 after an `agent`'s check, reproduced). It also breaks any later scan that reads non-source files. One line in that test's child environment removes it: `"PYTHONDONTWRITEBYTECODE": "1"`, the switch every other process already has.
   - A: both changes in this story (recommended). They have the same cause, both are test-only, both need a leave of the same kind, and the story stays small.
   - B: only the scan here, and the switch in F0027-S0003 (its refiner must then add the leave for an F0033 test).
   - C: only the switch, and no change to the scan. It removes the cause, but the scan stays brittle against any unreadable non-source file.
3. **The `E` lines in the stall's output.** Not in this story (see above). I recommend the human's one-line `Makefile` change (`COLUMNS=200` in the `test` recipe) as the cheapest fix. Otherwise, a later factory story can keep more of the tail.
