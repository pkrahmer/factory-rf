## Is the token out of the agent's reach? (S0001 with S0002)

- **The direct read: yes, on all three runtimes.** The folder is made in the image layer as `factory:factory`, `0700`; the runtime creates the file's mount point inside it and leaves the folder's owner and mode as built. The agent (uid 1001, group `factory-work`, not in `factory`) cannot traverse it, whatever the file shows: on Docker Desktop and Podman on Windows the bind mount shows `0777`, owner 0 (probe); on Linux Docker the host's owner and mode; on rootless Podman the folder's owner is a sub-uid on the host and 1000 inside, and the agent's uid maps to another sub-uid, so the same permission check holds. `/proc/<pid>/root`, `/environ` and `/mem` of the factory's processes need the factory's uid. The agent's environment carries no token (allow list of six names), and its git gets nothing from the helper (`[ -r ]` fails).
- **What still reaches it.** (1) Code the factory's user runs from the shared checkout: the project commands, already left for v2 (decision of 2026-10-14); and git's hooks and configuration in `/work/.git`, which the decision does not name. The agent can write files there through `uv run python ...` (allowed in `claude/settings.json`); `git_environment()` sets no `core.hooksPath`; `/work` is `2775` and the factory runs with umask `002`. A hook the agent drops into `.git/hooks` runs as `factory` at the factory's next checkout and can read the file. Same class as the project commands, not something this story can close. (2) On the host: anyone who can read `image/secrets/hosting-token`, or who can run `docker`/`podman exec` as another user.
- **Only the morning observation proves it in a running container** (FEATURE, Out of scope): S0001's docs criterion carries it.
