## Facts checked

- **The agent's git reads `/etc/gitconfig`.** `GIT_CONFIG_NOSYSTEM=1` lives only in `GitCli`'s per-call environment (and in the test helpers), never in the factory's process environment. The agent run's environment is `scrub_environment` (six names) plus `SWITCHES` (three names), passed through `env -i`, so neither `GIT_CONFIG_NOSYSTEM` nor any `GIT_CONFIG_*` reaches the agent. Its git, and the git Claude Code's shell tool starts, read the system file. The Assignment's claim holds.
- **`safe.directory` semantics on 2.39.5** (probe 1):
  - The file as the Interface gives it lists as exactly `safe.directory=/work/checkout`; `--get-all safe.directory` prints `/work/checkout`.
  - Trusted with the exact work-tree path. Refused (`detected dubious ownership`) with a trailing slash, with `<path>/.git`, with the parent folder and with another path; `*` trusts it. So the value must be the work tree's path exactly, and criterion 2's tie to `CHECKOUT_PATH` is the right guard.
  - Trusted from a subfolder and through `git -C`; `git log` and `git diff` work.
  - With `GIT_CONFIG_NOSYSTEM=1` the same system file is ignored and the repository is refused: the factory's own git is unaffected, as the Assignment says.
  - A `safe.directory` in the repository's own `.git/config` is ignored (git honours it only in system, global and command-line configuration), so the agent cannot trust a repository for itself from inside one.
  - A CRLF copy of the file: `git config --file --list` prints the value without `\r`, and the CRLF file as system configuration still trusts the repository. The `sed` in the Dockerfile is harmless and consistent with the other copied files; criterion 1 cannot tell a CRLF file from an LF one, which is fine.
- **S0006's `0640`: a `.git` the agent cannot write** (probe 2, the owner's write bits removed from `.git` and every entry, a changed file with an old mtime so that `status` wants to refresh the index): `git status --short` prints ` M a.txt` and `?? untracked.txt`, exit 0; `git status`, `git diff --stat` and `git log` exit 0; no `index.lock` is left. Git's opportunistic index refresh skips the write silently when it cannot take the lock. A write (`git add`) fails with `Unable to create '.../index.lock': Permission denied`, as S0006 intends. So read access through the group is enough for everything the story promises.
- **The test's own git call inside an other-owned checkout** (probe 3): `git config --file <file> --list` with `GIT_CONFIG_NOSYSTEM=1` (as `run_git` sets it) succeeds with the current folder inside a repository of another owner, from its root and from a subfolder.
