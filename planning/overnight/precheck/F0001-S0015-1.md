## Facts checked

- Every named operation exists with that signature in `src/factory/adapters/git_cli.py`: `resolve(ref)`, `show_file(ref, path)`, `list_files(ref, directory)`, `is_ancestor(ancestor, descendant)`, `log(ref, *, since=None, path=None)`, `changed_paths(since)`, `clone(url)`, `checkout(branch, *, start_point=None)`, `push(branch)`, `delete_remote_branch(branch)`, `delete_branch(branch)`, `merge(ref, *, fast_forward_only=False)`, `reset_to(ref)`, `revert_paths(commit, paths)`. `check_repository_path` is in `src/factory/domain/git.py`, where the new function goes.
- `merge`, `reset_to` and `revert_paths` call `resolve` first (`_resolve_or_raise`), so a check in `resolve` covers them before git starts. `delete_branch` calls `resolve(f"refs/heads/{branch}")`, which does not start with `-`, so it needs its own check before that call. `clone` creates the parent before git runs, so the check must come first. That is all inside the coder's change.
- Stand-in: `GitOptions(executable=...)` exists, and `tests/git_support.write_executable(directory, body) -> Path` exists as named. `tests/adapters/test_git_cli_reading.py` already uses both together.
- `BEFORE_PUSH` can be observed: `KillPoints.reached(point)` counts every reach, armed or not, and the `checkout` fixture is built with the test's `kill_points`. The test asserts `kill_points.reached(KillPoint.BEFORE_PUSH) == 0`.
- `LC_ALL=C` fits the code as it is. `_environment()` builds `{**os.environ, **options.environment, identity…, GIT_CONFIG_NOSYSTEM, GIT_CONFIG_GLOBAL}`, so one more key at the end is "after the process environment and `options.environment`".
- `LC_ALL=C` and paths: `run_process` decodes with `.decode("utf-8", errors="replace")` itself, whatever the child's locale. Git's `-z` listings write paths verbatim. The text of `log` follows `i18n.logOutputEncoding`, which defaults to UTF-8, not to the locale. On the host, `status --porcelain=v2 -z`, `ls-tree -z` and `log -z --format=%an%x00%B` printed the same bytes for `dätè.txt`, an author `Ä` and a subject `Größe` with and without `LC_ALL=C`. GNU gettext ignores `LANGUAGE` when the locale is `C`, so `LC_ALL=C` alone is enough.
- No existing test passes an empty or `-`-led value to any of these operations, so no test written by another story changes.
- The `human` fixture is a `HumanClone`, not a `GitCli`. `push_file("main", path, text)` makes it the writer of a diverged `main`. It does not return the commit id, so the test reads the id with `run_git` in `tmp_path / "human"`. That is possible, just one line more.
- Demo, run on the host against today's code with only the `try` line changed to print the result: `rejected`, then `force: pushed`, then `['diverged', 'one']`. That reproduces the acceptance finding. The default identity committed without any global configuration. The clone of the empty bare remote was on `main`, so `a.push('main')` and `b.push('main')` succeeded. `log` returns `CommitInfo` objects with `subject`, and `--date-order` puts the child `human` before `one`. Once `push('--force')` raises `ValueError`, the three lines are exactly `rejected`, `refused` and `['human', 'one']`.
- On `--end-of-options`: on git 2.48, `reset --hard --end-of-options <ref> --`, `switch`, `ls-tree`, `merge-base` and `rev-parse` all accept the marker. The draft's "`git reset` refuses that marker after `--hard`" is the container's git 2.39, as the comment at `git_cli.py:304` records. The support depends on the git version, which is one more reason for a rule in the domain.
- Write paths: `src/factory/domain/git.py` and `src/factory/adapters/git_cli.py` (coder); `tests/domain/test_git.py` (a new function) and `tests/adapters/test_git_cli_arguments.py` (new) (tester); `docs/project-guide.md` and `docs/decisions.md` (documenter). ## Intake

`question`

1. The Assignment rejects passing the values after `--end-of-options` "for now, for the human to confirm". Is refusing every option-like value with `ValueError` before git runs the decision (option a, which the story builds), or should the values go after `--end-of-options` and `--` where git takes them (option b, which would change criteria 3 to 8 and the docs criterion)? I would choose (a).
2. The Assignment asks the human to confirm that `LC_ALL=C` does not change how the wrapper reads paths. Is `LC_ALL=C` on every git call confirmed? Criterion 10 and the docs criterion depend on it.

Had both been settled in the story, intake would accept:

- Interface: `check_git_argument(value: str) -> None` in `factory.domain.git`, beside `check_repository_path`. The list of operations and positions matches the methods of `GitCli`. The tests and fixtures are named.
- Criteria: each one can be tested by one function. The rule's failing sides are covered: empty and `-` refused (c1), refused before git and before `BEFORE_PUSH` with nothing changed (c3 to c8). Its passing sides are c2 and c9. `LC_ALL` cannot be lifted (c10).
- Demo: runnable. The `Expect:` line gives three exact lines.
- Architecture: the rule is pure, so it is domain. The wrapper calls it, and no new module or dependency is added.
- Scope: R9 and FEATURE.md decision 10. Listed in FEATURE.md as S0015, and outside nothing in "Out of scope".
