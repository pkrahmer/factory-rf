## What I ran

**Smoke test block 1 on today's code** prints `refused False` three times. That is today's `unknown key: kept_ignored`; its base definition alone loads. On a prototype of the field it gives the expected three lines (`tool_path_folder` and the `~/` rule refuse exactly the patterns criterion 1 names).

**`GitCli.remove_ignored(kept)` as the Interface draws it.** I built a prototype that lists with `git ls-files -z --others --ignored --exclude-standard --directory`, leaves out what lies at or beneath a kept folder by segments, and runs one `git --literal-pathspecs clean --quiet --force --force -d -X -- <entries>`. I ran it in a throwaway container of v1.1's image (git 2.39.5).

- Block 2 prints `['.gitignore', 'mutants/src/mod.py']`, as expected.
- Criterion 3's first row fails: with the stand-ins `.venv/lib/standin.pth`, `mutants/src/mod.py`, `mutants-old/x`, `run.log` and `[a].log` and `kept=["mutants"]`, `mutants/src/mod.py` is removed too.

I reduced it with `git clean -n`. Git 2.39.5 removes `mutants/` whenever the pathspecs hold `mutants-old/` together with any second pathspec, literal or not (`mutants-old/ run.log`, `.venv/ mutants-old/`, `[a].log mutants-old/`). Alone, `mutants-old/` removes only itself. `mut/` beside `.venv/` does not trigger it.

So the listing approach is unsound in the image's git. A kept folder is lost as soon as an ignored sibling's name starts with its own and one more ignored entry exists. The coder cannot make criterion 3 pass with the Interface as written, and asks.

**What works:** negated exclude patterns, one call. On the same tree, `git clean -ffdX -e '!/mutants/' -e '!/mutants/**'` removes `.venv/`, `[a].log`, `mutants-old/` and `run.log`, and keeps `mutants/`, a `mutants/run.log` that `*.log` matches included.

- `-e '!/a/b/' -e '!/a/b/**'` with `a/` ignored removes `a/` whole. Git does not re-include beneath an excluded folder, which is exactly the story's rule for a kept folder inside a larger entry.
- A kept folder that no rule ignores, or that does not exist, changes nothing.
- An untracked, not-ignored `notignored/x` stays.
- It is one `git clean`, with no listing and no pathspecs, so neither the literal-pathspec point nor the git fault above arises.

Decision 13's finding that an exclude *pathspec* (`':(exclude)mutants'`) does not work stands; `-e` is a different mechanism.

**mutmut and `mutants/`.** mutmut 3.8 runs every test with its working directory in `mutants/` (`change_cwd("mutants")` in `runners/harness.py`). It puts `mutants/src` first on `sys.path` (`setup_source_paths`). It copies a source file into `mutants/` only when the copy does not exist yet (`copy_src_dir`, `if target_path.exists(): continue`). It copies `tests/` over `mutants/tests` with `copytree(..., dirs_exist_ok=True)`, which leaves extra files in place. So a kept `mutants/` holds code that is not in git and that the next `mutmut run` executes: a `conftest.py` an agent left in `mutants/tests/`, or a module it changed in `mutants/src/`. Under F0024 that run is the factory's own `mutants` report after the coder, as the factory's user. See the feature's point 2.

Edit 1 (required, Interface, `factory.application.git` and `factory.adapters.git_cli`): replace the bullet that starts "With `kept` not empty, `GitCli` lists the ignored entries" with

```markdown
- With `kept` not empty, `GitCli` runs one `git clean --quiet --force --force -d -X -e !/<folder>/ -e !/<folder>/** ...`, two negated patterns for each kept folder in the order given. A kept folder is then not ignored and neither is what it holds, so `-X` keeps it whole, also a file in it that another rule matches (`mutants/run.log` with `*.log`). Every other ignored entry is removed, `mutants-old/` beside a kept `mutants` included. A kept folder inside a larger ignored entry is removed with that entry, because git does not re-include a path beneath an excluded folder. A kept folder that no rule ignores, or that does not exist, changes nothing. The command of a fault is that command line.
```

The replaced bullet is the one that holds the listing, the literal pathspecs and "With no entry left, it runs no `clean`", so intake question 1 falls away with it. In the Description, "The removal keeps every ignored entry that is a kept folder or lies beneath one." stays true.
