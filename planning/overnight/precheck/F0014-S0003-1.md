## Points for the human, with the recommended answers

1. **FEATURE decision 9's reading of your words.** Your answer (`briefs/draft-F0014.md`, item 3) says "through the runtime's environment (the allow list gains that one name only for agent runs; ...)". The draft keeps `ALLOWED_ENVIRONMENT_NAMES` at six names and adds `CLAUDE_CODE_OAUTH_TOKEN` in the adapter, from the file only, dropping one that comes in a request. That honours "only for agent runs" more strictly than the allow list could, because the allow list filters the factory's own environment, where the token never is. **Recommended: confirm the draft's reading.**
2. **The token on the `sudo` command line (decision 11) is visible beyond the container.** On a Linux host (Docker Engine, rootless Podman) any host user can read the arguments of `sudo` and `timeout` while a run lasts (`ps`, `/proc/<pid>/cmdline`, unless `hidepid`). Under Docker Desktop or the Podman machine on Windows, only the VM can. Options:
   - (a) Keep the draft and say so in the guide and the decision log: a Linux host shared with other users exposes the token during runs, and `hidepid=2` on the host's `/proc` closes it.
   - (b) Decision 11's alternative: the agent's own shell reads the file inside the `sudo` call, so the token never stands on a command line. This needs a shell in the call; the argv changes only when a login file is set, so no earlier test changes. It also means the factory does not have to read the file at all, which S0004's mode `0440` with group read would no longer need.

   **Recommended: (a) for now** (the shakedown hosts are Windows VMs, and the shell route is a larger, riskier change), with edit 5's wording and an open point in the decision log.
3. **The UTF-16 file and the other untested clauses.** **Recommended: edits 1 to 4.** An operator who saves the token with PowerShell 5 gets UTF-16. The run then stops with `cannot read the agent's login file ...`, which the guide can explain, rather than a crash of the preflight.
