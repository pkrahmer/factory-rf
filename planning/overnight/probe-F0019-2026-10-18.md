# Probe for F0019, 2026-10-18: in-place `Edit`, `CLAUDE_CONFIG_DIR`, fixed `/tmp` paths

The probe settles the three facts that F0019's pre-check left open (`precheck/F0019-feature-1.md`, H1 and H3). Each was seen in a real Claude Code run under Landlock, in a throwaway container of v1.1's current image.

## Setup

- **Image.** `factory-self-factory:latest` = `:3bcee441ca02` (id `67dd5b0bdc1a`), Claude Code 2.1.296.
- **Container.** Every container was `docker run --rm --init --entrypoint bash --user agent -e HOME=/home/agent`. The user `agent` is uid 1001, group `factory-work`; the image's default user is `factory`. `sudo` was not used.
  - No volume of an instance was mounted, nothing was done to `factory-self-factory-1`, and nothing was installed.
  - The mounts:
    - the probe's script folder, read-only, at `/probe`;
    - for the two Claude runs only, `image/secrets/claude-token`, read-only, at `/home/agent/.claude-token`.
  - The shell inside set `CLAUDE_CODE_OAUTH_TOKEN` with `tr -d ' \t\r\n' < /home/agent/.claude-token`. The token was never read, printed or logged outside that.
- **Kernel.** `6.18.54.1-microsoft-standard-WSL2`. `landlock_create_ruleset(NULL, 0, 1)` returns **ABI 7**.
- **The wrapper.** A throwaway `ctypes` script, about forty lines, kept in `%TEMP%/probe-F0019` and removed afterwards. It does this:
  - handles `0x7FF2`, the twelve write rights of the design;
  - adds a folder rule (`0x7FF2`) or a file rule (`WRITE_FILE|TRUNCATE` = `0x4002`) for each path;
  - calls `prctl(PR_SET_NO_NEW_PRIVS)`, then `landlock_restrict_self`, then `os.execvpe`.

  A shell check under it gave what the design expects:
  - writing the allowed file in place and writing in the allowed folder pass;
  - `touch /tmp/z`, a new file beside the file rule, `mv` of the file and `cp` to `README.md.tmp` each fail with `Permission denied`.
- **The rules of both Claude runs** (no folder rule on `/tmp`, on the checkout or on the home's root):
  - folders: `/home/agent/.claude`, `TMPDIR=/tmp/probe/run`, `/dev/shm`;
  - files: `/tmp/probe/checkout/README.md`, plus `/dev/null`, `/dev/zero`, `/dev/full`, `/dev/random`, `/dev/urandom` and `/dev/tty`.
- **The checkout.** `/tmp/probe/checkout`, holding only `README.md` (`The colour is alpha.`), made before the rules were applied. The run's working directory was the checkout.
- **The call.** `claude -p '<edit README.md alpha to beta with Edit; then Bash: echo ok > "$TMPDIR/x" && cat "$TMPDIR/x" && pwd; quote any error; answer done>' --tools Read,Edit,Bash --permission-mode bypassPermissions --max-budget-usd 0.30 --output-format json`
  - The call ran with `CLAUDE_CODE_DISABLE_AUTO_MEMORY=1`, `CLAUDE_CODE_DISABLE_GIT_INSTRUCTIONS=1` and `PYTHONDONTWRITEBYTECODE=1`.
  - `bypassPermissions` was accepted.
- **Observation.**
  - The JSON result and stderr of each run.
  - `ls -la` of the home, `~/.claude`, `/tmp` and the checkout before and after.
  - `stat` of the README's inode before and after.
  - `find $HOME /tmp -newer <marker>`.
  - The image has no `strace`, so the system calls themselves were not traced.

## Fact 1: `Edit` writes in place. Yes

- **What happened.** In both runs `Edit` replaced `alpha` by `beta` in `README.md`. The rules allowed only that file (`WRITE_FILE|TRUNCATE`), and its folder was refused. The model reported "Both tool calls succeeded".
- **The file.** `stat`: `inode 337745 size 30` before, `inode 337745 size 29` after, so it is the same inode, written and truncated in place.
- **No traces.** No temporary file and no backup were left in the checkout, and the checkout folder gained no entry.
- **What this cannot rule out.** Without `strace`, it cannot rule out that Claude Code first tried a temporary file and a rename, and fell back silently. If it did, the fallback works and nothing failed visibly.

**For F0019.** Decision 3 holds, and the precheck's worry (F5) is settled. A file rule is enough for the work item and for the documenter's `README.md`. Neither needs its folder, and S0003's targets stay as drafted.

## Fact 2: where Claude Code writes its state. Only under `~/.claude` with the variable; without it `.claude.json` is silently lost

- **Run 1 (with `CLAUDE_CONFIG_DIR`).** The run started and finished, with no error.
  - New entries under `/home/agent/.claude`:
    - `.claude.json` (52474 bytes, `0600`)
    - `backups/.claude.json.backup.<n>`
    - `.last-cleanup`
    - `policy-limits.json` and `policy-limits.json.stamp.json`
    - `remote-settings.json`
    - `projects/-tmp-probe-checkout/<session>.jsonl`
    - `session-env/<session>/`
    - `sessions/`
    - `shell-snapshots/`
  - Nothing was written at the home's root: `/home/agent` kept `.bash_logout`, `.bashrc`, `.profile` and `.claude` (plus the mounted token).
- **Run 2 (without the variable).** The run also started and finished with `success`, and stderr had no line from Claude Code.
  - The same files appeared under `~/.claude` except `.claude.json` and `backups/`.
  - `/home/agent/.claude.json` was not created: its write in the home's root was refused, and Claude Code said nothing about it.
  - The settings, the transcript and the shell snapshot still go to `~/.claude`, because that is the default config folder.

**For F0019.**
- Decision 9 holds. The variable is what keeps `.claude.json` (onboarding, project state, the per-session data Claude Code saves) inside the allowed folder.
- Without the variable the guard does not break a run. It loses that state silently, run after run. So S0004's `CLAUDE_CONFIG_DIR` is needed as drafted, and no story needs a change.
- The image already makes `~/.claude`: `drwxrwsr-t factory:factory-work`, and the agent writes it through the group.
- Note for the live instance: once the variable is set, the existing `/home/agent/.claude.json` (52 KB) is no longer read. Claude Code starts from a new `~/.claude/.claude.json`, and run 1 shows that this works.

## Fact 3: fixed paths outside `TMPDIR`. None seen; `/tmp/claude-<uid>` and `/tmp/cc-socks` follow `TMPDIR`

- **What happened.** In both runs `/tmp` itself was refused, and the `Bash` tool ran `echo ok > "$TMPDIR/x" && cat "$TMPDIR/x" && pwd`. It printed `ok` and `/tmp/probe/checkout`, and there was no refusal at all.

  - its shell snapshot, under `~/.claude/shell-snapshots/`.
- **Nothing else.** `/tmp` itself gained nothing; it kept only the probe folder and the image's own `uv-f76e1c7172f0c20c.lock` from the build.

**For F0019.** Decision 11, the run's own `TMPDIR`, is enough for Claude Code and its `Bash` tool. No fixed `/tmp` path needs a rule or a story, so H3 is settled for Claude Code.
- **Not checked.** `/tmp/semgrep-mcp`, made by `make sast` in the live container, was not checked here, because no `make check` ran. Change 6 still has to watch it. If semgrep writes it at a fixed path, it is a story, because no tool path can name `/tmp`.

## Extra: `uv run ruff --version` and `~/.cache`

- **Setup.** A small project in the checkout: `pyproject.toml`, with ruff as a dev dependency.
- **The base rules.** `TMPDIR`, `~/.claude` and `/dev/null`, plus a folder rule on `.venv` (made beforehand, as decision 6 makes a missing folder).
- **What each case gave:**

| Case | Seen |
|---|---|
| `~/.cache` missing and not allowed | `error: failed to create directory `/home/agent/.cache/uv`: Permission denied (os error 13)` |
| `~/.cache` allowed, no `uv.lock` yet | `error: failed to write to file `/tmp/probe/checkout/uv.lock`: Permission denied (os error 13)` |
| `uv.lock` present (made before), `.venv` and `~/.cache` allowed | ruff downloaded into the cache, installed into `.venv`, `ruff 0.17.1`; a second run `ruff 0.17.1` |
| the same synced `.venv` and a filled cache, `~/.cache` **not** allowed | `error: failed to open file `/home/agent/.cache/uv/sdists-v9/.git`: Permission denied (os error 13)` |

- **Where uv wrote.** With `uv.lock` present, uv wrote only `.venv`, `~/.cache/uv` and a lock `uv-<hash>.lock` in `TMPDIR`; it honours `TMPDIR`.

**For F0019, change 5.**
- `~/.cache/*` must stay in `tool_paths`. Without it, even a fully synced `uv run` fails, because uv opens its cache for writing on every start. `.venv/*` must stay as well.
- A fresh home has no `~/.cache`, and S0004's rules must make it (decision 6). The image does not.
- `uv.lock` gets no rule (it lies at the checkout's root), so a run that would change it is refused with the line above. That is acceptable, because a new dependency already needs the human's leave. It is also a reason to keep `uv.lock` current on `main` before the guard goes live.
- No change to the list is needed.
