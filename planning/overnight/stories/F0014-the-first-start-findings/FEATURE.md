# The first start's findings

## Goal

v1.1 started for the first time on 2026-10-17, as instance `shakedown` under Docker Desktop and `shakedown-podman` under rootless Podman 5.8.3, both on the todo demo's empty project (plan step 2, `planning/overnight/restructure-after-f0011.md`; the results in `planning/overnight/first-start-checklist.md`, "Results"). Both became healthy, and most of the operator guide's observations held, but the start found four faults, and a fifth was found while this feature was drafted. The agent cannot use git in the shared checkout (`detected dubious ownership`). The agent can write the checkout's git hooks, which the factory's git runs as the user who can read the hosting token. Every new instance needs an interactive `claude` login as `agent`. The operator guide is wrong or silent in three places. And the agent can write the checkout's whole `.git`, its configuration included, so a `core.fsmonitor` line it writes makes the factory's own git run a command. The human added one more item on the same day, for the status map, a viewer that reads GitHub only: a journal record does not say when, in which stage or from which run it was written, and a cost record does not say which instance ran it. This feature fixes them, built by v1 before the shakedown run (plan step 4), which needs agents that can read a diff, a factory whose git cannot be made to run an agent's code, and instances that start with no login. It is for the human, who runs the shakedown next, and for every operator after: credentials are injected from outside, never typed into an instance. Done when every story below is merged, `make check` is green, the factory's git runs no hooks, the factory alone writes the checkout's `.git`, the image trusts the checkout for the agent's git, the agent runs get their login token from a mounted file, the operator guide says what the first start saw, and every new journal record carries `at` and `stage` (and `run` when it came from a run) and every new cost record `instance`.

## Scope

- The factory's git runs no hooks (fault 2, the human's answer 2): `core.hooksPath` set to the null device in the factory's git environment, tested with real hooks in a real repository (S0001).
- The factory alone writes the checkout's `.git` (fault 5, the human's word of 2026-10-17, decision 19):
  - `core.sharedRepository=0640` in the factory's git environment.
  - A seal that takes the group's and others' write bits from `.git` and everything in it, run at the start of every iteration and before every agent run.
  - A check that refuses a `.git` that is not the factory's alone, run on an existing checkout and after every agent run. A checkout that fails it is removed and cloned again.
  - Tested with real repositories and git's own modes under umask `002`. The real check as `agent` is plan step 4's (S0006).
- The agent's git trusts the shared checkout (fault 1, the human's answer 1): a root-owned `/etc/gitconfig`, readable by the agent, with `safe.directory` for `/work/checkout`, and a test of the image file; the real `git status` as `agent` is observed in step 4 (S0002).
- The agent's login from a token file (fault 3, the human's answer 3): the setting `FACTORY_CLAUDE_LOGIN_FILE`, the `claude -p` runtime that hands the token to each run as `CLAUDE_CODE_OAUTH_TOKEN`, the wiring and the probe's detail (S0003); the image's `ENV` and the compose file's read-only mount of `image/secrets/claude-token`, with the operator guide's steps for `claude setup-token` (S0004).
- The guide (fault 4, the human's answer 4): the place of the login (S0004's docs criterion, which rewrites that paragraph); `2775` for an agent-made folder and the Podman connection on Windows (S0005, documentation only).
- The data the status map reads (the human's word of 2026-10-17, `planning/overnight/first-start-checklist.md`, "Results", item 6, decision 25):
  - `JournalRecord` gains `at`, `stage` and `run`, optional when read and set by every place that appends an entry; the front matter writer leaves an unset one out (S0007).
  - `CostRecord` gains `instance`, optional when read and set by `CostRecorder.begin` from the settings; the cost record writer leaves it out when unset (S0008).

## Out of scope

- An API key (`ANTHROPIC_API_KEY`) injected the same way: it would fit the mechanism (one more file and one more name in the runtime), but it is left out. The factory runs agents under the operator's own subscription login (R12), an API key bills by use instead, and Claude Code prefers an API key it finds over the subscription, so a stray key file would change who pays without a word. Nothing in v1.1 needs it now; a team setup that wants it gets its own story (decision 15).
- The work tree's own `.gitattributes`, `.gitignore` and `.gitmodules`: they stay writable by the agent, like the rest of the work tree. They name no command git runs without a driver or command defined in the configuration, which only the factory writes now (S0006; decision 17 is superseded by decision 19).
- An agent process that outlives its run and writes after the check: the time limit ends the run's processes, and the guide's time-limit observation checks that none is left (`pgrep -u agent -l` prints nothing). The seal's guarantee holds from one check to the next agent run (decision 21).
- A test of S0006 as two real users in `make test`: there is no second user there (decision 22). The real check as `agent` is the morning observation S0006's docs criterion writes, run at step 4.
- A real agent run end to end and a `time_limit` under `sudo`: the tiny story of plan step 2's item 5, run after F0014 at the start of step 4.
- A real `git status` as `agent`, a real probe run under the token, and the token's survival of a new instance: observed by hand at step 4, as the docs criteria of S0002 and S0004 write the observations.
- The project commands, which run as the factory's user and can read the hosting token: left for v2 (F0010, the human's decision of 2026-10-14).
- A preflight item of its own for the login file: the probe makes the call that needs the token and names the file when it fails (decision 13).
- The hosting token: unchanged (the human's answer 3, "the hosting token as today").
- The status map itself, markers in a work item's body and any change to the pull request (the human's word on item 6: "No markers in the body, no change to the pull request"). A migration of the records written before S0007 and S0008: they stay valid without the new fields (decision 25).
- A `run` on the `crash` and `expiry` entries: recovery writes them on a later tick from the claim and does not know the run; the run's `started` cost record in the sidecar names it (decision 26).

26. How, for the journal, taken by the session for the human, to confirm (S0007):
    - `append_entry` takes `at` and `run` as optional keywords, and takes the stage from the state of the document it is given. A record gets the three fields only when `at` is given. A `run` without `at` is a `ValueError`. Every caller in `src/factory` passes `at`; each path is pinned by a changed or a new test. With the keyword optional, the tests that call `append_entry`, `book_merge` or `book_refusal` directly stay unchanged (about forty calls in nineteen modules). The record has no rule tying the three fields together, so a reader accepts any of them alone.
    - The started entry's `at` is the claim's `started_at`, the same reading of the clock. Each other entry reads `clock.now()` where it is appended.
    - The stage is whatever the state holds when the entry is appended, and no call site changes its order. So a `move_back` entry carries the stage the human set.
