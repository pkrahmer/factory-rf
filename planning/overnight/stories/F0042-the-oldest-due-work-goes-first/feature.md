# The oldest due work goes first

## Goal

On 2026-10-20 the acceptance of F0037 (a torn record line never stops a check) was due from 06:49:45 UTC (08:49 local), when F0037-S0001 was archived, and opened only at 09:44:44 UTC, while the stories and acceptances of F0020, F0029 and F0030 ran before it; F0030-S0001 had been started at 07:42:34 UTC, fifty-three minutes after F0037's acceptance was due. The human wants the work item that has waited longest to go first. The cause is the ranking of new work in the evaluation (`_new_work` in `src/factory/domain/evaluation.py`, tier 4 in `docs/project-guide/watching.md`): every runnable work item is keyed by `work_item_order(id)` and every due feature by `(<feature id>, 1, "")`, so the lowest feature id wins, whenever its work was started. A feature with a low id that is started late overtakes every feature with a higher id that waits already. The dispatcher (`src/factory/application/dispatcher.py`) only hands the one event on, and the claim (`src/factory/application/claims.py`) only takes the work item the event names; neither chooses. The board (`src/factory/application/board.py`) lists its rows in the same id order, but it chooses nothing either. This feature ranks new work by the time it became due instead, read from `origin/main`'s history, with the id order kept only for ties and for work without a known time. What stays: the four tiers, so a waiting work item still holds back all new work and a held claim still means that nothing else runs. It is for the human, who starts stories and merges acceptances and expects them to be worked on in the order they became due. Done when every story below is merged and `make check` is green.

## Scope

- `src/factory/domain/evaluation.py`: tier 4 ranks its candidates by their queue time; `EvaluationInput` carries the queue times (S0001).
- `src/factory/application/watcher.py`: reads each candidate's queue time from `origin/main`'s history and hands it to the evaluation (S0001).
- `src/factory/application/git.py` and `src/factory/adapters/git_cli.py`, only where the reading needs one more operation or an optional parameter of `log` (S0001).
- `docs/project-guide/watching.md` (*The four tiers*, tier 4), `docs/operator-guide.md` (the order of new work and of a due acceptance) and `docs/decisions.md` (a new entry), from S0001's docs criterion.

## Out of scope

- Tiers 1 to 3: the integrity checks, the first waiting work item in id order (which pull request is looked up), and the first claimed work item. While one work item waits for the human, no new work starts, as today (decision 4).
- The board's and `factory-watch`'s row order: the rows stay in id order (decision 5, open).
- Running more than one agent at a time, or letting new work start while another work item waits for the human. Of F0037's three hours, about an hour (67 minutes in six waits, the longest 43 minutes for F0029-A0001's merge) were waits for the human's merge, which no ranking changes.
- Any record of its own for the queue time: it is read from git, never written (decision 2).
- Every paid call: no story and no smoke test makes one.

## Decisions taken for the human

1. **The cause (checked against the history of `origin/main`, 2026-10-20).** The evaluation does not prefer newer work; it prefers lower feature ids. F0037-S0001 was archived at 06:49:45 UTC. Before F0037's acceptance opened at 09:44:44 UTC, the factory ran F0020-S0016 (started 06:48:41), F0020-A0004 (due 07:09:28), F0029-S0002 (started 06:48:44), F0029-A0001 (due 07:42:17), F0030-S0001 (started 07:42:34) and F0030-A0001 (due 09:25:56): every one of them had a lower feature id, and two of them became due after F0037's acceptance. The second case of the human's note does not show a fault of the ranking: F0041-A0002 opened at 14:43:56 UTC on its branch, twenty seconds after F0027-S0002 was archived, and the human's start of F0027-S0003 reached `main` at 14:44:00 (its commit is a sibling of the opening commit, on the same parent `ee60a6f0`). At that tick F0027-S0003 was still in `backlog/`, so no ranking could have chosen it. Under the rule of decision 2, F0041-A0002 (due 12:56:32, when F0041-S0004 was archived) would even have gone before F0027-S0002 (started 12:56:42, ten seconds later), which ran first because F0027 < F0041 (S0001).
2. **What "oldest" means: OPEN, for the human.** Options:
   - (a) The time the work item became due, read from `origin/main`'s history (recommended). A story's queue time is the committer time of the newest commit on `origin/main` that added its file under `in-progress/` (the human's start; a move from `backlog/` counts as an addition there). A due feature's queue time, and that of its running acceptance, is the committer time of the newest commit on `origin/main` that changed one of the feature's story files in `backlog/`, `in-progress/` or `done/`: the archive of its last story, or the removal of its last story from the backlog. Reasons: it is what "has waited longest" means for both kinds of work; both times are on the remote, which is the only truth, so the order survives a restart and every instance and `factory-watch` see the same order; nothing new is recorded. Cost: one git command per candidate per tick, on the local clone.
   - (b) The start commit's time for stories and the id order for acceptances. A story would no longer be overtaken by a lower feature's story, but a due acceptance would still wait behind every lower feature, which is the F0037 case.
   - (c) The backlog order (the id order of today). No change; the F0037 case stays.
   - (d) The position of the commit in `origin/main`'s first-parent history instead of its committer time. Immune to a skewed clock, but harder to read in `git log`, and a start the human pushes after merging `main` locally is not on the first-parent line.
   S0001 is drafted with (a). With (b), its criteria 2 and 3 lose the acceptance rows; with (c), S0001 is dropped.
3. **Ties and unknown times (S0001).** Git keeps committer times to the second. Candidates with the same queue time go in `work_item_order`: the lower feature id first, a story before an acceptance, then the id. A candidate whose queue time cannot be read (no such commit on `origin/main`) goes after every candidate with one, in `work_item_order`. So an `EvaluationInput` without queue times ranks exactly as today, and every earlier evaluation test built without them keeps its meaning.
4. **What does not change (S0001).** Only tier 4 changes. A blocked work item, and one at an approval stage, is no candidate and still holds back all new work (tier 2); when its block ends, it keeps its queue time, because the time is read from `main`'s history and not from its state, so a question to the human never sends it to the back. A running acceptance and a due feature share their feature's queue time, so opening the acceptance does not move it. The attempts cap stays: the first candidate gives `ask` (`attempts cap`) as today. A story and a due acceptance of the same feature never compete: the acceptance is due only when no story of its feature is in `backlog/` or `in-progress/`.
5. **The board's order: OPEN, for the human.** Options: (a) the board and `factory-watch` keep their rows in id order (recommended: they choose nothing, the order is documented in the operator guide, and the event line of `factory-watch` already names what runs next); (b) the board lists the work item rows in queue order, which needs the queue times in `BoardReader` too and changes the board's tests. S0001 is drafted with (a).
6. **The clocks (S0001).** The human's start commits carry the time of the human's machine, the factory's commits that of its container. On this machine both read the same clock; a clock that is off by some minutes moves the order by as much. The queue time is never compared with the factory's own clock, only with other commit times, and `factory.domain` stays without a clock of its own.
7. **No leave is needed (S0001).** A prototype of the rule on a copy of `main` of 2026-10-20 ran the whole suite in a throwaway container: with the committer times as git writes them, the same 9 tests failed as without the change (all of them faults of the container: the umask, the reopened folders and three YAML messages), and no other. A second run ranked every commit strictly by its place in the history, as if no two commits ever shared a second, to find the earlier tests that pass only by a tie. It found one, `tests/application/test_watcher_acceptance.py::test_a_started_story_of_the_feature_runs_before_its_in_flight_acceptance` (both rows), and only because the prototype read the acceptance's time from `done/` alone. Under the rule of decision 2 the human's start of the new story changes a story file of the feature, so the story and its running acceptance share that commit's time, and the tie gives the story, as the test expects. So no earlier test changes; S0001's criterion 2 holds that tie as a row (S0001).
8. **A story started beside a running acceptance (S0001).** When the human starts a new story of a feature whose acceptance is running, both get the start's time (decision 7), and the story goes first, as today: the acceptance then reads a feature with a story in progress.
