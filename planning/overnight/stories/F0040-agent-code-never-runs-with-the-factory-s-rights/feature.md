# Agent code never runs with the factory's rights

## Goal

The human decided on 2026-10-20 to close two gaps that the decision log left open. (1) The project commands run code that agents wrote as the factory's user, who can read the hosting token. `MakeProjectCommands.run` (`src/factory/adapters/make_commands.py`) starts `make --no-print-directory <command>` with no user switch and with the factory's whole environment less three make variables, and the wiring (`build_boundaries` in `src/factory/entry/wiring.py`) builds it so for every instance. Every caller goes through `boundaries.project_commands`: a stage's checks and reports through `KnownResults._run` and the preflight's `lint` on `main` (`Preflight._run_probe`). So `make check`, `lint`, `test`, `secrets`, `duplicates` and `documents` run tests and scripts the agents wrote, as `factory`, and a test could print the token into the output tail the factory writes into the journal (decision log, *The project commands run as the factory's user and are left for v2*; operator guide, **Left for v2.**). (2) The agent's home survives every run. `/home/agent/.claude` is the volume `claude-home`, the rest of `/home/agent` lives as long as the container. On the instance `self` on 2026-10-20 (read-only listing) it held `.claude.json` (53 KB), `backups/`, `plugins/` (2.7 MB), `session-env/` (721 folders), `shell-snapshots/`, `sessions/`, `projects/` (the full transcripts of all earlier runs, about 222 MB, a folder only `agent` can enter), and outside it `.cache/` (uv, pylint), `.semgrep/`, `.bashrc`, `.profile`, the two mounted login files and the factory's empty, read-only `.config/opencode`. No `CLAUDE.md` and no `.credentials.json` were there. The cause is the run's rules: the Claude Code runtime allows the whole `~/.claude` (`RUNTIME_FOLDER`, because it sets `CLAUDE_CONFIG_DIR` there and Claude Code replaces `.claude.json` by renaming), and the folder is `factory:factory-work` with mode `3775`, writable by the agent's group. The drafting agent checked it on 2026-10-20 in a throwaway container of `factory-self-factory` (`--network none`): as `agent` through `sudo -n -u agent -- timeout ... env -i ... factory-confine --rules <rules>` with the Claude Code runtime's rules (`/home/agent/.claude` allowed), `echo probe > ~/.claude/CLAUDE.md` succeeded (`-rw-rw-r-- agent factory-work`), and so did `mkdir ~/.claude/rules`; `~/.profile` was refused. With opencode's rules and with the tool paths alone, both writes were refused. So a Claude Code run can plant a user `CLAUDE.md` or a rules file that every later run loads silently, and it can read every earlier run's transcript; an opencode run can read every earlier session in `~/.local/share/opencode/opencode.db`. What must survive between runs is only a login: Claude Code's comes from the mounted token file at every call (`CLAUDE_CODE_OAUTH_TOKEN`), and only a login made by hand lives in the home (`~/.claude/.credentials.json`, the operator guide's empty-token path); opencode's API key comes from its mounted file, and a login by hand lives in `~/.local/share/opencode/auth.json` (`opencode auth list` names that file); an operator's own opencode build keeps its login in the folders of `FACTORY_OPENCODE_FOLDERS`. The first instance start began with an empty `claude-home` volume and passed its probe, so Claude Code needs nothing else of the home. This feature closes both gaps. Every project command runs as `agent`, through the same `sudo -n -u agent -- timeout --signal=KILL ... env -i` start the agent runs use, with the checkout's git folder sealed; and before every agent run and every project command a small program, run as `agent`, removes everything `agent` made in its home except those logins. It is for the operator and the human, who trust the token to stay in the factory and a run's result to come from that run's instructions alone. When it is done, no code an agent wrote runs as `factory`, and no run sees or inherits what an earlier one left in the home. Done when every story below is merged and `make check` is green; the real check is the operator's, after the merge (*The human's changes*, 3).

## Out of scope

- Confining the project commands' writes with `factory-confine` (decision 1).
- The agent's own login files: `/home/agent/.claude-token` and `/home/agent/.anthropic-api-key` stay readable by `agent`, by design, so a test can still print the agent's login into an output tail, as an agent run can write it into its work (decision 6).
- Network egress of a run or a project command, `/tmp` and `/dev/shm` between runs, and the checkout's git-ignored files (F0027's).
- A process of `agent` that outlives a run or a project command (F0027's leftovers program; see *The human's changes*, 4).
- The image, the entrypoint, the compose file, the sudoers file and the volume `claude-home`: unchanged (decision 12).
- Keeping the transcripts somewhere else for the operator: the last run's transcript stays until the next run starts (decision 10).
- Every paid call: no story and no smoke test makes one.

## Decisions taken for the human

1. **The project commands run as `agent` through `sudo`, `timeout` and `env -i`, without `factory-confine`** (S0001, S0002). The gap is a read (the token), and the user switch closes it whole: `agent` cannot enter `/home/factory/.secrets`. Landlock limits writes only, and a project command's writes reach no later run: the home is cleared before every run and command (S0004), the git folder is sealed (S0002), and the restore cleans the work tree. Confining them would need the pipeline's tool paths in `ProjectCommands.run`, an interface change, and the preflight's probe has no pipeline definition to take them from. Options: A, this (recommended); B, also `factory-confine` with the tool paths and a temporary folder, at the price of that interface change and a probe with fixed tool paths.
2. **`launch` is reused, not copied** (S0001). The make class calls `launch`, `killed_at_limit` and `SUDO_GRACE` of `factory.adapters.agent_launch`, so an agent run and a project command start the same way and one change reaches both.
3. **The kill at the limit is the agent's own `timeout`** (S0001). The factory may not signal root's `sudo` (decision log, 2026-10-16), so `timeout --signal=KILL` inside the call kills at the limit and the factory's kill waits 30 seconds longer. A command killed so is `time_limit`, an exit status of 137 before the limit is a failure.
4. **A refused `sudo` is a `ProjectCommandError`, not a red check** (S0001). Only `sudo:` lines and a failing status mean `make` never ran; a red `main` would otherwise stop the repository with `main_branch_failing` for a fault of the machine. At the preflight's probe it is `preflight_failed`, as an agent run's refused `sudo` is.
5. **The command's environment is the agent run's, plus `PYTHONDONTWRITEBYTECODE=1`, and no login** (S0002). Today make gets the factory's whole environment (`FACTORY_TOKEN_FILE` and every variable of the operator). The agent run's allow list (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TERM`, `TZ`, `HOME` the agent's) is what every agent's own `make check` already runs with; the bytecode switch is what the image's `ENV` gave make so far. No login shell: a project command needs no model.
6. **The agent's own login stays readable by project commands** (S0002, out of scope). It is the agent's, which every agent run reads; a third user only for project commands would be a new mechanism for a smaller risk. The operator guide says so.
7. **Each project command runs with the git folder sealed** (S0002). Between an agent run and its checks the factory's git (undo, commit) writes group-writable files into `.git` under the umask `002`, such as a branch's ref; a command as `agent` could rewrite them before the factory pushes. The seal before and the check after are `run_sealed`'s, for the same reason. The known results (F0023) need no change: a rebuilt image has a new identity, so no result recorded as `factory` is reused after the upgrade.
8. **A fresh home by clearing, before each stage run and each project command, not a new `HOME` per run** (S0004). `HOME` stays `/home/agent`, so `FACTORY_OPENCODE_FOLDERS`, the mounted login files, the tool paths `~/.cache/*` and `~/.semgrep/*` and the factory's own files in `~/.claude` keep their places. A new home per run would have to be made by the factory and be writable by the agent with read-only agents and settings inside, a second copy of what the image and the entrypoint already set up. The reset sits in `run_sealed`, not in the runtime's `run`, because `PatientRuns` resumes a session after a provider limit through the runtime, and the session's transcript must stay for that. Options: A, this (recommended); B, a home per run under the run's temporary folder.
9. **What survives: the logins only** (S0003, S0004). The two mounted login files, `~/.claude/.credentials.json` and `~/.local/share/opencode/auth.json` (each runtime's login made by hand), and the folders of `FACTORY_OPENCODE_FOLDERS`. Everything else the agent made goes, the caches included: a cache is a file a run wrote that a later run (and, with F0027-S0003, a later check) reads. Cost: a `uv run` that must sync `.venv` downloads again (the instance has network); with F0027-S0003, which removes `.venv` after every run, every check would download every package. Risk: a login by hand might need more of Claude Code's state than `.credentials.json` (account data in `.claude.json`); not checkable offline, so it is the operator's check 3.6. Options: A, this (recommended); B, keep `~/.cache/uv` too, as a kept folder, if the operator's measurement after F0027 shows checks too slow.
10. **The reset comes before a run, not after** (S0004). It suffices for the rule (no run starts with what an earlier one left), and the last run's transcript stays for the operator to read after a failure until the next run starts. The first reset after the upgrade removes what the volume gathered (222 MB on `self`).
11. **A failed reset stops the run with `AgentRuntimeError`** (S0004). A run in a home the factory could not clear would break the rule silently; the error takes the path a refused `sudo` takes (a counted error at a stage, `preflight_failed` at the probe).
12. **The image, the entrypoint, the compose file and the volume stay** (S0004). The entrypoint's installed files belong to `factory`, so the program leaves them; dropping the volume would change `tests/test_compose.py` and gain nothing, since the program empties it of the agent's files. `.bashrc`, `.profile` and `.bash_logout` belong to `agent` (from the image's skeleton) and go at the first reset; no start of the factory reads them (`sh -c`, no login shell).
13. **The program decides by ownership and has no default home** (S0003). It runs as the agent, so it can remove exactly what the agent can, and an entry of another user is the image's or the factory's by construction. A folder the agent made is walked and removed once empty, so a factory-owned folder inside it (`.config/opencode` inside the agent's `.config`) is never removed with it. `--home` is required, so no call clears a home it was not named, which is what the human's change 1 relies on.
14. **No leave to change a test another story wrote.** Every story adds new test modules; `tests/adapters/test_make_commands.py`, `tests/application/test_sealed_runs.py`, `tests/application/test_interfaces.py`, `tests/test_compose.py` and the settings tests stay unchanged and green.
15. **The number and the name.** F0040 is free in `factory/features/` (F0018 to F0036) and `planning/overnight/stories/` (F0027 to F0039); F0041 is drafted beside it. The name says what is true when it is done.
