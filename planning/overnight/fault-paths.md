# v1's thirteen fault-injection paths in v1.1 (WE1.2)

Draft for WE1.2's story (decision 007, question 3). Status: proposed; the operator reads it with WE1.2's story.

## Summary

- The book's list (chapter 16, *Paths walked*) has thirteen paths; v1's demo hardening mode lists twelve. The thirteenth, a test change the human approves (`doing → tests`), was split off path 3 by run 3's plan and is not in the demo's list. No other count was found.
- None of the thirteen is a kill point. Each is a behaviour path: a question, a rework, a cap, a close or `reject`. v1.1 keeps every one of these mechanisms (handover section 3, items 10, 12 and 14; ST2 for `reject`). So no row reads "mechanism removed". Every row is walked by an injection test that runs the path with one kill point of section 7.2 at the step the path adds.
- The pairing of kill point and path is this draft's choice, not something the inputs derive. All six rows of section 7.2 are used: during an agent run, as a crash for paths 1 and 13 and as a stall for paths 4, 6 and 8; between a commit and its push for paths 2 and 9; between a post and its record for paths 3 and 7; the tick at any other point for paths 5, 10 and 11; the container for path 12.
- `reject` (path 9) is walked by `test_reject_of_hand_stage_change_killed_between_commit_and_push_reverts_once_and_leaves_main_clean`, which also covers WE1.3.
- The removed mechanisms that WE1.2 gives as examples are mechanisms of the restart during a stage: the lock reclaimed after the lease plus ten minutes, the run record as recovery state, and leftovers committed after a kill. That restart is one of four paths that run 1 also walked and that the book keeps outside its thirteen. The section *Differences* maps them.
- Every kill point has a path. Section 7.2 still needs one test that no path carries: a crash repeated up to the crash cap.

## The thirteen paths

Every test runs against a real local bare git remote and its clones in `tmp_path`, with the fake hosting client and the fake agent runtime. Injection points in the wrappers raise, or end the process, at the named point. No real container is killed and there is no second-instance test (006, points 15 and 16; R36). A crash test then restarts with the same instance name, and for the container it restarts on an empty disk. Each crash test checks the crash criteria of section 7.2 and each stall test checks the stall criteria. The name says only the kill point and the recovery that is specific to the path.

## Differences from the demo's twelve paths

- **The count.** The demo README (hardening mode) lists twelve paths, each carried by a story marked `<!-- carries path N -->`. The book lists thirteen, because run 3's plan split *a test change the human approves* off path 3 as a thirteenth and the README does not list it (chapter 16, *Hardening mode*; run-facts, *How run 4 was driven*). The demo therefore lacks path 13 under a number of its own. By the book's account it sits inside the README's path 3, the tester's finding against the interface. The inputs do not give the README's wording of its twelve, so whether it names any other path differently cannot be said from them (open question 5).
- **Run 4 uses the book's numbering.** Run-facts names the paths that run 4 walked as 2, 4, 12 and 13, one of them the path the README does not list. Whether run 4 ran in hardening mode at all is not stated.
- **Live coverage.** The handover (WE1) and the book's table agree: four paths never ran live (3, 5, 6, 9) and five ran only on generation 4 (1, 7, 8, 10, 11). Paths 2, 4, 12 and 13 ran on both generations.
- **Paths outside both lists.** The book adds that run 1, on generation 4, also walked four paths that neither list counts. They are not rows of the table, because the book does not number them. They are where WE1.2's examples of removed mechanisms belong:

## Kill points without a path

Every kill point of section 7.2 carries at least one path in the table above. This includes both classes of *during an agent run*. Section 7.2 still requires one thing that no path carries:

| Kill point | What 7.2 requires that no path carries | Test it still needs |
| :- | :- | :- |
| during an agent run (the tick dies), repeated | "a crash that repeats reaches the crash cap (default 2), where the human is asked"; the counter resets when the stage moves forward (GH2.4) | `test_tick_killed_during_agent_run_twice_reaches_crash_cap_and_asks_human` |

The two counts of kill points differ. WE1 and WE1.1 speak of five kill points, while section 7.2's table has six rows, because *during an agent run* appears once as a crash and once as a stall. This draft uses the six rows (open question 3).

## Open questions

1. **What "walked" means.** The thirteen are behaviour paths, not kill points. This draft walks each one with one kill point added, chosen by judgment. The alternatives are a plain test of the path with no kill and the kill-point tests of WE1.1 kept separate, or every path under every kill point (78 tests). Recommendation: one kill per path, as drafted.
2. **No row is "mechanism removed".** WE1.2's examples belong to run 1's restart path, which is not among the thirteen. Should the table in the code's documentation carry run 1's four further paths as extra rows, or only the note under *Differences*? Recommendation: the note. The book numbers only thirteen.
3. **The crash counter outside an agent run.** Does a crash at a kill point that falls after a stage's result raise the `crashes` counter, and if so on which stage? These are between a commit and its push once the result is committed, between a post and its record, and the tick at any other point. R23 counts per work item and resets on a forward move, but such a kill falls between two stages. This affects the crash criterion "the `crashes` counter is one higher" for paths 2, 3, 5, 7, 9, 10 and 11. Also, which count do WE1.1 and its story use: five kill points or six?
4. **Path 1's second half.** A smoke test without `Expect:` is stopped by code's form check before intake, so there is no agent run or handler step worth killing. Is the form check's unit test enough for that half? Recommendation: yes.
5. **The demo's names.** The inputs give the demo README's count (twelve) but not its wording. Confirming that it names no path otherwise than the book needs `demo/README.md` (lines 125 to 144 per run-facts), which this brief excluded.
6. **Two of run 1's further paths have no v1.1 test or item:** a close while the stages work (only GH3.3 records it) and a merge while the move-back question is open. Should either get an injection test?
7. **Path 9's branch.** v1's `reject` sees only the last commit of the checked-out branch (L18, which stays for v2). The test assumes the work item's branch as read from the remote-tracking refs (R18). Is that the intended scope for ST2's rule?
