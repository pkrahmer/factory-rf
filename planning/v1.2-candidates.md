# Candidates for v1.2

v1.2 is a planned change of v1.1, not a reimplementation (the human, 2026-10-20). This file collects the larger changes that wait for it, each with what is known so far. Nothing here is decided. **The proposed plan of 2026-10-24 is `planning/v1.2-plan.md`**: it takes the first section's design (one snapshot instead of many layers) as decided by the human on 2026-10-24 and lays out the features, the machine, the measures and the open questions.

## Isolate the agent by a throwaway environment instead of layers

**Guiding principle (the human, 2026-10-20).** Keep it simple; the holy grail is in the architecture. One mechanism that cleans everything by a reset or a snapshot, instead of many layers that each clean one thing (tonight's stops came from layers meeting each other). Concerns are raised, but the design stays simple. The prototype measures both sides: simple (how many moving parts the cycle has, and how many of today's layers it removes: it must remove more than it adds) and fast (from a stage's start to the agent's first step, and the reset: seconds, no `.venv` rebuild in the normal case).

**The idea (the human, 2026-10-20).** The factory and the agent run apart: the factory keeps the hosting token, the state and the push rights; every agent run gets a fresh environment that starts from a snapshot of the checkout, and is thrown away afterwards. The factory takes the run's result as a commit or a diff and keeps only the files in the role's write paths.

**A rolling base snapshot (the human, 2026-10-20).** The snapshot is not taken once: it is pulled forward regularly (after every merge, or after every run), so the base always holds a checkout close to `main`, with its `.venv` and caches already built. A run then starts from that base, and bringing it up to date costs only the last commit (a pull of one commit and, at most, a sync of what that commit changed), not a fresh clone and a full `.venv` build. Rolling back after a run means returning to the base; moving the base forward means taking a new snapshot of the updated checkout and dropping the old one.

**What it would replace.** The second user with `sudo`, the umask and group rules, the leftovers program (F0027-S0001/S0002), the removal of ignored files (F0027-S0003), the fresh agent home (F0040), probably Landlock and the undo. Tonight's restore stops (2026-10-20) came from these layers meeting each other.

**Three variants to compare.**
1. A small Linux VM with ZFS that runs the factory and starts Podman inside for the agent: instant snapshots and clones, `.venv` included (no rebuild per run). Needs an ordinary distribution (Ubuntu ships ZFS; the WSL2 and `podman machine` kernels do not) and a VM of one's own at work.
2. The same with an in-kernel snapshot instead of ZFS: btrfs, or overlayfs (a thin writable layer over a fixed base, thrown away as the rollback). Runs wherever Linux runs.
3. Throwaway containers on Docker or rootless Podman, with a fresh local clone per run or a `commit`-based base image. Neither engine snapshots volumes; both throw a container's own layer away.

**Open questions that decide it.**
- Can the human run a VM of their own at work (Hyper-V or similar), or only Podman Desktop?
- Who starts the agent's environment: a Docker socket is effectively root on the host; a rootless Podman socket is much less.
- Time per run: a fresh clone and `.venv` (tonight: about 3.6 min for a `.venv` rebuild after the removal) against a snapshot clone.
- How the role's write paths are kept: by taking only those files from the result.
- Where the snapshots live. On the host (OpenZFS on Windows is a beta port with its own driver; OpenZFS on OS X needs a kernel extension; native: APFS `cp -c` clones on macOS, ReFS block cloning on a Windows 11 Dev Drive), a container sees them only through the file sharing of Docker Desktop's or `podman machine`'s Linux VM: slow for thousands of small files and without real Unix owners and modes. Inside that VM (btrfs or overlayfs, no extra driver), next to the containers, they run at full speed with real permissions. Leaning: inside the VM (2026-10-20).

**Leading candidate to prototype first (2026-10-20): Podman's overlay mount.** `-v /base/checkout:/work:O` makes the base checkout the read-only lower layer; the container's writes go to a temporary upper layer that is thrown away when the container ends, so every run is rolled back by itself, rootless included. The rolling base snapshot is the lower folder, moved forward between runs by a pull of the last commit, its `.venv` kept. To design: how the run's result leaves before the layer goes (the agent pushes to a small local repository, or the factory reads the diff first). With `:O,upperdir=<dir>,workdir=<dir>` the upper layer is kept instead of thrown away: the run's changes as plain files (deletions as whiteout entries), the base untouched. So after a run the factory can discard it (rollback), keep it as an exact record of what the run wrote (an undo that knows, not guesses), or merge it into the base. Leaning: git decides what persists (the run's commit moves the base forward by the normal pull, only within the role's write paths); the upper folder is only the record. Docker has no `:O`; neither engine offers volume snapshots without third-party plugins (ZFS, NetApp, the old Convoy), which are no option at work.

**The cycle to prototype (the human with Claude, 2026-10-20; simplified the same night).**
```
   stage layer (:O, thrown away)  <- checkout of the story branch, the agent's work
   base A or B (read-only)        <- main + .venv, updated only while idle
   + /results/repo.git (writable) <- the only way out: the agent's commit
```
1. Two base copies, A and B, each a checkout of `main` with `.venv` built. A folder in use as the lower layer of `:O` must not change while a container runs on it, so after a merge the factory updates the idle copy directly (a pull of the new commits, a `.venv` sync only when the lock changed), then new runs start from it; runs on the other copy finish undisturbed. The next merge updates the other copy.
2. Every stage gets a throwaway layer (`:O`) on the current base and checks out its story's branch inside it (a few files; a `.venv` sync in the layer only when the story changed the lock). No branch layer and no stacking of layers.
3. The way out: beside the `:O` mount the container gets one writable folder, a bare git repository only the factory reads. The agent pushes its commit there (no credentials); the factory takes it, keeps only the role's write paths, and pushes to the hosting service with its own token.
4. The container ends and its layer goes, with every cache, temporary file, leftover process and stray write. Its upper folder may be kept as the run's record.

**Feature branches (an open idea, not part of the cycle).** A layer per feature only holds more than `main` if stories merge into a feature branch and only the accepted feature merges into `main`. That gives a `main` of accepted features and a feature-wide acceptance before landing, at the cost of a second merge level, conflicts between features (F0040 and F0041 touched the same files) and a change to the human's approvals. A decision of its own for v1.2.

**Three ways to get the moving base (from Fable, assessed 2026-10-20).**
1. `podman commit` after every update (start the base, fetch and check out the commit, commit as `project:current`, run throwaway containers from it). Works, but every commit adds a layer: the image grows and needs squashing or a fresh build now and then. Least simple; not chosen.
2. A Dockerfile that clones at a commit (`--build-arg SHA=...`): copy `pyproject.toml` and `uv.lock` first and install the dependencies, then clone, so `.venv` is rebuilt only when the lock changes and a new commit costs a clone from a local mirror (seconds). The same on Docker and Podman. A lock changed by an agent's commit runs `uv sync` in the build, not with the factory's rights.
3. The overlay mount (`:O`, Podman only): the leading candidate above; "the host" must be the Linux VM, not a Windows or macOS folder. Docker's fallback (`git reset --hard && git clean -fdx` on a volume) is close to v1.1 today and works in a throwaway container with one user.
Credentials never go into an image; beyond that, the agent's container gets no hosting token at all: the factory takes the run's commits (from its layer, or from a local repository the agent pushes to without credentials) and pushes them itself. `--depth 1` is optional; a local mirror is faster for a small repository.
Leaning: prototype way 2 (portable) and way 3 (fastest under Podman) side by side, measured by the two measures of the guiding principle.

**A possible host: TrueNAS SCALE (2026-10-20).** Its apps run on Docker since 24.10 (Kubernetes before), on a Linux with ZFS: the base checkout could live on a ZFS dataset with real snapshots and clones. An app sees its dataset only as a mounted folder, so taking or rolling back snapshots from a container needs extra rights or a helper on the host side.

**Running on TrueNAS (2026-10-20).** Its apps are Docker, without `:O`. Three ways: (1) way 2, the Dockerfile with the lock-keyed dependency layer, runs on its Docker as it is; (2) a system container with Podman inside, under the menu "Containers" (Incus system containers; the human's TrueNAS has "Containers", "Virtual Machines" and "Apps" side by side, 2026-10-20; nesting must be allowed for Podman inside), gives `:O` without a full VM; (3) a small VM always works. Not: Podman on TrueNAS's own system (an appliance; updates replace it), nor in a privileged Docker container (it weakens the isolation). So the reset sits behind one small interface with two implementations, Podman `:O` where available and the Docker image way elsewhere; the same factory then runs on TrueNAS, at work and on Docker Desktop.

**Next step when v1.2 starts.** A design note comparing the three variants (security, speed, maintenance, what runs at work) with a small timing prototype.

## For v1.3: the agents' project commands run through the factory (the human, 2026-10-24)

- **The gap.** In v1.2 the coder and the tester run `make check`, `make test` and single tests themselves, in the agent's container, which has the network and the agent's login. So code those commands run (a test, a `conftest.py`, a dependency) runs beside the login. The human does not mind that the agent itself holds the key; the concern is foreign code run by a check.
- **The simpler idea (chosen over a login proxy, which the human found too complicated).** An agent asks the factory to run a project command instead of running it itself; the factory runs it in a check container that holds no login (as `ContainerMakeCommands`, F0042-S0009, does for the gate) and hands back the result and the output's tail. The factory's gate after the coder stays as it is.
- **What it needs.** A channel from the agent's container to the factory (for example a small command in the stage image that writes a request into a mounted folder or socket and waits for the answer); and a copy of the agent's unfinished work for the check, because the check container resets the dataset to the base, which would wipe the work in progress (a take first, or a second clone).
- **What it costs.** A container start per test run (about 0.15 s on the VM, plus the copy and `make sync`); the agents' instructions name the new command instead of `make`.
- **Rejected for now.** A proxy on the host that adds the login to the agent's API calls (no secret in the container at all): the human, 2026-10-24, too complicated for v1.3. An allow-list of the agent's network: needs the same kind of proxy.

## For F0045, beside the six items above (the human, 2026-10-24)

- **The idle shutdown, an option, off by default.** On a VM the factory may power the machine off when it has had nothing to do for a while, so a stopped VM costs only its disks. A setting turns it on and gives the idle time (for example `FACTORY_IDLE_SHUTDOWN_MINUTES`; unset or 0 means off, which is the default); "nothing to do" is the board's idle state: no claim held, no work item startable, for that many minutes in a row. The factory then logs one line and runs the shutdown through a wrapper (`systemctl poweroff`, with the one right it needs given by `vm/setup.sh` only when the option is used). Starting again is outside the factory: the human (`gcloud compute instances start`) or a GCP instance schedule. Never on `inline`/Docker. Open: how the operator guide's chapter "The machine" describes the schedule; whether a stage waiting for the human (approval, a question) counts as idle (proposed: yes, the lease is not held then).
- **The stall reason `left_branch` goes** with the records contract's next major (F0044 decision 29 (b)).
- **The two defaults that name v1.1's image** (`FACTORY_CLAUDE_HOME`, `FACTORY_IMAGE_ID_FILE`): made required or given the VM's paths (F0044 decision 29 (c)).
