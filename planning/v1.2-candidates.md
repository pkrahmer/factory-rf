# Candidates for v1.2

v1.2 is a planned change of v1.1, not a reimplementation (the human, 2026-10-20). This file collects the larger changes that wait for it, each with what is known so far. Nothing here is decided.

## Isolate the agent by a throwaway environment instead of layers

**The idea (the human, 2026-10-20).** The factory and the agent run apart: the factory keeps the hosting token, the state and the push rights; every agent run gets a fresh environment that starts from a snapshot of the checkout, and is thrown away afterwards. The factory takes the run's result as a commit or a diff and keeps only the files in the role's write paths.

**A rolling base snapshot (the human, 2026-10-20).** The snapshot is not taken once: it is pulled forward regularly (after every merge, or after every run), so the base always holds a checkout close to `main`, with its `.venv` and caches already built. A run then starts from that base, and bringing it up to date costs only the last commit (a pull of one commit and, at most, a sync of what that commit changed), not a fresh clone and a full `.venv` build. Rolling back after a run means returning to the base; moving the base forward means taking a new snapshot of the updated checkout and dropping the old one.

**What it would replace.** The second user with `sudo`, the umask and group rules, the leftovers program (F0027-S0001/S0002), the removal of ignored files (F0027-S0003), the fresh agent home (F0040), probably Landlock and the undo. Tonight's restore stops (2026-10-20) came from these layers meeting each other.

**Three variants to compare.**
1. A small Linux VM with ZFS that runs the factory and starts Podman inside for the agent: instant snapshots and clones, `.venv` included (no rebuild per run). Needs an ordinary distribution (Ubuntu ships ZFS; the WSL2 and `podman machine` kernels do not) and a VM of one's own at work.
2. The same with an in-kernel snapshot instead of ZFS: btrfs, or overlayfs (a thin writable layer over a fixed base, thrown away as the rollback). Runs wherever Linux runs.
3. Throwaway containers on Docker or rootless Podman, with a fresh local clone per run or a `commit`-based base image. Neither engine snapshots volumes; both throw a container's own layer away.

**Open questions that decide it.**
- Can the human run a VM of their own at work (Hyper-V or similar), or only Podman Desktop?
- Who starts the agent's environment: a Docker socket is effectively root on the host; a rootless Podman socket is much less.
- Time per run: a fresh clone and `.venv` (tonight: about 3.6 min for a `.venv` rebuild after the removal) against a snapshot clone.
- How the role's write paths are kept: by taking only those files from the result.
- Where the snapshots live. On the host (OpenZFS on Windows is a beta port with its own driver; OpenZFS on OS X needs a kernel extension; native: APFS `cp -c` clones on macOS, ReFS block cloning on a Windows 11 Dev Drive), a container sees them only through the file sharing of Docker Desktop's or `podman machine`'s Linux VM: slow for thousands of small files and without real Unix owners and modes. Inside that VM (btrfs or overlayfs, no extra driver), next to the containers, they run at full speed with real permissions. Leaning: inside the VM (2026-10-20).

**Leading candidate to prototype first (2026-10-20): Podman's overlay mount.** `-v /base/checkout:/work:O` makes the base checkout the read-only lower layer; the container's writes go to a temporary upper layer that is thrown away when the container ends, so every run is rolled back by itself, rootless included. The rolling base snapshot is the lower folder, moved forward between runs by a pull of the last commit, its `.venv` kept. To design: how the run's result leaves before the layer goes (the agent pushes to a small local repository, or the factory reads the diff first). Docker has no `:O`; neither engine offers volume snapshots without third-party plugins (ZFS, NetApp, the old Convoy), which are no option at work.

**Next step when v1.2 starts.** A design note comparing the three variants (security, speed, maintenance, what runs at work) with a small timing prototype.
