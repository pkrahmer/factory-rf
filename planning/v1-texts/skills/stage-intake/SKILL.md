---
name: stage-intake
description: Stage instructions for `ready`. Preloaded into the intake agent; not invoked directly.
---

Check that the story is buildable before anyone spends tokens on it. You do not improve the story; you accept it or ask. The factory has created the ticket branch, written the story's frontmatter and opened a draft pull request with the Assignment and the criteria; you only read and judge. Every tool call is a turn and your turns are few: read the files first, then judge.

0. The story arrives as the human promoted it from `drafts/`. Its id is the file stem without the slug (`F0001-S0003`), its feature the folder two levels up, whose `FEATURE.md` you read as well.
1. If the task's `Branch:` line says intake asked before, the human's answer is in the latest log entries: check the story again with it. When the answer changes the story (adds or rewords a criterion, an Interface line, a Demo expectation), write exactly that into the story and say in your entry which log entry it comes from (a new criterion goes before the two closing ones, R5); that is the human's edit carried in, not an improvement of yours. If the meaning of the task changed, rewrite `## Assignment` and its "as of" heading.
2. The factory has already checked the story's form and names the result in your task (`Format check: passed`, or `Format check found:` and a numbered list): the place and id, every section of `factory/TICKET.md`, an `Expect:` line after every Demo block, the criteria and the log numbered, `make check` and `docs:` as the last two criteria. Every finding is a question; do not check those things again. A story with a finding cannot move on, whatever you answer. Check what code cannot: `## Interface` names concrete modules and signatures, every acceptance criterion is testable by one test function without further decisions, the Demo commands are runnable and each `Expect:` line says something the output can be checked against.
3. Every behaviour stated in an `## Interface` comment (a conversion, a format, an ordering, a default) has a criterion that tests it; one without is a question, because two coders will read it two ways and both will pass the tests. Every rule the Interface states — a limit, a validation, an error raised, a default, a rejected input — has a criterion for the side that fails as well as for the side that passes ("a blank title is rejected with `InvalidTitle`", not only "a title is stored"); a rule whose failing side has no criterion is a question, because nobody will test it otherwise and a later story will discover it in production.
4. Check it against the architecture `CLAUDE.md` describes (and the documents it names): the interface puts things where they belong. Check it against `FEATURE.md`: the story is within the feature's scope and not in its "Out of scope".
5. If anything is missing or ambiguous: end with `question` and the questions as one numbered entry, the format check's findings among them. Do not answer them yourself.
6. If the story is complete: end with `tests`. Your entry starts with `accepted` and then has one line per check of steps 2 to 4, each saying what you found: the Interface; the criteria (each testable, each rule with its failing side); the Demo (runnable, each expectation checkable); the architecture; the scope. A check you cannot write a line for is one you did not do: do it.
