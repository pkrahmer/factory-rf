# GitHub outage of 2026-11-04: how the factory held up

This report reads the evidence the human secured on the morning of 2026-11-04 (the factory log and journal from 09:00 UTC, the stop and command records, the work item of F0050-S0001 (the base image holds only the instance's runtime) with its cost records and transcripts, the timeline of PR #538, the human's night log, and GitHub's status history) and the code that handles a failing hosting service. All times are UTC. The journal of the service is written in local time (UTC+1), so 10:36 in the journal is 09:36 here. Where a statement is a reading of the code or an inference, it says so.

## 2. Did a factory call to GitHub fail, and how was it handled?

**Measured facts.**

- The factory log of 09:00 to 10:13 holds no stop line, no `iteration failed` line, no `died` line and no `error cap reached` line. The stop records show only an old fetch failure on 2026-11-04 at 01:22:26 that cleared 1.6 s later, and a main-branch stop at 02:19; none lies in the window. The health file is empty of stops. So no fetch failed in a way that raised `fetch_failed`, no tick or preparation threw an exception, and no stop was raised. The factory did not stop and did not need to.
- Two things in the window did fail, and neither writes a line to the factory log: the result push of the first docs run (about 09:36:48) and the three hand-over attempts (about 09:40:35 to 09:42:30). The reason they are silent: when a handler raises, the dispatcher counts the error in memory and writes nothing until the third error. Only the third produces a visible report, as a comment on the pull request. The code is in `src/factory/application/dispatcher.py` (`_count`, `_report`).

**Handling of each failure.**

1. The result push of the first docs run. This is the first of the three kinds of outcome that the code allows: nothing was retried inside the stage; the exception left the stage; the dispatcher counted one error; the claim stayed on the remote; at the next tick (30 s idle pause later) the factory saw its own claim, recorded a crash (journal entry 40), discarded the run's work and ran the stage again. The re-run was a second paid agent run for the same result. The work was not lost on the remote, but the finished run was thrown away and done twice, and its cost record was lost (see 3).
2. The hand-over. Three attempts in about 90 s (the pauses are 30 s and 60 s) all failed. The third attempt's error is known: `PushFailed: push of work-item/F0050-S0001 failed: rejected`. The first two errors are not recorded anywhere. They happened before the PR was marked ready, so they failed in the step that sets the description or the draft state, or earlier. This is an inference; it fits the code, because the description is written with a PATCH call, and the installed PyGithub 2.10.0 (`GithubRetry`, read in `.venv`) retries 5xx answers but only for GET, POST, PUT, DELETE and the like, not for PATCH. So a 5xx on the description call would fail at once. This is not proven. After the third error the factory reported once on the PR and, by design, tried no more. The effects before the push (description, ready, cost comment) are safe to repeat and were done once visibly: the cost comment carries a key, so it was posted once. The "handed over" record was never written: the finished file holds `handed_over: null`. This had no consequence because the human merged anyway.
3. The factory's reads and writes at the end: the archive push and the branch deletion at 09:59 and 10:00 succeeded. The 2 min 40 s delay after the merge is not explained by any log line. It fits one or two counted errors (a failed PR read or a failed archive push) in the 30 s and 60 s pauses, but the evidence does not decide this.

**Why no stop appears.** The window was mostly the factory waiting at an approval stage. In that state each iteration (idle pauses of 30, 60, then 120 s) does two fetches, one read of the pull request, and no write. All of these evidently worked, because they would otherwise have raised `fetch_failed` or logged `iteration failed`. By the pause schedule there were roughly 8 to 10 iterations between 09:42:30 and 09:59, so some 15 to 20 fetches. This count is estimated from the schedule; no log line counts them.

**Lost or done twice.** Nothing was lost on the remote: no commit, comment or label was lost, and no state is wrong. Done twice: one docs agent run (about 28 s of agent time) and the hand-over steps that are safe to repeat. Lost: the cost record of the first docs run (see 3).

## 3. The crash at 09:37:25 and the missing cost record

**Cause.** A crash is raised only when a tick finds the factory's own claim on a branch while no stage runs (`claim_status` and `RecoveryHandler`). The service did not restart, so the claim was left behind by an iteration that ended after the claim and before the result was released. The first docs run (transcript session f7dd4ad2, started 09:36:19) ran normally, and its checks passed at 09:36:42 to 09:36:46. The checks run only inside `StageFinisher.finish`, so the agent had finished with an allowed decision. What follows the checks in `finish` is the commit, the push, and the label write. No "docs ends" commit exists for that run on the branch, so the commit or the push did not reach GitHub. The most likely cause is that the push was refused or could not reach GitHub. The crash recording 39 s later and the new claim at 09:37:52 worked, so the trouble was short.

How sure this is: the timing and the code fit and there is no other candidate, but nothing records the exception. The transcripts end at 09:36:34 only because the copier takes a snapshot every 10 s; the successful second docs run's transcript also ends on a tool result, so the end of the transcript is not a sign of an agent failure. Anthropic's status history shows no incident for 2026-11-04. I therefore call it a refused result push during GitHub's trouble, probable but not proven. The outage "caused" it only in this sense.

**Cost.** The cost record of a run is written to the sidecar in the work tree and travels with the stage's result commit. The crash recovery discards everything not on the remote, including that record. This is by design: the decision of F0005-S0008 says a stage that crashes before any commit is discarded "so no run is counted that left no commit". So the run was paid for and not counted: PR #538 reports 19 runs and 7.72 USD, but 20 agent runs started. The unrecorded run's cost is not known. The last budget line in its transcript, taken at 09:36:34, shows 0.12 USD used of 1.50 USD; the run lasted about 7 s longer, so it cost at least that, and probably between 0.12 and 0.25 USD (an estimate; the re-run of the same stage cost 0.11 USD). That is about 1 to 3 per cent of the story's recorded cost.

## 4. Paths an outage would hit that this one did not, from the code and its tests

For each path the table says what the code does. "Safe" means the remote stays consistent and the factory tries again by itself. "Weak" means a gap.

| Path | What the code does | Judgement |
|---|---|---|
| Fetch at the start of a tick (`Tick._fetch`) and in `_follow_main` | A failing fetch raises the stop `fetch_failed`, ends the iteration and clears itself at the next good fetch. Tested (`test_tick*`, `test_stops`). A fetch failure writes a log line every iteration. | Safe |
| Clone and `origin/main` check at the start | `repository_unavailable` stop, reported once. Tested in `test_scheduler`. | Safe |
| Preflight call to the hosting service | It runs only after a new image build. A failure raises the machine stop `preflight_failed`; the next tick checks again. In a job a machine stop standing for 10 minutes ends the process. | Safe on the VM; in a job it ends the process after 10 minutes, as designed |
| Read of the PR at every tick and before every run (`RunGate`) | A failing read becomes the event `pull_request_lookup` or an error before the claim; it is counted and reported after 3 tries. Nothing was started yet. | Safe |
| Push of the claim at stage start | `PushFailed` before any agent runs; tests `test_claims` (226, 247) and `test_stage_launch` (236, 258) show the remote stays without a claim and no run starts. The dispatcher retries. | Safe |

| Report posted on the PR after the cap | If the post fails, it is tried again at the next tick without counting. Tested in the dispatcher tests. | Safe |
| Merge by the human | A human act on GitHub. The factory sees it only through the PR read. | Not the factory's |

The guide tells the human to "push a commit to the branch", which is not possible after a merge. | Weak after a long outage (from reading the code; not seen. Here the archive worked) |

| Publication of the stop records | Failure is logged ("cannot publish the stop records") and the records wait in the state directory. | Safe |

The general rule behind most of this: a handler error is counted three times, with the idle pauses of 30 and 60 s between, so about 90 s. An outage lasts longer (this one about 35 minutes by the human's view). After the third error the factory stops trying that event for that remote state, and only a new commit on the branch or a restart wakes it. That fits a broken file but not an outage of the hosting service.

## 5. Proposed improvements

Each item names the evidence, the risk it removes and a rough size. Sizes: small is under about 40 lines with tests, medium is a day of the factory's work.

1. **Write one log line for every counted handler error.** Evidence: the cause of the crash at 09:36 and the first two hand-over errors cannot be read from anything the factory kept, and I had to infer them. Risk removed: blind diagnosis of any outage or bug. Proposal: `Dispatcher._count` writes `handler error <event key> <n> of 3: <type>: <text>` to the factory log. Size: small. This is the cheapest and most certain gain.
2. **Retry the push of a stage's result and of any recorded change a few times before it fails.** Evidence: the docs result of 09:36 was lost to one failed push, which cost a repeated agent run, an unrecorded cost and one of two crashes. For a doing or tests stage a rerun costs 1 to 2 USD. Risk removed: a short GitHub trouble turning a finished run into a crash. Proposal: in `WorkItemRecorder.publish` and `StageFinisher._commit_and_push`, on `rejected` or `unreachable` wait 5, 15 and 45 s and push again, then raise `PushFailed` as now. A true non-fast-forward rejection fails the same way and only costs about a minute. No forcing. Size: small, with a fake git that fails the first pushes.
3. **Keep git's reason in `PushFailed`.** Evidence: the PR report says only "rejected". Git reports a server error such as "Internal Server Error" on a refused push as a `!` line, which `_is_rejected` calls a rejection, exactly as it calls a lost race; the human cannot tell the two apart and the guide describes "rejected" as another writer or a hook. Proposal: add the last lines of git's output to the exception text. Size: small.
4. **Give the hosting client a real retry.** Evidence: PyGithub 2.10.0 is created with its default `GithubRetry`; reading the installed code shows 5xx and 403 are retried up to the urllib3 default of 10 times with no backoff, and PATCH is not in the allowed methods. The calls `set_description`, `close`, `reopen` and the state edits use PATCH. Whether this explains the first two hand-over errors is a guess. Risk removed: a failing 502 for a few seconds failing a PATCH at once, and the other calls using up their retries in a second. Proposal: pass `GithubRetry(total=5, backoff_factor=2, allowed_methods=<default plus PATCH>)` in `pygithub_service`. These PATCH calls are repeat-safe. Size: small. Evidence level: reading only; no test of the real library.
5. **Let a capped event come back after a long wait.** Evidence: the hand-over was capped at 09:42:30 and never retried during the 20 or more minutes of the incident that remained; the merged and crash events are capped by the same rule and the merged event has no way to get a new remote state. Risk removed: a work item that waits for a human restart after a short outage. The simplest solid form: a capped event is tried once more every 10 minutes, keeping the "reported" mark so no second report is posted. Size: medium, because the dispatcher holds counts only per event and state. I recommend asking the human first (it is a quiz item): the manual route (restart, or a commit on the branch) works today, and the cap protects against a hammered loop.
6. **Do not charge a crash for a stage in which no agent ran.** Evidence: the code reading in 4 (failure of PR create or read after the claim). Not seen in this outage. Proposal: first the test that fails the hosting service after the claim; then either read or create the PR before the claim, or release the claim on that error. Size: small to medium. After improvement 4 this path is much rarer; I would write the test and decide after it.

**What needs no change.** The fetch handling and the `fetch_failed` stop were never triggered, but they are well tested and clear themselves, so a pure fetch outage stops safely. The claim and crash design keeps the remote consistent: nothing was left half-written and nothing was forced. The post keys make comments and the cost table safe to repeat, and the hand-over steps are safe to repeat. The stop records and the stale-branch cleaning wait for the next good tick. The deliberate decision to discard the cost record of a crashed stage can stay: improvement 2 removes most of the cases, and a record without a commit would be a second source of truth. The cost of a run lost this way (here about 0.1 to 0.25 USD) is small.

## Verdict

The evidence shows that the factory kept working through the GitHub trouble of 2026-11-04: it raised no stop, threw no exception out of an iteration, lost nothing on the remote and finished the story. It also shows two real weaknesses. A single failed push of a finished stage result turned into a crash, a repeated agent run and an uncounted run, and a hand-over that failed three times in 90 s was dropped for the rest of the incident without any log line to say why. The cheapest and surest fixes are a log line for every counted error, a short retry of pushes, and keeping git's reason in the error; the capped-event wait and the crash charge without an agent run are worth deciding with the human. What the evidence cannot show is how many fetches and reads failed and were retried in silence, and the exact error of the push at 09:36, because the factory records neither.
